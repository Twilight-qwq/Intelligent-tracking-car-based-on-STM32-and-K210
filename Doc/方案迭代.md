## 1 版本时间线（V0 → 现在）

**怎么读这一节**：**§1.1~§1.16 是 16 个版本**，一个小节 = 一个版本，每节五件事 —— 什么时候 / 为什么改 / 改了什么 / 结果 / **留下来还是退回**。§1.17 和 §1.18 是附在时间线末尾的两份旁证（当前卡住的那件事 + 两个仿真），**不算版本**。带一串字母数字的（如 `33caf6e`）是 git 提交号，可以 `git show 33caf6e` 直接翻出当时的改动；写成 `V-1118` 这种的是**没有留下提交号、只能按日期排**的版本（1118 = 11 月 18 日）。

### 1.1 V0　仓库建立之前（没有提交号）

- **什么时候**：建仓库之前。这份记录最后一次更新是 **2026-11-08**，固件基线叫 `v1.0.0-pre-tuning`（意思是"调参之前的第 1 版"）。
- **为什么改**：车压根不动、或者动起来发抖，必须先把这四件事排掉才能谈控制。
- **改了什么**（四条，全在《优化记录》第 0 节）：

| 编号 | 问题 | 改法 |
|---|---|---|
| 0.1 | **PID 输出限幅全传成 0** —— 编译通过、电机有电、PWM 也在发，车就是不动 | 速度环上下限改成 `±MOTOR_DUTY_FULLSCALE`（**±1000‰**：占空比用千分比表示，1000‰ = 100%）；方向环改成 `±Speed_Straight` |
| 0.2 | **按键定在 PA8**，而 PA8 同时是 TIM1_CH1（左轮 PWM 的输出脚），按键初始化把 PWM 复用功能盖掉了 | 按键挪到 **PA0**，PA8 专供左轮 PWM |
| 0.3 | **OLED 拖垮节拍**：软件 I2C 全屏刷新一次约 **5–10 毫秒**，而内环（管速度的那个环）周期就是 **5 毫秒**，等于"走走停停" | 整个 OLED 模块**删掉**，状态改由板载灯 PC13 和蓝牙/VOFA+ 表达 |
| 0.4 | 浮点用了整型函数 `abs()`（小数被截断）、`USART_Cmd(...)` 少个分号 | 改 `fabsf()` + 补 `#include <math.h>`；补分号 |

- **结果**：车能动了；内环恢复成确定的 5 毫秒，PB8 / PB9 两个引脚被释放。
- **留下来还是退回**：全部**留下来**。0.1 那条后来被当成全工程最隐蔽的 bug 写进了教训：代码没错、编译没错、就是不动。

### 1.3 `49b70e3`　调度上移到 Service 层 + 可选看门狗

- **为什么改**：`main()` 里原来有一份时间片结构，调度和业务混在一起，每加一个任务都要改 `main.c`。
- **改了什么**：
  - `main()` 变成 **14 行**循环：每次只取**一个共享时间戳**，依次交给四个任务 `ServiceTask_5ms / _10ms / _30ms / _100ms`（周期单位毫秒）。
  - 每个任务自己管自己的周期闸门（算出来"离上次执行还不到周期"就直接 `return`）。
  - 新增 `WatchDog` 模块：IWDG，时钟源 LSI 再 **64 分频**，重装值 **625**（约 1 秒不喂狗就复位），由 `WATCHDOG_ENABLE` 控制，**默认关闭**。
- **结果**：加任务只改 `Service.c`，`main.c` 从此没再动过。
- **留下来还是退回**：调度**留下来**；看门狗**留模块但关着**（理由：1 秒内任何一次阻塞都会复位，赛前没验证过最坏情况）。

### 1.4 `976d708`　调试输出改成二进制帧

- **为什么改**：原来用 `printf` + `%.1f` 发文本，依赖 MicroLIB，格式化耗时随小数点位数变，**不可控**。
- **改了什么**：改用 VOFA+ 的 **JustFloat** 协议，一帧定长 **24 字节** = 5 个 IEEE-754 小端 float（每个 4 字节，共 20 字节）+ 帧尾 `0x00 0x00 0x80 0x7F`（4 字节）。通道顺序：左目标 / 左实际 / 右目标 / 右实际 / 视觉误差。发送走 `DMA1_Channel7` → USART2。
- **结果**：彻底摆脱 `printf`；100 毫秒发一帧，115200 波特率下约 **2 毫秒**发完。
- **留下来还是退回**：**留下来**，一直用到现在（后来通道从 5 个扩到 7 个，见 §1.13）。

### 1.5 `3215a30`　编码器采样顺序（白送的一拍延迟）

- **为什么改**：速度环反应偏迟钝，内环有额外的相位滞后（可以理解成"用旧数据算控制"）。
- **改了什么**：`Encoder_GetDeltaLeft/Right()` 返回的是**上一次** `Encoder_Update()` 算出来的增量，而原代码先读后更新 —— 等于给速度环喂了一份过期 5 毫秒的测量值。改成**先 `Encoder_Update()`，再读**。
- **结果**：内环的相位滞后少了一个控制周期（5 毫秒）。串级控制里内环延迟直接决定带宽上限。
- **留下来还是退回**：**留下来**。

### 1.6 `85ae41e`　协议重构 + 手机在线调参（最大的一次改动）

- **为什么改**：三个毛病 —— ① `Protocol.c` 直接暴露全局变量，中断和主循环共享还不加保护；② 蓝牙接收在主循环里同步轮询，会阻塞；③ 调一个 PID 参数要"改代码 → 编译 → 烧录 → 试车"，单次几分钟。
- **改了什么**：对外只暴露 `VisionData_t` / `BtCommand_t` 两个结构体和 `Protocol_GetVision()`；读取时保存/恢复 PRIMASK（关中断再开中断）保证读到完整一帧；蓝牙接收加 **32 字节环形缓冲**，中断只负责存字节；参数校验两层（先拦 NaN / Inf，再按类型做上下限）；基速与 PID 增益改成**运行期变量**；差速限幅改为跟随当前基速；`Service.c` 拆成 **6 个**命名的 handler。
- **结果**：调参从"分钟级"降到"秒级"（手机发一帧立刻生效），这也是后来能快速试出 PID 参数的前提。
- **留下来还是退回**：**留下来**。

### 1.8 `73e2ea2`　PC13 状态灯

- **为什么改**：赛场上不可能一直连着串口，需要一个远距离一眼看得见的状态指示。
- **改了什么**：分两层 —— 硬件层 `IndicatorLED.c` 只做四件事 `Init / TurnOn / TurnOff / Toggle`，不参与决策；策略层是 `Service.c` 里的 `Task_Indicate`，跑在 100 毫秒任务里。三种状态：停车/上电**慢闪**（500 毫秒翻转一次）、运行中视觉正常**常亮**、视觉断线**快闪**（100 毫秒翻转一次）。
- **两个关键设计**：
  1. **故障锁存**：视觉断线会让车自动停，如果"停车就变慢闪"，故障信号就被藏起来了。所以故障标志只在**重新收到真实数据**时清除。
  2. **启动边沿重新计时**：`Vision_LastTick` 初值是 0，若上电 30 秒后才按启动，`30000 − 0 > 120` 会立刻误报断线，所以在"0→1 起跑"那一刻重新打时间戳。
- **阈值**：断线判定 **120 毫秒** = 4 × 30 毫秒，和 `Task_FetchVisionData` 的丢包判定对齐，灯和车同时反应。
- **结果**：不用连电脑也能看出车在干什么。
- **留下来还是退回**：**留下来**。

### 1.10 V-1118　K210 提帧率：19.2 → 38.5（没有提交号，2026-11-18 实测）

- **为什么改**：视觉一帧 **52 毫秒**（= 19.2 帧/秒），车在两次测量之间要盲走一段。当时以为是传感器时序锁死，还编了一套"寄存器卡住"的理论。
- **改了什么**：先实测把各种猜想排除（见下表），最后发现**单缓冲**才是元凶，`sensor.reset(dual_buff=True)` **一行**修好。

| 条件 | 帧率（帧/秒） |
|---|---|
| 单缓冲 + 不处理 | 38.46 |
| 单缓冲 + 每帧处理 20 毫秒 | **19.23** |
| **双缓冲 + 每帧处理 20 毫秒** | **38.46** |

- **连带做的一件事**：分辨率从 160×120 切到 **320×240**（帧率从 19.23 变 38.46），几何量**全部乘 2** —— 焦距 **75.9 → 151.8 像素**，扫描行号 **68/60/52/43/35 → 136/120/104/86/70**；发出去的偏差先除以 2，所以 STM32 那边一个数都不用改。
- **结果**：帧周期 52.0 → **26.0 毫秒**；外环（管方向的环）实际频率 16.7 → **33 赫兹**（被 30 毫秒的检查节拍卡住）；总延迟从 **78 毫秒**降到约 **61 毫秒**（78 = 等帧 26 + 处理 12 + 等节拍 15 + 电机 25）。
- **代价**：最长曝光从 52 毫秒砍到 26 毫秒，场地暗时画面更噪；每帧处理从 6 毫秒涨到 22~23 毫秒。
- **留下来还是退回**：**留下来**。这是"每帧处理完还来得及在 26 毫秒内"的前提。
- **教训（原文照抄）**：相机报的帧率是"空转帧率"，**带负载的帧率才作数**。

> 顺便否掉的一条：想靠"裁剪画面"省算力 —— 裁剪**不改模式**（裁出 160×120 照样 38.46），而裁出来的范围又用不了（最近那行两条线在列 37 和 283，全在裁剪窗口外），所以放弃了。

### 1.11 V-1120　转弯改成"数编码器差分量角度" + 编码器里程台架（2026-11-20）

- **为什么改**：原来转弯看视觉判断"弯结束没有"。但弯里 **66% 的帧好行 ≤ 2**（好行 = 同一行上两条线都认出来的行数），视觉基本是瞎的，由它决定什么时候停，每次转出来的角度都不一样。
- **改了什么**：
  - **原理换了**：转弯时左右轮走的路不一样长，**长度差 ÷ 轮距 = 车转过的角度**。
  - **换算**：1 个编码器计数 / 5 毫秒 = **0.01405 厘米**（由"30 档 = 30 计数/5 毫秒 = 84.3 厘米/秒"推出）；转 90° 要累计 `1.5708 × 轮距 ÷ 0.01405 = 111.8 × 轮距`；轮距 **11 厘米** → **111.8 × 11 = 1230 计数**。
  - **加了台架标定模式**：按住按键上电 → 灯常亮 = 进标定，电机不驱动、可以随便推，推过一段量好的距离就读数。VOFA+ 五个通道 `I0` 左轮累计计数 / `I1` 右轮累计计数 / `I2` 按当前换算出的厘米 / `I3` = 1 表示数值已锁定 / `I4` 保留。
  - **同一个晚上又加了"第二道闸"的前身**：编码器累计到某个数也强制停。
- **结果**：转角第一次有了一个能数的量。但**编码器量的是轮子转多少，不是车转多少**，中间隔着打滑 —— 换个地面（更滑/更涩），同样的计数会转出不同角度。
- **留下来还是退回**：**原理留下来，但"以编码器为准"退了一半** —— 第二天陀螺仪接管了"转多少度"，编码器只当兜底（§1.12）。
- **踩过的坑（后来才认出来）**：台架手推出的 **0.01610 厘米/计数**（112 厘米 ÷ 6955.5 计数）比理论值高 **14.8%**，用户确认那次手推不准 → **永久取消手推标定**，改回理论值 **0.01402**（13 线 × 4 倍频 × 28 减速比 = 1456 计数/轮圈；轮径 65 毫米 → 周长 20.42 厘米 → 20.42 ÷ 1456）。

### 1.12 V-1121　陀螺仪接管"转多少度" + 里程查表 + 语音启停（2026-11-21）

这是全套方案成型的一天，四件事一起进：**陀螺仪、里程表、第二道闸、语音**。

- **为什么改**：
  1. **1730 这个数是在固定场地上被手推出来的**，它把打滑、地面、电量全都折进去了；换个地面、电池电压变低、轮胎磨了，同样的 1730 会转出不同角度。陀螺仪直接量车身转了多少度，**和打滑无关**。
  2. **五个弯角度不同**（直角 90° / 钝角 38.5° / 锐角 103° / 钝角 38.5° / 直角 90°），全按 90° 转必压线；而视觉认不出是哪种，只能认出"有没有弯"。
  3. 陀螺仪半路坏掉时，车会一直转，只剩 800 毫秒超时兜底 —— **800 毫秒 × 240 度/秒 ≈ 190 度**，车直接转成背朝前。
- **改了什么**：
  - **谁决定"是第几个弯"**：里程。每转完一个弯，段内里程清零、弯编号 +1，所以**误差不跨段累积**。
  - **谁决定"转多少度"**：一张按弯编号查的表。
  - **谁保证"真转到位"**：陀螺仪。`Gyro_GetTotalAngle()` 要角度、`Gyro_ResetTotalAngle()` 清零；上电就没认到（`Gyro_IsOk() = 0`）才退回数编码器。
  - **三个能单独回退的开关**：`TURN_USE_MILEAGE_TABLE`（0 = 完全不查表，回到"视觉报弯就转 90°"）、`TURN_USE_38_BENDS`（1 = 两个 38.5° 浅弯也甩，默认 0 = 当直线靠方向环自己过）、`TURN_ALLOW_FORCE`（1 = 里程到了视觉还没报就强行转，默认 0 = 只认视觉）。
  - **第二道闸**：编码器累计超过 **2400** 计数也停。来历：90° 要 1730 计数，103° 约 1980；2400 = 1730 × 1.39，正常转弯（包括 103°）都够不到，不会误触发。
  - **陀螺仪单独成文件**：`HardwareLayer/Gyro.c + Gyro.h`（2026-11-21 用户要求），这里只留"怎么用它"。
  - **语音启停正式接入**：原来的计划注释接上，多两道保险 —— 启动走唯一写入口 `CarRun_Set()`、启动前查 `Vision_EverSeen`（视觉没起来不许启动）；帧格式 `AA 01 55` = 启动、`AA 02 55` = 停车。
- **结果**：转弯从"一个玄学数"变成三个明确的分工。转弯结束条件改一句话就能回退（把陀螺仪开关改 0 就是老办法）。
- **留下来还是退回**：**全部留下来**，这是现在三系统分工的雏形（§7）。
- **注意一个坑（写进代码注释的）**：`Gyro_IsOk()` **只在初始化时决定一次**；跑着跑着 I2C 接触不良，它仍然是 1，角度只是不再增长 —— 这种情况靠 2400 计数兜底，**不是**"自动退回编码器"。

### 1.13 V-1122　门禁改不对称（左 30 / 右 10）+ 遥测四选一 + 里程阈值减外拐点偏移（2026-11-22）

- **为什么改**：
  1. 原来"信不信视觉喊弯"的容差是**对称 40 厘米**，两头都难受（下面写推导）。
  2. 要做台架，就得能换着看不同的数；一个开关四选一比"按住键进台架就自动换"简单。
  3. 三个里程阈值是照《赛道数据》量的，而那份文档写明"**按外轮廓量**"—— 量到的是**外拐点**的里程，车跑的是**车道中心线**，两者相差 `20 × tan(角度÷2)`（20 = 外线到中心线的横向距离，单位厘米）。
- **改了什么**：
  - **容差改左 30 / 右 10**（单位厘米）。先记住：容差不是"提前多少厘米转弯"，它只决定**信不信视觉喊弯** —— `门什么时候开 = 阈值 − 左容差`，`车什么时候转 = 门开 + TURN_ARM_CM(20)`。
    - **左边（早）收到 30**：对称 40 时 180 − 40 = 140 门开，140 + 20 = 160 才转，而 160 正好是内拐点、也正好是合格线 [160, 180] 的最边上；收到 30 后 180 − 30 = 150 门开，150 + 20 = 170 才转，几乎就是理想点 171.5。
    - **右边（晚）收到 10**：车晚报弯本来就几乎不可能（弯一进画面视觉会每帧一直喊）；对称 40 允许 220 也通过，220 + 20 = 240 才开转，那时车已冲出弯口 60 厘米。只留 10，是给"里程刻度偏大"留的余量。
    - **硬约束**：总宽 30 + 10 = 40 必须小于最短一段（110 厘米）的一半（55 厘米），否则会串到下一个弯 —— 满足。
  - **三个里程阈值各减掉"自己的外拐点偏移"**：200 → **180**（90° 弯，减 20 × tan45° = 20.0）；350 → **325**（103° 弯，减 20 × tan51.5° = 25.1，取 25）；350 → **330**（90° 弯，减 20.0）。改完这三个数的含义变成"到中心线拐点（拐角正方形的中心）的距离"。
  - **遥测一个开关四选一**（`TELEMETRY_MODE` 0~3）：0 = 跑车用（车轮目标/实际 ×4 + 视觉偏差 + 报弯里程 + 开转里程）；1 = 视觉台架；2 = 里程台架（和卷尺比的那一项）；3 = 陀螺仪台架。
  - **新增两个锁存通道**：报弯里程、开转里程。为什么锁存而不是发遥测时现取 —— 遥测 100 毫秒一帧，车速 70 厘米/秒时一帧就走了 7 厘米，而关心的转弯窗口本身只有 20 厘米宽，**现取会差出三分之一**。
  - **台架标定抽成函数**（原来直接写在 5 毫秒任务里），并补了一个坑：以前"一静止就锁"，而上电摆车本来就是静止的，1 秒后就把自己锁死 → 加了"已经推过一段"这个前提。
- **结果**：调参从"两个旋钮互相打架"变成"一个弯一个旋钮，而且是线性的（阈值减 5 = 提前 5 厘米）"。
- **留下来还是退回**：**留下来**。注意 `TURN_DIST_EARLY_CM / TURN_DIST_LATE_CM = 30 / 10` 之后一直没再改。

### 2.1 纯里程过弯：设计完了，没实现、没上车（2026-11-21 草案）

这是唯一一份**写完的完整方案却没上车**的。一句话原理：**车按"走了多远"决定什么时候转，按"查表"决定转多少度；视觉只负责直道巡线，以及在明显不对时报警。**

**为什么想这么做**：把"什么时候转"从视觉手里拿出来。视觉在弯里 **66% 的帧好行 ≤ 2**（好行 = 一行上两条线都认出来；其中 **47.5%** 的帧是一条好行都没有），靠它决定转弯时机，每次都不一样。

**方案内容**（数字都照原文）：

- **赛道**：一圈 5 个弯；斜边 **200 厘米**、竖边 **110 厘米**（都沿外轮廓量）；内框宽 **300 厘米**、内框底到底边间隙 **50 厘米**；底边长直道 **≈ 294~300 厘米**；顶部锐角**约 77°**（图纸标的角度）。
- **一圈 = 147 + 110 + 200 + 200 + 110 + 147 = 914 厘米**（按实测的白色路面长度）。
- **别把两个"一圈"混用**：914 厘米是这份草案按"白色路面分段相加"的口径；后来工程上用的是整圈 **998.8 厘米**（见 §6.4），两个数出自不同口径。
- **起转点必须提前**：车走圆弧，半径 `R = 速度 ÷ 角速度 = 42.1 ÷ 4.2 = 10.0 厘米`（42.1 厘米/秒是 15 档的速度，4.2 是当时的角速度）。在拐点上才开始转，车会切进内线 **10 厘米**；要让圆弧和两条边相切，必须提前 `R × tan(θ/2)`：

| 弯 | 转多少 | 提前多少（R × tan(θ/2)） |
|---|---|---|
| 直角 | 90° | 10.0 厘米 |
| 钝角 | 39° | 3.5 厘米 |
| 锐角 | 103° | 12.6 厘米 |

- **四个状态**：巡线 / 等里程 / 转弯 / 恢复。转弯的"停"由编码器说了算（转角累计 ≥ `TurnCnt[Phase]` 就停），**不等视觉**。
- **视觉只当软信号**：里程没到阈值时视觉报弯，**不转**（多半是反光）；连续 3 帧报弯且图案像真弯，把 `Odo`（本段已走里程）**前移一半**，不清零；里程到了，视觉报不报都照转。
- **三道自检**：① 报警计数（连续 3 个弯都"视觉先报、里程还差很远" → `CmPerCount` 上调 10%）；② 一圈对账（一圈总里程和 914 厘米差超 **15%** 就记日志 + 指示灯报警，但不停车）；③ 完全失联（连续两个相位没触发）就退回"视觉报弯 → 转 90°"的老逻辑。
- **仿真结论**（出弯后偏离车道中心多少，半车道 = 20 厘米，超过就是压线）：

| 情形 | 最大横向偏差 | 结论 |
|---|---|---|
| 表填对（提前 R×tan(θ/2)） | **0.5 厘米** | 几乎完美 |
| 表里填了带尺的 147 | **32.5 厘米** | 直接出赛道 |
| 起转点不提前（就在拐点上转） | 12.3 厘米 | 切内线 |
| 刻度偏 +5% | 9.1 厘米 | 可接受 |
| 刻度偏 +10% | 17.0 厘米 | 勉强 |
| 刻度偏 +15% | 24.2 厘米 | 出赛道 |
| 刻度偏 −10% | 19.9 厘米 | 擦边 |

**为什么没上（三个理由，按重要性）**：

1. **前置的三个标定值量不出来**。方案要求先量三个弯的真实转角、每个弯的 `TurnCnt`、里程刻度。其中"里程刻度校准"（直道推 294 厘米、读累计计数）当天就**作废**了 —— 用户原话："做不到，我手推不准，也不要再提手推了。" 手推的值后来被证实偏 **14.8%**（0.01610 vs 理论 0.01402）。
2. **两条最关键的验证没做**：视觉误报时会不会误转（要日志回放）、错位检测能不能抓到（要注入故障）。
3. **容差要求太紧**：里程刻度必须准到 **±10%** 以内（最好 ±5%），偏 15% 就压线；三个转角每差 1°，转 90° 就偏约 **1.3 厘米**。

**最后实际落地的是什么**：方案里"**按里程决定什么时候转**"这一层**上了**，但不是以"纯里程"的形式，而是 **阈值门禁 + 段内里程**：里程只回答"现在这个弯该不该有弯"和"离阈值还差多少"，视觉仍然负责报"这里有弯"（§1.13、§7）。也就是说：**"视觉完全出局"这层没上，"里程当尺子"这层上了。**

### 2.2 《优化记录》第 8 节：五条评估过、明确不做的改动

| 候选改动 | 结论 | 理由 |
|---|---|---|
| 电机低速死区补偿（给占空比加下限） | **不做** | 速度环是闭环 PI，积分项本来就在逐步顶穿静摩擦；硬加下限会在低速段制造极限环（车一顿一顿地抽） |
| 目标速度斜坡 | **不做** | 若直接作用在 `target` 上，急停会延迟约 **200 毫秒**；且 30 毫秒与 5 毫秒两个任务会抢同一个变量。正确做法要用独立变量 + 非对称斜率，赛前来不及验证 |
| 蓝牙环形缓冲加 `count` 区分满/空 | **不做** | 人手发送间隔 ≥ **300 毫秒**，缓冲 100 毫秒排空一次，丢包成本几乎为零 |
| 使能 IWDG 看门狗 | **暂缓** | 模块已就绪，但任何一次 > 1 秒的阻塞都会复位；未在实车充分验证前开启，风险大于收益 |
| `CarRun_State` 单写入点重构 | **赛后** | 能显著降低现场排障成本，但要动 5 毫秒内环和所有写状态的位置，赛前来不及完整验证 |

**判断标准（原话）**：赛前只接受"**编译能验证 + 上车能立刻验证**"的改动；纯结构性收益的改动一律推迟。

### 2.3 《答辩》里三条"不改（有理由）"

| 候选 | 结论 | 理由 |
|---|---|---|
| 把 5 行的行车距离提前算好存表 | **不改** | 这个函数只在启动打印时调用 5 次，一次几微秒，总共不到 **20 微秒**；而把 5 行打到串口本身要 **17 毫秒**，**打印比计算贵 1000 倍**；预存一张表反而多一个要和扫描行列表同步的全局量 |
| 外环节拍从 30 毫秒改成 52 毫秒（跟着帧率走） | **不改 52**，要改往小改 | 方向环里"没有新帧就直接返回"，它实际已经是"来一帧算一次"；30 毫秒只是**检查频率**。改成 52 毫秒反而平均 **26 / 最坏 52 毫秒** 才取走一帧，还会和 52.6 毫秒的帧周期打架 |
| 帧率 19 上不去就换相机模块 | **接受现状** | 换模块（GC0328 / OV2640 通常能 30 帧以上）之后视场角、焦距全变，**整套参数要重新标定**；而且 0.7 米/秒的设计速度在 19 帧的预算之内，帧率不是当前瓶颈 |

**⚠️ 这三条是 2026-11-17 的判断，其中两条的前提后来变了**：2026-11-18 实测查明 19.2 帧是**单缓冲**造成的，不是传感器节拍，`sensor.reset(dual_buff=True)` 一行修到 **38.46 帧**（§1.10）。所以"帧率就只有 19、要靠换模块"这个前提**已经不成立**；但"**换模块不值得**（换了要重标全部参数）"这个结论**没变**。

### 2.4 《待优化清单》里算过账、决定不做的

这几条不是"没想到"，是**想到了、算过、否了**：

1. **远处偏差取最近 3 帧中位数** → **不建议无条件常开**。3 帧中值等于把延迟再加约 **52 毫秒**（78 → 130 毫秒），Kp = 0.15 时相位裕度从 49° 掉到 35°。改成"异常帧才压一帧"（正常帧零代价）。
2. **协议里加 1 字节帧序号**（让 STM32 知道这一帧有多旧）→ **暂时不做**。要同时改 K210 和 STM32 两边，成本高。
3. **"没新数据就发 0"** → **千万不要**。那样车会以 19 赫兹一顿一顿地抽。代码里"防止旧数据"这件事**已经做了**（`Service.c:123` 没新数据就 `return`；`Protocol.c` 的 `data_ready` 收到帧尾才置 1、取数时清零），不需要再加 `if`。
4. **靠裁剪画面省算力** → **没用**。裁剪不改模式（裁出 160×120 照样 38.46），而裁出来的范围又正好缺了最近和最远那几行。省算力的抓手在"每行扫多宽"，不在分辨率。
5. **TF 卡记录脚本在正式跑圈时存图** → **不要**。写卡会卡几百毫秒，会触发 STM32 的断线停车。
6. **换更高帧率的相机模块** → 见 §2.3 第三条，整套参数要重标，代价太大。

## 3 试过但失败的方案

> 这一节里的每一条都**真上过车、真失败过**。写清楚"为什么失败"，是为了不再试第二遍。

### 3.1 方案 A：按转速预测提前停（真实角度表）

- **为什么想这么做**：陀螺仪到了目标角只是撤掉**命令**，车身还在以约 **200 度/秒**转，靠地面摩擦慢慢停，这一段程序完全不管。滑多少取决于电池电压、地面摩擦、打滑程度 —— 同一个弯落地角度每次差 **±8 度**。角度表里那个 **×0.87** 就是"命令少给 13%、靠惯性补到位"的固定补偿，但固定数补不了波动。
- **怎么做**：把角度表换成**真实角度** `{90, 38.5, 103, 38.5, 90}`，然后**按角速度预测提前收**：判据是 `|角度| + |转速| × 0.1 ≥ 目标` 就停（角度是陀螺仪已经转过的度数，转速是角速度，单位度/秒，0.1 秒是往后预看的时间）。
- **结果**：用户实测"**大概率转 180°**"（车头直接对着墙），**全量回退**。
- **为什么失败**：原因**未确证**，当时怀疑转速估计在头几拍不准，提前量乱跳；预看的时间常数一旦偏大就会提前太多、偏小又没用，而真实角度表又比原来那套（×0.87）少了那 13% 的余量。
- **现在怎么绕开**：角度表仍用"眼睛标出来"的值，`×0.87` 那套思路保留（现值见 `记忆.md`）；惯性多转的那部分靠**超时兜底**和**冻住检测**兜着，不再试图精确预测。

### 3.2 方案 B：降差速（想让它停得更干脆）

- **为什么想这么做**：转弯时车身转得快、轮子转得慢，想让"撤命令"那一刻车身动得更少，最直接的办法就是把差速调小。
- **怎么做**：差速 `TURN_VALUE` **11.55 → 9.0**（差速 = 转弯时左右轮目标速度的差的一半，单位是"计数/5 毫秒"）。
- **结果**：**稳定转 180°**，比原来更糟。**此路不通，回退。**
- **为什么失败**：差速降到 9.0 后，右轮目标只剩 **6 个计数/5 毫秒**（换算：6 × 0.01402 厘米 = 0.084 厘米/5 毫秒 ≈ **16.8 厘米/秒**），**克服不了静摩擦被拖停**，车身变成"绕右轮硬拧"，转速反而不可控。
- **连带代价**：试降差速时超时先调到 **900 毫秒**（因为转得更慢了），失败后跟着一起退回 **600 毫秒**。
- **教训（原话）**：这套数是**用眼睛一趟一趟标出来的**，任何"理论上更优雅"的改法都会把这套标定推翻，代价是重新标五个弯。

### 3.3 其余失败清单（按发生顺序）

| # | 试的是什么 | 为什么想试 | 结果 | 为什么失败 / 现在怎么办 |
|---|---|---|---|---|
| 1 | **由视觉判断"弯结束"** | 视觉看得远，理应知道弯过完没有 | 每次转出来的角度都不一样 | 弯里 **66%** 的帧好行 ≤ 2，视觉基本是瞎的 → 改由编码器、再改由陀螺仪决定（§1.11、§1.12） |

## 5 答辩用：问题与优化思路

> **答辩就按这个顺序讲**：我遇到什么问题 → 怎么分析 → 怎么改（或为什么不改）。
> **标注规则**（讲的时候要说出来）：**【实测】** = 真机上量到的；**【模型】** = 按相机参数算出来的，只说明趋势；**【待做】** = 还没动手的。

### 5.0 一句话总览

这套视觉系统做四件事：

1. **相机几何**：把"画面第几行"换算成"车前多少米"；
2. **逐行找线**：在每一行上找黑色线段，配对出车道中心；
3. **多行合成**：近处几行给方向，远处两行给速度档；
4. **判定层**：丢线保护、弯道提前量、终点线识别。

设计和调试过程中一共识别出 **12 个具体问题**，分三类：**已定方案待实施 / 已实测确认 / 分析后决定不改**（§5.8 的状态总表把其中几条拆开列，共 15 行）。

### 5.1 相机几何（2 个问题）

| # | 问题 | 分析与结论 | 状态 |
|---|---|---|---|
| 1.1 | **安装参数是估的，现场又量不准** | 视场角只进一个式子：`焦距 f = 画幅半宽 ÷ tan(视场角 ÷ 2)`，算出 **75.9 像素**。f 只影响三处：①每行对应的车前距离（**不参与控制**，只用于启动打印）；②每行的半车道宽初值（**运行时会自己校准**，每帧往实测值挪 1/16）；③启动时选哪 5 行（这一项不会自校准）。所以参数偏了，最坏结果是"选出来的 5 行偏上或偏下几行"，**不会让系统失效** | 【待做】用"实测半宽 ÷ 理论半宽"反推真实焦距 |
| 1.2 | **5 行距离为什么不提前算好** | 这个函数只在启动打印时调用 5 次，总共不到 **20 微秒**，而把 5 行打到串口本身要 **17 毫秒** —— **打印比计算贵 1000 倍**；预存一张表反而多一个要和扫描行列表同步的全局量。判断标准：**这个量会不会变 + 这段代码多久跑一次** | **不改（有理由）** |

> 答辩时如果被问"参数到底准不准"：2026-11-23 已经实测标过一次 —— 低头角 **33.5°**、等效高度 **17.7 厘米**（只用了前 6 行拟合，残差 1.4%，见 §1.14），所以口径是"**标过一次，但还要复核**"，不是"完全没量过"。

### 5.2 找线（3 个问题）

| # | 问题 | 分析与结论 | 状态 |
|---|---|---|---|
| 2.1 | **每一行为什么自己算黑白分界线** | 三种做法：整幅图固定一个阈值（最省，灯光一不均就废）；整幅图大津法（要扫全部 **19200** 像素，太慢）；**每行自己算（采用，只扫 152 像素）**。做法是 `最暗 + (最亮 − 最暗) × 0.40`，取 0.40 而不是中点 0.50，是因为**黑线边缘有过渡带**，取中点会把灰边也算成黑，把线撑宽、中心拉偏 | 已实现 |
| 2.2 | **黑段长度为什么卡 3~26 像素** | 太短（1~2 像素）= 噪点；太长（> 26 像素）= 阴影、污渍、几条线糊在一起。**有用的副作用**：终点线是横的，会在某一行形成极长的黑段，**正因为"太长"被排除**，但它的像素数照样记进"本行黑点数"——这成了后面识别终点线的基础 | 已实现 |
| 2.3 | **只剩一条线时中心怎么推** | 用查表的半车道宽往内推；但线压在画面正中时，分不清是外侧线跑到中间还是内圈线跑到中间，**猜错方向会直接打反**，所以中间留 **12 像素**死区，宁可不给 | 已实现 |

### 5.3 弯道判据（答辩重点，4 个问题）

| # | 问题 | 分析与结论 | 状态 |
|---|---|---|---|
| 3.1 | **`左线列号 < 50` 到底在判什么** | 只剩外侧线时，返回的中心 = `左线 + 半车道宽`，所以 `lane_center − 半车道宽` **就是在把左线的列号还原回来**。等价变形（半车道宽按第 68 行的 62 算）：`lane_center − 62 < 50 ⇔ 推出的车道中心 < 112 ⇔ 偏差 < +32`。它真正的作用是"**排除**"：车明显偏在车道左边时，右线被挤出画面也会"只剩一条线"，**那种情况不是弯** | 分析清楚，判据保留 |
| 3.2 | **近两行判弯、远两行判速度，为什么不统一** | 近处像素密度高（1 厘米约 **2.2 像素**），**看得准但看得近**，等它有反应车已到弯口 → 适合**打方向**；最远两行看得远（**0.64 / 0.96 米**），但一个像素就是 **1.3 厘米**，抖 → 适合**判断要不要减速**。分工：打方向用 5 行加权（近处权重大）、降速度用最远两行、补提前量用最近两行 | 结构保留 |
| 3.3 | **车已经偏右进弯，近两行全丢怎么办** | 车偏右 → 车道整体出现在画面左边 → 外侧（左）线被推出画面；同时内圈线在弯口被切线拉长丢掉 → 近两行一条线都没有。此时**弯道信号不会亮**（它要求"只剩外侧线"），而 5 行里只要还有 1 行找到就走不到"丢线保护"，**方向完全由远处那两行决定，而它们本来最抖**。思路：①近两行全丢时沿用上一帧方向；②弯道信号加"远行也确认" | 【待做】 |
| 3.4 | **一帧反光/一大块黑，会不会打错方向** | **【实测】证据**：画面里放一大块黑色物体，打印立刻出现 `中心 74 / 只剩外侧 / 弯道信号 1` —— **一帧就触发**，偏差被强行改成 **40**。现有三道闸在直道上都挡不住（反光一照"只剩外侧"就成立；直道上左线本来就在 18~24 列，天然满足 < 50；"偏差 < 8 才允许强行改"在直道上也满足）。思路按性价比：①连续 2 帧确认；②远偏差取 3 帧中值；③速度档进出用两个门槛 | 【待做】 |

### 5.4 采样可信度（1 个问题）

| # | 问题 | 分析与结论 | 状态 |
|---|---|---|---|
| 4.1 | **只扫 5 行，可信吗** | 5 行 × 152 像素 = **760 个点**，占整幅 **19200** 像素的 **4%**。但赛道线是**竖直**的，一条横线扫过去就能定位它，不需要整幅图。风险：任何一行被破坏就整行作废，坏 2 行就是 **40%** 信息没了，而代码只会"少算一行"，不会知道这行可疑。思路：**先在时间上加确认**（连续几帧一致才算），不花算力；**不急着加行数**，加行会掉帧率，帧率掉下去比少一行更糟 | 结构保留 |

### 5.5 时序与控制（4 个问题）

| # | 问题 | 分析与结论 | 状态 |
|---|---|---|---|
| 5.1 | **帧率只有 19，为什么** | **【实测】排除过程**：160×120 自动曝光 19 / 固定 15 毫秒曝光 19 / **降到 80×60（四分之一大小）19.2** / 指定 30 帧 19.2 / 关掉画面回传 19（差 0.5）。结论：**不是脚本、不是显示、不是曝光、不是分辨率**，是传感器固定节拍（当时判断为 52 毫秒一帧的硬件节拍；后来查明是**单缓冲**，见 §1.10） | 已查明，接受现状 |
| 5.2 | **帧率上不去，速度是不是也上不去** | 19 帧 = 52 毫秒一帧，每帧盲走：0.7 米/秒 → 3.6 厘米（占半车道宽 27.5 厘米的 **13%**）；1.0 → 5.2 厘米（19%）；2.0 → 10.4 厘米（38%）。完整延迟链 = 等帧（平均 26、最坏 52）+ 处理 10~15 + 等外环节拍（平均 15、最坏 30）+ 电机约 25 → **平均 60~70 毫秒、最坏约 100 毫秒**。结论：**实用上限约 1 米/秒**，设计的 0.7 在预算之内 | 不改 |
| 5.3 | **外环节拍要不要从 30 改成 52** | 方向环里"没新帧就直接返回"，实际已经是"来一帧算一次"；30 只是检查频率。取帧延迟：30 毫秒 → 平均 15 / 最坏 30；52 毫秒 → 26 / 52（**更差**，还会和 52.6 打架）；10 毫秒 → **5 / 10（更好）**。**⚠️ 连带条件**：断线保护按**调用次数**算（连续 4 次收不到就停车），周期缩小 3 倍，阈值必须从 3 改成 12，否则每隔几帧自己停车 | 【待做】往小改 |
| 5.4 | **开机等曝光那 2 秒，车不会动** | 这 2 秒视觉一帧都不发，而 STM32 连续 4 次收不到数据会自动停车 → 安全，但按了启动车会顿一下再停。已定方案：①持续发"最低档 + 偏差 0"的帧；②不死等：连续两帧平均亮度差 **< 3** 就立刻切正常判断；③兜底最多 2 秒。**【实测】** 2 秒盲跑几乎不偏（最低档 0.42 米/秒 × 2 秒 = **0.84 米**；提前结束实际只盲走 **0.2 米**左右） | 【待做】 |

### 5.6 终点线检测（1 个问题）

| # | 问题 | 分析与结论 | 状态 |
|---|---|---|---|
| 6.1 | **80% 这个阈值准不准** | 三个问题：①`FINISH_LINE_ROWS = 4` **永远不成立**（5 行分布在车前 0.28~0.96 米，一条 5 厘米横线不可能同时盖住 4 行）；②**80% 是拍的**，线是斜的、落在两行之间、边缘被反光吃掉，占比都会降，**必须现场标定**；③建议换判据：**一条超过 80 像素的连续黑段**，不依赖曝光、不依赖车正不正。代价：现在只返回"黑点总数"，要让它多返回一个值 | 【待做】，且整块检测现在**关着**（`FINISH_LINE_ENABLE = False`），不影响跑车 |

### 5.7 工程方法（答辩可以讲的方法论）

**方法一：模拟只能给机理，给不了数字。**

为了回答"锐角弯时左线会不会跑到 50 列以右"，用真实相机参数建了模拟。**失败过两次**：①第一次把转弯前后两段路当成"两个半平面"拼接 → 黑线横切进白色赛道、出现大片黑块（模型错误）；②第二次改成连续折线，但**每个像素只朝地面取一个采样点** → 细线被采成虚线（采样错误）；③最后改成 **4×4 子采样 + 镜头模糊**（一个像素把覆盖面积平均掉），画面才和真实相机接近。

**结论**：模型能说明趋势（"远处的行先变"），但具体数字必须实测 —— 所以第二天安排现场实测，而不是继续改模型。

**方法二：分级验证（每一级都有独立的打印，出问题能定位到具体一层）**

1. 先测**相机能不能出图**（芯片 ID、亮度、对比度、帧率）；
2. 再测**单行能不能认出线**（黑段数、中心列）；
3. 再测**多行合成**（哪几行先丢线、弯道信号什么时候亮）；
4. 最后才闭环跑车。

**方法三：不轻易改代码。**

发现一个问题 → **先写进《待优化清单》**（记下现象、改法、收益、风险）→ 初版程序**存档之后**再一条一条改 → **一次只改一条，改完上车对比，不行就退回去**。

### 6.2 弯道状态机为什么拆成两半

这是整个工程最要紧的一个结构决定：

| 一半 | 跑在哪个任务 | 干什么 | 依赖视觉吗 |
|---|---|---|---|
| `Task_CornerDecide(state)` | **30 毫秒**任务 | **认不认这个弯**（视觉说这里是弯、里程也认账），返回 1 = 已接管 | **依赖**（没新帧第一句就 return） |
| `Task_5ms_CornerStep(curr_ms)` | **5 毫秒**任务 | **什么时候开转、转够了没有** | **不依赖** |

**为什么必须分开**：弯里 **47.5%** 的帧"一条好行都没有"（好行 = 一行上两条线都认出来）。视觉一黑，30 毫秒任务第一句就 return；如果"停"也写在那一半里，转弯就永远停不下来，车身一直转（约 **240 度/秒**）。

**目标速度只有一处赋值**：`Corner_SetTarget(kind)`，`kind` 是四种 `CORNER_T_*`。谁想改目标速度都得走它，这样不会出现两处互相打架。

### 6.3 一个弯从头到尾走一遍

1. **视觉报弯**：只回答"这里有弯"，**不再决定开转时刻**（它看得比车走得远，所以这句话总是比车到达弯早很多）。
2. **开转时刻由里程定**：段内里程走到 `阈值 − R` 就开转。`R` 是转弯时**内侧轮的转弯半径**，实测量出来是 **10.7 厘米**，所以现场看到的规律是 `开转里程 ≈ 阈值 − 10.7`（例如阈值 180 时，169.3 附近开转）。原来还有第二条路 —— "视觉报弯之后再走 `TURN_ARM_CM`（一度是 20，后来 16）"—— 现在用 **`TURN_ARM_CM = 999`** 把它彻底关掉了，一个弯只剩**一个**旋钮，而且是线性的：**阈值减 5 = 提前 5 厘米**。开转的那一刻，**陀螺仪角度清零**。
3. **陀螺仪量到转够目标角**：立刻停并锁存 —— 段内里程清零、弯编号 +1、目标速度拨到出弯档。

> 状态名对应：第 1 步之后是"已报弯、等开转"（`Corner_Armed`），第 2 步进"正在转"（`Corner_Active`）。

**为什么是"里程定何时、陀螺仪定多少"**：视觉只负责"这里有弯"（它认得出有没有弯，认不出是哪种弯）；何时开转由里程定（不受视觉抖动影响）；转多少度由陀螺仪定（不受打滑影响）。

**三道兜底，一个都不能少**：

| 兜底 | 触发条件 | 防的是什么 |
|---|---|---|
| **超时** | 转够时间上限还没到位 | 一切没预料到的情况，最后一道闸 |
| **编码器计数上限**（2400） | 转弯中累计（左 − 右）超过这个数 | 陀螺仪**半路**坏掉（`Gyro_IsOk()` 仍为 1，角度不涨） |
| **冻住检测** | 编码器已经数了 1400 计数（车确实在转）而陀螺仪角度 < 10 度 | 陀螺仪哑火 → 停在 **80~90°**（可救），而不是 180°（灾难） |

**四个容易讲错的点（都在代码注释里写明过）**：

- **转弯中途不许被"视觉说不是弯"取消**。弯里 47.5% 的帧一条好行都没有，视觉在转弯过程中本来就经常哑火；而一个 90° 弯要转 **374 毫秒**（= 90° ÷ 240 度/秒），"连续 3 次方向环说不是弯"只有 **90 毫秒**（3 × 30 毫秒）。真正的结束条件只有两个：**转到目标角**或**超时**。
- **"连续 3 次方向环"数的是方向环调了几次，不是视觉出了几帧**。视觉是约 **27.7 毫秒**一帧（36 帧/秒），方向环 30 毫秒看一次，所以计数器每 30 毫秒才可能 +1（旧注释写"3 帧 = 300 毫秒"是错的，那时视觉还是 10 赫兹）。
- **转完立刻把目标改成直行**，而且要拨到**出弯档**、不是直道档：接下去还有 **500 毫秒**是盲开的（`CORNER_HANDOVER_MS`），那段时间加速会越跑越偏。为什么要"立刻"：目标速度只有 30 毫秒任务会改，而要等下一帧视觉（最多 27.7 毫秒）；如果视觉正好在这一刻断掉，目标会一直停在转弯差速上，直到 330 毫秒超时停车 —— 这段时间车会再转将近 90°（离线仿真验证过）。
- **转完只保证"大致到位"**。编码器量的是轮子转了多少，不是车转了多少，中间隔着打滑。剩下的 ±20 度交给视觉去修 —— 视觉不擅长从 0 转 90°，但很擅长修这 ±20°。

### 6.4 里程这一块：一个数干四件事

段内里程 = **从上一个弯转完到现在走了多少厘米**。

| 用途 | 和谁比 | 说明 |
|---|---|---|
| ① 决定该不该转、转多少度 | 阈值表 / 角度表 | 按弯编号查表 |
| ② 当冷却用 | `CORNER_COOLDOWN_CM` | 防止同一个弯被报两次（实测推车时出现过"报弯 → 松开 → 又报弯"） |
| ③ 台架核对 | `Odo_LeftTotal` / `Odo_RightTotal` | 两轮从上车到现在一共转了多少计数，**永不清零**；段内里程每过弯就清零，要量"整段距离"必须有一个不清零的 |
| ④ 终点停车 | `Task_5ms_FinishStep` | 最后一个弯转完，再走够固定里程就停车 |

**为什么不数整圈**：整圈 **998.8 厘米**，按 ±2% 的刻度误差会累积到 **±20 厘米**；每过一个弯清零，最长一段 350 厘米，误差只有 **±7 厘米**。

**终点兜底那一小段代码**（这是全工程最容易被"只看结论"讲错的一段）：

```c
static uint8_t Task_5ms_FinishStep(void)          // 每 5 毫秒问一次：该停车了吗
{
    if (Finish_Armed == 0) return 0;              // 还没转完最后一个弯 → 不管
    if (Corner_SegMileage < FINISH_STOP_CM) return 0;  // 段内里程还没走够 → 不管
    Finish_Armed = 0;                             // 只停一次，先把"待停车"标记清掉
    CarRun_State = 0;                             // 进停车状态
    Motor_SetDuty(0, 0);                          // 立刻把占空比写成 0，断输出
    return 1;                                     // 告诉调用者：这一拍我处理完了，别再算 PID
}
```

- **为什么必须 `return 1` 马上返回**：这段代码在 5 毫秒任务里排在 PID **之前**。如果只写 0 不返回，下面几行马上算出新的 PWM 又把电机推起来；而下一拍 `CarRun_State == 0` 会提前退出，**没人再写 0** —— 车就带着最后那份 PWM 一直跑（最长到 100 毫秒后的 `Task_CarStop`）。
- **为什么是 99 厘米**：最后一段中心线 **98.8 厘米**；转完弯那一刻车已经在中心线拐点之后约 **5 厘米** → 到起点线约 **93.8 厘米**；再留 **5 厘米**保证确实过了线。这个数等实车量完"转完弯到起点线"再定。
- **"什么时候置 `Finish_Armed`"有个坑**：判断必须放在**弯编号自增之前**。`Corner_Index` 记的是"正在处理的这个弯"，转完才加一；"刚转完的是不是最后一个"只能在加一之前问，否则第 2 个弯转完编号已经变成 2（最后一格），会被误判成最后一个也转完了。

| 转完 | 进来时编号 | `2 + 1 >= 3`？ | 置位？ | 编号变化 |
|---|---|---|---|---|
| 第 1 个弯 | 0 | 否 | 不置 | 0 → 1 |
| 第 2 个弯 | 1 | 否 | 不置 | 1 → 2 |
| 第 3 个弯 | 2 | 是 | **置位** | 不动 |

顺序反了的后果很严重：车在第 2 个弯后 99 厘米就停 —— 那时第 3 个弯（当时阈值表里是 330 厘米，见 §1.13；现值看 `记忆.md`）还在 231 厘米外。

**③ `scan_one_row(img, row, row_index)`：一行怎么变成"这一行的中心列"**

- **传进去**：画面 `img`、行号 `row`、这一行是第几行 `row_index`（0 = 最近）。
- **返回 8 个值**，顺序固定：中心列、单线标记、合格段数、实测半宽、暗点数、最暗、最亮、段列表。

| 步 | 干什么 |
|---|---|
| 1 | 把第 4 列到第 155 列共 **152 个像素**读进一个列表（跳过左右两侧暗角） |
| 2 | 找这一行最暗、最亮的灰度 |
| 3 | 最亮 − 最暗 **小于 70** → 这行根本没有线，直接返回"没线" |
| 4 | 分界线 = 最暗 + (最亮 − 最暗) × **0.40** |
| 5 | 扫过去，连续低于分界线的算一个"黑段" |
| 6 | 段长 **3~26 像素**才算线（太细是噪点，太宽是阴影或横线） |
| 7 | 每段的中心列 = （起列 + 止列）÷ 2 |
| 8 | 找到**两段以上**：中心 = 左右两条线的平均；实测半宽 = (右 − 左) ÷ 2 |
| 9 | 实测和理论差 ≤ **14 像素**，就把理论半宽往实测挪 **1/16**（自己校准） |
| 10 | 只有**一段**且在 **68 列**以左 → 那是外侧线，中心 = 左线列 + 半车道宽 |
| 11 | 只有**一段**且在 **92 列**以右 → 那是内圈线，中心 = 右线列 − 半车道宽 |
| 12 | 只有一段但夹在 68~92 之间 → 分不清是哪条，返回 **−1**（这行作废） |

**68 和 92 怎么来的**：中心列 **80**（160 宽画面的正中那一列）± 单线死区 **12** = 68 / 92。一条线离画面中心不到 12 像素，程序分不清它是左线还是右线，所以放弃这一行。

**举个例子**：某一行扫出两段，20–25 和 140–145。左线中心 = (20+25) ÷ 2 = **22**；右线中心 = (140+145) ÷ 2 = **142**；这一行车道中心 = (22+142) ÷ 2 = **82**；实测半宽 = (142−22) ÷ 2 = **60**；这一行对偏差的贡献 = 82 − 80 = **+2**。

**④ `scan_frame(image)`：5 行怎么合成一个"要发出去的偏差"**

- **传进去**：一张 160×120 的灰度图。
- **返回 10 个值**：五行结果、偏差、远偏差、找到行数、远处找到行数、弯道信号、触发弯道的行、状态、实际发出的误差、备注。

| 步 | 干什么 |
|---|---|
| 1 | 5 行挨个调 `scan_one_row()` |
| 2 | 在预览画面上画扫描线和圆心（只是显示） |
| 3 | 算**弯道信号**（见下） |
| 4 | 每行算出 (中心列 − 80)，乘权重累加 |
| 5 | 偏差 = 加权和 ÷ 权重和 |
| 6 | 远偏差 = **只用最远两行**（第 4、5 行，权重 2 和 1）同样算 |
| 7 | 一行都没找到 → 10 帧内沿用上次，超过 10 帧降档 |
| 8 | 按判定规则算出"实际会发出什么" |

**弯道信号的全部内容，只有三条**（这就是"直角/锐角识别"）：

1. 这一行"**只剩外侧**"（单线标记 = 1）；
2. 只允许**最近两行**（`row_index ≤ 1`）触发；
3. 推出来的左线列号在 **0 ~ 49** 之间（小于 50）。

三条同时成立 → 弯道信号 = 1。**注意第 2 条**：只有最近两行能触发，也就是说这个信号是**车已经压到弯口上**才出现的，不是提前看到的 —— 这就是"估计不来直角和锐角"的地方：不是几何错了，是这个判据本身就只在最后一刻才亮。

**偏差怎么合成**：五行偏差 +10、+8、+4、0、−2，权重 3、3、2、2、1 →
`(3×10 + 3×8 + 2×4 + 2×0 + 1×(−2)) ÷ (3+3+2+2+1) = (30+24+8+0−2) ÷ 11 = 60 ÷ 11 = +5`。

**"实际发出"和"偏差"不是一回事**（后面四步全在改它）：

| 步 | 干什么 |
|---|---|
| 先校准 | 偏差 × 1.0 − 0（校准值当时是 0） |
| 弯道顶 | 弯道信号 = 1 **且** 偏差 < 8 → 偏差直接改成 **40**（强行打满方向） |
| 判档 | 远偏差绝对值 < **10** → 状态 0；< **22** → 状态 1；否则状态 2（三档基速当时是 25 / 20 / 15） |
| 兜底 | 远处一行都没找到 → 至少状态 1；弯道信号亮了 → 直接状态 2 |

**⑤ 打印一块长什么样**（8 行，现场就靠它判断）

```text
===== 采样#3  组=1 直道正中  运行 7.5 秒  fps 19.2  用时 12.4 ms =====
行  68 | 暗 25 亮200 | 段 16-21* 139-144*          | 中心   79 | 两条 | 实61 理61
行  60 | 暗 28 亮195 | 段 18-22* 136-141*          | 中心   78 | 两条 | 实59 理52
偏差 +1 | 远偏差 -3 | 弯道 0 | 状态 0 | 找到 5/5 | 远 2/2
实际发出 +1
```

- `fps` 是实际帧率（当时应该 19.2）；`用时` 是 `scan_frame` 花多少毫秒（超过 30 毫秒就是太慢）。
- `暗` `亮` 是这一行最暗、最亮灰度（对比度 < 70 就认不出线）。
- `段` 是所有黑段的起止列，带 `*` 的是被当成线的 —— **判断"这一行到底看到了什么"就看这里**。
- `实61 理61` = 实测半宽 / 算法当前用的半宽，两个数差 ≤ 3 说明安装参数对。
- 第 7 行是原始测量结果（要抄回表格的主力）；第 8 行 `实际发出` 才是真正发给 STM32 的数。

**⑥ 主循环**：开机（`sensor.reset()`、灰度、QQVGA 160×120、丢掉前 2 秒画面等自动曝光稳定）→ 打一张开机表（焦距、镜头参数、分界线规则、5 行行号表、判档阈值）→ 死循环：拍一张 → 计时 `scan_frame` → 累加用时和帧数 → 到了 2500 毫秒打一块、计时清零。帧率算法：`这一窗口的帧数 × 1000 ÷ 这一窗口的毫秒数`。

## 7 三个系统分别管什么（视觉 / 里程 / 陀螺仪）

> 一句话：**视觉说"有弯"，里程说"是第几个、什么时候转"，陀螺仪说"转够了没有"。** 三个各管一段，谁也替代不了谁。
> 配图见 `Doc/image/图42_整条链路.png`。

### 7.1 分工表

| | **视觉（K210）** | **里程（编码器）** | **陀螺仪** |
|---|---|---|---|
| **管什么** | ① 直道上车偏左还是偏右（给方向环）；② "这里是不是弯"；③ 远处看得见看不见（决定减速） | ① 现在是第几个弯；② 离本段阈值还差多少厘米（门禁 + 开转点）；③ 冷却（防止同一个弯报两次）；④ 终点停车 | 转了多少度（车身真实转角） |
| **输入** | 摄像头画面 | 左右轮编码器计数 | I2C 读到的角速度，按时间积分 |
| **输出** | 一个偏差数字 + 一个"有弯/没弯"的信号 | 厘米 | 度 |
| **什么时候说话** | 30 毫秒任务里（有帧才说） | 每 5 毫秒 | 每 5 毫秒读、转弯时每 5 毫秒判 |
| **不信它的理由** | 弯里 47.5% 的帧一条好行都没有；单帧反光就能误报"弯"；报弯早晚差 19 厘米就毁整圈（仿真 60.2% 没分） | 打滑时编码器读数约为真值的 2 倍；编码器坏一个里程就偏小，车永远"没走到" | 软件 I2C 在振动/大电流下丢数；`Gyro_IsOk()` 只在初始化决定一次，跑着坏了它照样是 1 |
| **它出错谁兜** | 收不到视觉数据 → 自动停车（阈值与转弯中的放宽值见 `记忆.md`）；PC13 快闪报警 | 不对称门禁（左 30 / 右 10）把"里程明显不对时的报弯"当假信号；终点停车的唯一手段就是里程 | 2400 计数上限 / 超时 / 冻住检测（§6.3） |

### 7.2 为什么必须三个一起

- **只信视觉**：弯里它基本是瞎的（47.5% 的帧一条好行都没有），由它决定什么时候停，每次转出来的角度都不一样 —— 这是 §1.11 要换掉它的原因。
- **只信里程**：里程量的是"轮子转了多少"，打滑、地面、电量全都能骗它；而且一旦错位**它自己不知道**，后面全错（纯里程方案专门写了三道自检，见 §2.1）。
- **只信陀螺仪**：它只回答"转了多少度"，不回答"该不该转"；而且它一坏，车会一直转 —— 当时是 800 毫秒超时，800 毫秒 × 240 度/秒 ≈ **190 度**，直接背朝前（现在的超时值见 `记忆.md`）。

**所以现在的分工是**：

- **要不要转**：视觉报"有弯" → 里程用阈值确认"这个弯现在该出现吗"（对不上就当假信号，不转）；
- **什么时候转**：段内里程走到「阈值 − 内轮半径 10.7 厘米」就开转（"报弯 + `TURN_ARM_CM`"那条路已用 999 关掉）；
- **转多少**：查表（按第几个弯）+ 陀螺仪量到位就停；
- **转完**：立刻拨到出弯档、直行 500 毫秒（让相机从弯道画面里缓过来），再把方向盘交回视觉。

### 7.3 一张"谁拍板"的对照表

| 时刻 | 谁拍板 | 其余两个在干什么 |
|---|---|---|
| 车在直道上偏了 | **视觉**（偏差） | 里程在累加；陀螺仪在积分（但没人看角度） |
| 决定"这里有个弯" | **视觉**（报弯） | 里程核对"这个位置该有弯吗"；陀螺仪待命 |
| 决定"什么时候开始转" | **里程**（走够开转点） | 视觉已经说完话；陀螺仪在开转那一刻被**清零** |
| 决定"转够了没有" | **陀螺仪**（角度到位） | 里程在累计转角（兜底用）；视觉在弯里基本瞎着 |
| 决定"停车" | **里程**（终点兜底） | 视觉那条"终点信号"是死代码（K210 只发 0/1/2，`case 3` 永远走不到） |

**最后一句**：三个系统里，**视觉最容易骗人但看得最远，里程最老实但会被打滑骗，陀螺仪最准但最容易坏**。这套方案的全部设计，就是让它们互相检查 —— 而不是让任何一个单独说了算。
