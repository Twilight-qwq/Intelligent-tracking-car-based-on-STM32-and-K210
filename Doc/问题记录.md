# 问题记录（从建车到现在的全部坑）

> 怎么看：每一条都是「**现象 → 原因 → 解决 → 教训**」四段，编号从 1 到 88 全文连续（不会每个大节重新从 1 开始）；先按大节找方向，再拿现象里的词去搜，不要从零猜。
> 时间跨度：2026-11-16 ~ 2026-11-24。

## 一、视觉（K210 / 摄像头）

### 1. 直道画龙（车左右来回摆）

- **现象**：直道上车像画龙一样左右摆，越跑越收不住。
- **原因**：三个叠加 ——
  ① 视觉在弯口附近九行只剩 1~3 行（九行 = 画面里在车前布下的 9 条横向扫描线，一条叫一行），偏差本身在跳：单帧能跳 10~23 格（偏差 = 均值 − 中心列；均值 = 左右两条黑线中心列取平均，中心列 = 画面正中那一列 = 80；1 格 ≈ 0.48 厘米）；
  ② 方向环（管「往哪边打方向」的那条 PID）的 Kp（比例系数：偏差乘它就得到差速）过大，为 0.231，偏差 13 格就要求 3 个计数差速（计数 = 编码器数到的脉冲，5 毫秒一个控制周期数一次）；
  ③ 死区（偏差比它小就当 0 的一段）±3 格，正好把「车头歪 2 度以内」整段吃掉，小偏差永远不纠（这条展开见第 24 条）。
- **解决**：Kp 0.231 → **0.15**；D 项（微分项：偏差变化越快，出力越大）每帧限幅 8 → **4**（挡住假跳变）；死区 3 → **1** 格。
- **教训**：**先治噪声，再谈加阻尼**。顺序反了会越调越糟。

### 2. Kd 一加大，画龙反而更严重

- **现象**：把 Kd（微分系数）从 0.53 提到 1.10 想加阻尼，用户实测「更大了，十分严重的画龙」。
- **原因**：偏差会单帧跳 10~23 格（反光 / 褶皱骗的）。Kd 越大，跟着这些假跳变抽的鞭子越狠 —— 那不是阻尼，是往火上浇油。
- **解决**：Kd 退回 0.53，改为把 **D 的每帧限幅从 8 砍到 4**。依据：真摆动时偏差每帧只变 3.4 格，限幅 4 对真阻尼毫无损失，却能把 10~23 格的假跳变砍掉大半。
- **教训**：**加阻尼之前必须先确认误差信号是干净的。**

### 3. 弯口的「假偏差」把车拽出去

- **现象**：一出弯车就被拽一下，看着像画龙。
- **原因**：只剩一条线时，中心是拿「车道半宽」倒推的（中心列 = 那条线的位置 ± 半宽）。直道上倒推是对的，**弯里车道是拐的，同一条线倒推出来的中心能偏 ±30 刻度**（刻度 = 画面上的像素列，和「格」是同一把尺子）。
- **解决**：**只有「两条线都在」的行，才准往偏差里投票**。单线行仍然参与判弯、判速度档。
- **教训**：推算值不能和实测值同权。

### 4. 九行的认线成功率差得很远（权重要按实测定，不能凭「越近越可信」）

- **现象**：九行的认线成功率差得很远 —— **最近那行（27.5 厘米）反而是近四行里最差的**。实测定量（最近 5 趟、1533 个采样块；采样块 = 一帧里九行的一次完整扫描结果）：行 118（车前 27.5 厘米）**54.0%**、行 103（34.6 厘米）**71.6%**、行 88（44.7 厘米）**67.8%**、行 71（63.3 厘米）50.6%、行 64 64.1%、行 59 62.1%、行 56 45.6%、行 53 44.0%、行 51 47.0%。最靠谱的是 34.6 和 44.7 两行。
- **原因**：最近那行经常看到一大块黑（车自己的影子 / 车头），宽块作废 26 次；而「越近越可信」只是几何直觉，实测根本不成立。
- **解决**：`NEAR_WEIGHT`（九行的权重表，原来给最近四行配的数是 (3,3,2,2)）从 (3,3,2,2) 一路试到 **(0,4,2,0)**（完全不用最近那行）。
- **教训**：**权重应该按实测成功率定，不是按几何远近想当然。**

### 5. 「只剩外侧」很多，「只剩内侧」一次都没有

- **现象**：统计里 `只剩外侧`（只找到左边那条线）出现得很频繁，`只剩内侧` 是 0。
- **原因**：**原因未证实**。能确定的是**内侧（右边）那条线经常丢**；右转的弯里，内侧线丢了会直接把偏差带偏。下次可以查：是不是右侧光照 / 阴影、或者扫描窗口把右侧切掉了。
- **解决**：**未解决**，先把上面两条查法记下来，下次开测先查这两条。
- **教训**：**统计里出现次数为 0 的那一项，往往比出现很多次的项更值得查** —— 它不像正常现象，更像有东西把它挡住了。

### 6. 视觉零点不是 0（偏差在「车摆正」时读 −6 或 +2.5）

- **现象**：车摆在赛道正中，偏差却稳定读 −6（后又变成 +2.5），怎么调补偿都不彻底。
- **原因**：视觉零点（两条线中心的中点 vs 画面正中那一列）本身有偏移；相机装得略偏就会这样。
- **解决**：先量零点，再补 —— **车不动，把车依次摆最左 → 正中 → 最右，取左右两点的中点当零点**（左右两边各自的位置偏差方向相反，一平均就抵消）。**不要用「正中」那一点**：人眼判断 40 厘米宽车道的中心，偏 5~7 厘米很正常。实测：最左 +25、正中 +15、最右 −20 → 零点 = (+25−20)/2 = **+2.5 格（≈1.2 厘米）**。然后设 `LINE_ERR_OFFSET`（零点补偿，喂给方向环之前先减掉它）= **−2.5**（只负责把零点对齐到 0）。
- **教训**：**换个视觉权重、动过相机角度，零点必须重新量，不能沿用。**

### 7. K210 跑两秒突然停（UnboundLocalError）

- **现象**：车跑两秒突然停，日志里偏差冻结、目标速度（想让它跑多快，单位 counts/5ms）归 0。
- **原因**：给「看不全就沿用上次偏差」加计数器时，函数里写了 `hold_frame_count += 1` 却没加 `global hold_frame_count` → 局部变量未赋值就自增 → 抛异常（UnboundLocalError）→ 脚本崩。
- **解决**：函数开头补上 `global` 声明。
- **教训**：MicroPython 里在函数内给模块级变量赋值，**必须写 global**。

### 8. 起点没摆正，被误判成「视觉坏了」

- **现象**：日志里九行全是 `没线 宽块1`（一条 92 像素宽的黑块），看着像摄像头坏了。
- **原因**：**车根本没在纸上**，在赛道外面起步。
- **解决**：每次跑前把车摆到起点线正中。
- **教训**：看到「九行全灭」，先确认车在不在赛道上，再怀疑硬件。

### 9. 配对取「最左 + 最右」，右边的线被杂物挤掉

- **现象**：两条线配对经常配错，偏差跟着错。
- **原因**：原来的配对规则是取「最左 + 最右」两段。**画面里任何杂物都会把右线挤掉**（右边那一大片墙根最容易被当成「最右」）。
- **解决**：改成挑「**间距最接近 2×半宽**」的一对（半宽 = 车道一半的宽度，九行每行各自查表）。
- **教训**：**配对的判据要用几何关系（间距），不能用「谁在最边上」。**

### 10. 配对失败还硬推中心，推出 39 / 144 / 245

- **现象**：某一行两条线根本配不上，程序还是硬算出一个中心，值荒唐：39、144、245（39 / 144 / 245 = 画面列号，内部按 320 尺度算，即画面宽 320 列）。
- **原因**：配对失败时没有「作废」这条路，仍然拿一条线的位置 ± 半宽倒推中心。
- **解决**：**配不上直接判这一行作废**，不给它投票。
- **教训**：**没有可信数据时要输出「没有」，不要硬算一个数。**

### 11. 帧率报出来只有 19.2，其实是单缓冲 + IDE 数据传输吃掉的

- **现象**：测出来的帧率只有 19.2 帧/秒，以为相机到极限了。
- **原因**：两个叠加 —— ① **单缓冲**（采集和计算共用一块图，必须等上一帧算完才能采下一帧）→ 帧率砍半；② **MaixPy IDE 的「数据传输」开着**，要吃掉 5 毫秒。
- **解决**：`dual_buff=True`（双缓冲：一块在算，另一块同时在采）；另外 IDE 的「数据传输」要关掉 —— 它开着时是 28 ms / 20 帧，关掉后是 23 ms / 38 帧。
- **教训**：**报出来的帧率是「空转帧率」，带负载的才作数。** 19.2 不是相机的极限，是这两项代价。

### 12. 车道半宽是假的（27.5 厘米）→ 实测 20 厘米

- **现象**：按车道半宽 27.5 厘米算出来的阈值、容差全不对，近处远处的线都认不好。
- **原因**：27.5 厘米不是量出来的，是「假」的（照抄 / 估的）。
- **解决**：改成实测 **20 厘米**（半宽 = 车道一半的宽度，九行每一行都有自己的半宽）。
- **教训**：**所有几何量都要实测，别拿估的数往上套。**

### 13. 单线死区按画面中心算，把好行整行废掉

- **现象**：行 59 那条左线明明在列 137（离画面中心 23 像素），却被判进死区 → 整行作废。
- **原因**：只剩一条线时，死区是按**画面中心**算的（离中心 24 像素以内分不清），不是按这一行的车道中心算。
- **解决**：**未修**（当时记在待办里）。
- **教训**：**死区要绑在「这一行的车道中心」上，不能绑在画面中心上。**

### 14. 判弯只看单行 / 最近两行 → 看不到远处的弯

- **现象**：车开到弯前才认出来，来不及打方向；单看一行时，光照一变就以为有弯。
- **原因**：判据只看最近的 1~2 行。**单行判断不了对错**：一条线被反光切成两段，和真的弯，单帧看起来一模一样。
- **解决**：改成「九行连起来 + 时间」一起看：数「好行」（两条线都认出来的行）的个数，按帧串成序列，判弯用序列而不用某一行的偏差。
- **教训**：**单行判断不了对错，序列才能** —— 九行 + 时间，才能回答「是不是弯、多近、真的假的」。

### 15. 「没看见」和「看见它没了」混在一起 → 光照冒充弯道

- **现象**：光照一变（比如车顶阴影扫过），程序报「有弯」，车在直道上就打死方向。
- **原因**：两种完全不同的情况用了同一个表示：`x` 是「没看见」（这一行什么都没扫到），`L` 是「看见它没了」（左边有线、右边没有）。混在一起，**光照就会冒充弯道**。
- **解决**：两种状态分开表示，判弯时分别处理。
- **教训**：**误判和漏判不是一样糟**：误判（把光照当弯）= 直道上打死方向 = 必死；漏判（把弯当没事）= 还能靠偏差硬拐 = 还有机会。**设计要偏向漏判。**

### 16. 绝对像素阈值出不了近处

- **现象**：靠近车的几行总是认不出线，越近越差。
- **原因**：线宽、容差、段长全部用**绝对的像素数**当阈值。可线在画面里近处粗、远处细，一个固定像素数不可能两头都对。
- **解决**：**全部改成按「距离 / 比例」算**（每一行用自己的理论线宽乘系数）。
- **教训**：**像素阈值必须跟着距离走，不能一刀切。**

### 17. 场地光不够：对比度只剩 76，阈值是 70

- **现象**：画面里黑线和地面的对比度只剩 76，而判黑白的阈值是 70，只差 6，线时有时无。
- **原因**：场地光照不够（2026-11-18 那次的光照条件）。
- **解决**：当时记为「未修」；后来 2026-11-19 夜间重标参数后，现场实测对比度都在 70~110，够用，这条只剩历史记录。
- **教训**：**阈值和实际对比度只差个位数时，等于没有余量** —— 先解决光照，别在阈值上抠。

### 18. 起跑线开头和出弯后两段还在画龙（11-20 夜间现场观察）

- **现象**：用户口述（按赛道上行驶顺序整理）：① 起跑线那一段**开头时有微弱画龙，此后不再画龙**；② 从钝角弯处往锐角弯开的时候，**画龙严重**。
- **原因**：**原因未证实**。当时的初步线索：① 指向**启动瞬间** —— 速度环从 0 起步的过渡，或第一帧视觉的基线没对齐；② 如果那段是**刚出弯的恢复段**，说明交回视觉后 PD 在振荡；如果是**长直道**，说明 Kp / Kd 本身不行。
- **解决**：当时没有解决，只留了「下次验证」的办法：看日志开头 1~2 秒的偏差序列；看那一段的偏差摆动周期和幅度。
- **教训**：**「只在起步 / 出弯时出现」和「整段都画龙」是两种病**，不要用同一个参数去治。

## 二、控制（STM32）

### 19. 转弯被编码器兜底掐断，只转了 43°

- **现象**：车先左摆头（转弯已开始），然后只摆了一半就直着冲墙。
- **原因**：`TURN_COUNT_BACKSTOP`（编码器兜底：转弯中编码器数够多少计数就强行结束转弯）按理论计数设（1487 × 1.05 ≈ 1561；1487 = 一次 90° 转弯的理论编码器计数，1.05 = 留 5% 余量），但**原地打转时轮胎打滑，编码器数出的角约是真值的 2 倍** → 兜底抢在陀螺仪前面把转弯掐断。实测过一次：编码器认为转了 82°，陀螺仪只认 43°。**影响**：所有按编码器计数设的转弯判据都会**提前**。
- **解决**：兜底比例 1.05 → **3.0**（只防「陀螺仪冻住」这一种情况），超时 800 → 600 毫秒。
- **教训**：**打滑时编码器不可信，角度必须听陀螺仪的** —— 轮子转 ≠ 车身转。

### 20. 转弯有时候 90°、有时候 180°（真 bug，已修）

- **现象**：同一个弯，有时候正常 90°，有时候转 180°（车头对着墙）。180 正好等于超时（超时 = 600 毫秒的兜底时间，陀螺仪不报「到了」就一直转到它）。
- **原因**：`Gyro_Update()` 里 **`Gyro_LastUpdateMs = current_ms;` 写在「读数据之前」** —— 读失败的那一拍，时间戳已经被更新，那一拍的转动**永久丢失**。陀螺仪积分是「转速 × 时间」，时间被吃掉角度就少算 → 程序以为没转够 → 拖到 600 毫秒超时 → 180°。而转弯时电机振动和大电流干扰最重，I2C 读失败的次数每次都不一样 → **忽好忽坏**。
- **解决**：时间戳挪到「读成功之后」才更新，丢的那段下一次成功时一次性补回来（单次最多补 50 毫秒）。
- **教训**：**积分器的 dt 必须只在「样本有效」时才推进。** 这类错误不会一次就露出来，只在 I/O 抖动时才发作。

### 21. 陀螺仪偶发 −999（软件 I2C 太快）

- **现象**：整趟没有陀螺仪，遥测 I3 一直发 −999（I3 = VOFA+ 的第 3 个通道，那里画的是陀螺仪积分角度；−999 是约定好的「没数据」）。
- **原因**：软件 I2C 位延时（每个电平保持多久，用 CPU 空转次数算）只有 25 次空转 ≈ 500 kHz，而总线是开漏、靠模块自带的上拉 → 太快，读不稳。
- **解决**：位延时 25 → **100 次空转（约 125 kHz）**；开机重试 5 → **20 次**；停车时每秒再试一次救回（`Gyro_TryRecover`）。根治（未做）：加 4.7 kΩ 上拉电阻、I2C 线远离电机线、电机端子加 0.1 µF 电容。
- **教训**：**软件模拟出来的时序也要按电气条件留余量**，「能读通一次」不算验证。

### 22. 转弯多转的那部分全是惯性，而且忽多忽少

- **现象**：同一个弯，落地角度每次差 ±8 度。
- **原因**：陀螺仪到了目标角只是撤掉**命令**，车身还在以约 200 度/秒转，靠地面摩擦慢慢停，这一段程序完全不管。滑多少取决于电池电压、地面摩擦、打滑程度。角度表里那个 ×0.87 是**按平均值**补的固定数（命令只给真实角度的 87%，剩下 13% 靠惯性滑到位），补不了波动。
- **解决**：试过两条路，都失败 ——
  - **降差速**（差速 = 左右轮目标速度差，11.55，单位是编码器计数/5 毫秒）→ 9.0：右轮目标只剩 6 个计数，克服不了静摩擦被拖停，车身变成绕右轮硬拧，转速不可控 → 实测稳定转 **180°**。**此路不通。**
  - **按转速预测提前停**（`|角度| + |转速| × 0.1 ≥ 目标` 就停）：实测「大概率转 180°」，原因未确证（怀疑转速估计头几拍不准，提前量乱跳）。**已整体撤回。**
  - **当前值**：角度表 `{78, 20.5, 90, 28.5, 78}`（五个弯的指令角度，手调实测）、差速 11.55、超时 600 毫秒。
- **教训**：这套数是**用眼睛一趟一趟标出来的**，任何「理论上更优雅」的改法都会把这套标定推翻，代价是重新标五个弯。**不要轻易改。**

### 23. 惯性的代价上限（保险）

- **现象**：陀螺仪一旦在转弯中途「冻住」（读数不动），程序以为还没转够，会一直转到 180° 撞墙。
- **原因**：主判据就是陀螺仪角度，它坏了没有第二个人拦。
- **解决**：加「陀螺仪冻住检测」—— 转弯中若「编码器已数了 1400 计数（车确实在转）」且「陀螺仪角度还 < 10 度」，判定哑火，立刻结束转弯。效果：陀螺仪哑火时停在约 80~90°（可救），而不是 180°（灾难）。
- **教训**：**给最坏情况留一道独立的刹车**，别指望主判据自己会停。

### 24. 死区太大，直道上慢慢往内线靠

- **现象**：直道上车一直往内线贴，怎么调零点补偿都不彻底。
- **原因**：死区 ±3 格 = 1.44 厘米。但偏差是在车前 **40 厘米**处量的，换算成车头角度：**车头歪 2 度 → 40 厘米外偏 1.4 厘米 ≈ 3 格 → 被死区吃掉**。也就是「车头歪 2 度以内，方向环这辈子都不纠」。车按 56 厘米/秒 斜着爬，95 厘米能爬 20 厘米。
- **解决**：死区 3 → **1 格**（0.48 厘米 ≈ 车头 0.7 度）。
- **教训**：**死区要用「角度」去换算，不能只看像素数。**

### 25. 「看不全就沿用上次偏差」在弯口反而害人（出弯左摆头 94°）

- **现象**：直道好了，但弯口出错 —— 车被一个旧的大偏差一直拽着；更狠的一次是出弯后视觉冻在 −20 长达 **1.2 秒**（12 帧一模一样），车头往左一甩。陀螺仪证据：这 1.2 秒里从 −97.6° 退回 −3.6°，**车真的往左转了 94°**。
- **原因**：弯口九行大面积掉，上一次有效的偏差很可能正是弯道的假偏差；无条件沿用 = 一直按它打方向。−20 是偏差读数（1 格 ≈ 0.48 厘米），等于照着「车偏左约 9.6 厘米」一直往左打死。
- **解决**：加三个条件 —— ① 上次偏差本身很小（|偏差| ≤ 6 格，说明在直道）② 最多连续沿用 3 帧 ③ 一出现有票的帧就清零（有票 = 这一帧至少有一条「两条线都在」的行给它投票）。任何一条不满足就置 0。
- **教训**：**「沿用旧值」这种保护，必须限定在「旧值可信」的条件下**；方向环也不能相信「冻住的」偏差。

### 26. 钝角弯的阈值改来改去「完全没反应」（三条猜测全被否掉）

- **现象**：第 2 个弯（钝角弯，真实角度 38.5°）有三个症状：① **转晚了**，车已经过了弯才开始转；② **转动角度 75~90°**，而指令角只有 33.5°（表里 `Turn_AngleDeg[1]`）；③ 1 号弯（90°）**正常**，10 次里 9 次笔直。调参时更怪：阈值试了 110 / 95 / 88，车的开转位置**一动不动**。
- **原因**：**原因未证实**。三条猜测全被否掉 —— ① 阈值不对（图纸值 110 太大）：110 → 95 → 88，**车一动不动**；② 是「视觉报弯 + 16 厘米」那条路在控制：把 `TURN_ARM_CM`（视觉报弯之后还要再走多少厘米才开转）16 → 999 彻底关掉，**还是没反应**；③ 陀螺仪角度没到 33.5、靠超时兜底：超时按角度缩放，33.5° 只给 223 毫秒，角度没变。三条都否掉说明：那个弯既不是「阈值 − 10.7」转的，也不是「报弯 + 16」转的。**最可能的根因（假设，尚未证实）**：查表下标 `Corner_Index` 没指向第 2 个弯 —— 若它停在 0，钝角弯实际用的是第 1 个弯的参数：阈值 189 → 开转点 189 − 10.7 = **178.3 厘米**（第 1 个弯到第 2 个弯只有约 110 厘米），车会冲到钝角弯后面 68 厘米才转；角度 78° 加惯性约 90°，正好落在「75~90°」。一个假设同时解释全部四个现象。
- **解决**：当时只做到「把 `TURN_ARM_CM` 改成 999，彻底关掉那条路，开转点只由阈值决定，一个弯只剩一个旋钮，而且它是线性的（阈值减 5 = 提前 5 厘米）」；真正的修法留到下一步：先确认 `Corner_Index` 在转弯结束那一刻有没有加 1。
- **教训**：**改一个参数没反应，先确认它是不是被另一条路接管了**；再不行就往上追一层 —— 参数再怎么调，下标指错了全是白调。

### 27. 里程强转被视觉状态挡住（`Corner_Done` 锁存）

- **现象**：钝角弯既不按里程转，也改不动。
- **原因**：「这一弯转过没有」原来用 `Corner_Done` 表示，而它的生死由**视觉**决定（要视觉说「这里不是弯了」才清）。它一旦卡在 1，里程强转整条路就被挡在门外。
- **解决**：改成 `Corner_TurnedForIndex`，**只跟弯序号走**：开转置 1、弯序号前进清 0，跟视觉无关。
- **教训**：**里程类的判据不要依赖视觉状态。**

### 28. 到终点不停车，还反复右拐 90°

- **现象**：转完最后一个直角弯后直走一段没停，反而又右拐 90° 继续开。
- **原因**：结构性死循环 —— `FINISH_STOP_CM`（数到多少厘米就停车）= 99，但最后一个弯的阈值是 75，强转点 = 75 − 10.7 = **64.3 厘米**。64.3 < 99，于是**还没数到 99 就先转了一次**，转弯一结束段内里程又清零 → 永远到不了 99 厘米 → 每 64 厘米右拐一次，永不停车。
- **解决**：给里程强转和视觉报弯都加 `Finish_Armed == 0` 的条件 —— **转完最后一个弯就不许再转**。
- **教训**：**「停车里程」必须大于「最后一个弯的开转里程」**，否则逻辑上就死循环。

### 29. 编码器坏了，里程全错 → 转弯永远「晚」

- **现象**：转弯位置忽然全都不对，以为要重新标定阈值。
- **原因**：左编码器没信号（见第 41 条）。里程是拿两个编码器算的，坏一个里程就偏小 → 车永远「没走到」。
- **解决**：修好左编码器接线（见第 41 条），里程恢复正常。
- **教训**：**遇到「转弯位置突然不对」，先看 I1 / I3 两个轮子的实际速度，别先怀疑控制参数。**

### 30. 陀螺仪静止重估零偏没有开关 → 转弯只转了 135°

- **现象**：车贴内侧线进弯、原地打转被卡住、根本转不动，最后实测只转了 135°（指令是 78°）。
- **原因**：加了「静止重估零偏」：每 0.5 秒看一次窗口（100 个样本）里读数的极差，小于 40 计数（≈0.6 度/秒）就判「车没动」→ 把这 0.5 秒的平均值当新零偏，并把累计角度清零。第一版**没有开关** —— 车原地打转被卡住时，陀螺仪读数就是「几乎不动」→ 被判成静止 → 累计角度被清零 → **永远到不了 78 度** → 转弯只能等 600 毫秒超时 → 135°。
- **解决**：加总开关 `Gyro_SetStillTrim(1/0)`，由 `AppTask_100ms` 按 `CarRun_State` 调用：`CarRun_State == 0`（停车）才允许，在跑一律禁止。
- **教训**：**任何「自动重估 / 自动校准」的机制，都必须有一个「现在允许吗」的开关**，而且这个开关要由控制层按运行状态给，不能靠「看起来静止」去猜。

### 31. 用两点插值猜阈值：算出 197，实测还是「晚了」

- **现象**：1 号弯的阈值想省一趟车，按「180 时早 20 厘米、200 时晚 3 厘米」两点插值，算出 197。
- **原因**：插值假设「阈值和早晚是线性的」，实际不是（还受地面、起始位置影响）。
- **解决**：实测用户回「还是晚了」，最后是用户直接说「再 −8」才到 189；这个数后来继续调到 188（见第八节）。
- **教训**：**这类只有实车能测的数，直接听用户说加减多少，不要自己插值。**

### 32. `error < 8` 没取绝对值 → 方向反了

- **现象**：偏差是 −11（车偏左）时也触发了「弯道顶方向」，发出 **+40** 的补偿，方向反了。
- **原因**：判断条件写的是 `error < 8`，没取绝对值 —— 负数永远小于 8，于是「所有负偏差」都被当成满足条件。
- **解决**：**当时未修**（记在问题清单里）。
- **教训**：**比大小之前先取绝对值**，否则负数会把判断整段带反。

### 33. 方向环 Kp = 0，车根本不会拐

- **现象**：车能直走，一遇弯就冲出去，方向完全不动。
- **原因**：方向环的 `Kp` 写的是 0 —— 比例系数为 0，偏差再大也乘不出一个差速。
- **解决**：后来按实测一路调到 0.5（画龙）、0.1（太钝）、0.231 → 0.18 → **0.15**（现在的值，见第八节）。
- **教训**：**先确认「这条环有没有在出力」**，再看它出力的多少。

### 34. `SM_BIAS_PX = 30` 在实车上等于「一有偏差就打死方向」

- **现象**：真车一跑就**直道画龙、提前掉头、原地转圈**；手推时一点看不出来。
- **原因**：方案 A 的写法是「只要偏差是正的、比 30 小，一律顶到 30」（30 = 像素列，1 格 ≈ 0.48 厘米，30 格 ≈ 14.4 厘米）。手推时车不动，偏差一直是同一个值，看不出这个「顶」；真车一动就变成每帧都往满舵打。
- **解决**：改成 **0**，关掉强制顶方向。
- **教训**：**「手推测试通过」不等于「实车能跑」** —— 手推时没有速度，很多跟时间有关的错都露不出来。

### 35. 直角弯「提前转 → 压线 → 过度掉头」

- **现象**：用户实车口述：直角弯似乎**提前转弯**，然后**压线**，之后**过度掉头**了，掉头回来继续跑；弯道前也出现「提前转弯」。
- **原因**：**原因未证实**。当时列了三条候选：(a) `TURN_ARM_CM` 偏小（该晚点转）；(b) `TURN_DIFF_TARGET` 偏大（转多了）；(c) 转完没有视觉收尾（那时 `LIMIT_LINE_ERR_MAX` 还是 20）。
- **解决**：当时的验证办法：先量**实际转角**，再量**开始转的位置**，两个分开调；优先级排第二（转多了一定会出赛道，比转少更严重）。
- **教训**：**「转早了」和「转多了」是两个独立的错**，必须分开量、分开调，不能一起改。

### 36. 锐角弯踩线过弯，出弯后自己纠正回来（好消息）

- **现象**：压线过的锐角弯：踩在线上过弯，过完之后**纠正了回来**。
- **原因**：「编码器粗转 → 视觉收尾」这条链在工作 —— 先按编码器粗粗转到位，再交给视觉把偏差拉回 0。
- **解决**：**不用解决，保留，不要动。**
- **教训**：**看到一条链路真的在工作，就别顺手「优化」它** —— 这是整趟里少见的好消息。

### 37. 没能过钝角弯：钝角弯按设计根本不转向

- **现象**：整趟**没能过钝角弯**。
- **原因**：**设计层面的新发现**：钝角弯按设计**不触发转向**（只降速，靠 PD 硬拐）。如果它过不去，说明钝角弯**需要真实转向**。
- **解决**：当时的动作：单独测钝角弯，在日志里看它到底有没有报状态 2（状态 2 = 弯道状态机判出的「这是弯」）。
- **教训**：**「按设计不该转」和「实际过不去」同时成立时，是设计错了，不是参数错了。**

### 38. 一个变量扛两个职责 → 按键永久失效

- **现象**：按键完全没反应，`Key_Request` 永远是 0，看着像硬件坏了。
- **原因**：原始代码只有一个 `KeyAPastLevel`，它同时当「上一次采样值」和「已确认的稳定电平」。推演：按下后 `current_level` 永远不等于 `KeyAPastLevel` → ① 每拍都执行 → `KeyA_Ticks` 永远被清成当前时刻 → ② 的差值恒为 0，永远 < 20 → ③ 永远不执行 → `KeyAPastLevel` 永远不更新 → 回到 ①，死循环。
- **解决**：拆成两个变量：`KeyStableLevel`（已确认的稳定电平，判「要不要提交」）+ `KeyLastSample`（上次采样值，判「有没有变化」），并在判断变化时**两个动作成对做**（重置计时器 + 更新采样值）。
- **教训**：**写状态机时先列出「需要记住哪些状态」，每个状态一个变量，不要复用** —— 同一个变量不能既当「候选」又当「已确认」。这类 bug 编译不报错、不崩溃，只是功能没反应，最容易怀疑硬件。

### 39. 用裸寄存器改 `AFIO->MAPR` → 随机制造「重新上电就坏」

- **现象**：重映射如果用 `AFIO->MAPR |= ...` 这种写法，会随机制造「重新上电就坏」，时好时坏。
- **原因**：`AFIO->MAPR` 里的 `SWJ_CFG[2:0]` 是**只写位**，读回来是垃圾值。`|=` 会先读、再或、再写 —— 把垃圾值写回去，随机破坏 JTAG 配置。
- **解决**：**必须用库函数**（`GPIO_PinRemapConfig`），禁止裸寄存器读-改-写。
- **教训**：**只写位不能读-改-写**；这类错只在复位 / 上电时发作，最难查。

## 三、机械 / 电气

### 40. TB6612 烧毁

- **现象**：一趟跑下来车一步不动，目标速度一直 20（单位 计数/5 毫秒，是想让它跑多快），两个轮子实际一直是 0。
- **原因**：堵转时 12.6 V 直接加在电机绕组上 → 6~12 A，而 TB6612 绝对最大只有 3.2 A（峰值）/ 1.2 A（连续）。（顺便澄清：**停车「抱死」不是凶手** —— 一次抱死能量只有 0.1 焦耳量级，温升几度。）
- **解决**：加堵转保护 `Task_5ms_StallGuard()`：目标 ≥15、两个速度环正向顶到 999‰（占空比 99.9%）、实际速度 < 1.5 计数、连续 400 毫秒 → 断输出 + 停车。启动后 500 毫秒宽限。
- **教训**：电机堵转的电流是驱动芯片额定值的 5~10 倍，必须有软件保护。

### 41. 左编码器 GND 被接到 5V → 左轮全速疯转，车自己画弧

- **现象**：车自己拐弯 / 画弧，一边轮子明显比另一边快；VOFA 里 I1（左轮实际速度）手转电机一直是 0。
- **原因**：**左编码器的 GND 接到了 5V**（整排插错一位）。编码器等于没有供电 → 不出数 → 速度环以为轮子没转 → 占空比顶到 100% → 左轮全速。
- **解决**：
  - **排查办法（按这个顺序）**：① 交换法：把左右电机的插头整体对调，看现象跟不跟着电机走（跟走 = 电机 / 编码器；不跟 = 主板）② 万用表：编码器 VCC-GND 有没有 3.3 / 5 V；手转轮子时 A 相对 GND 有没有 0↔VCC 跳变 ③ 量主板那一端的引脚 ④ 交换法只对调编码器信号线（不动电机动力线），能分开「编码器坏」和「主板坏」。
  - **烧毁风险**：GND 被抬到 5V 时，编码器只是「没电」，一般不会烧；但如果 VCC 是 3.3 V 而 GND 是 5 V，那就是反接 −1.7 V，有风险。另外它的输出相对板子地会抬高 5 V —— STM32 的 PA15 / PB3 是 5V 容忍脚（FT），5 V 扛得住，超过 5.5 V 才危险。
- **教训**：**插头「整排错一位」是最常见的接错形态**，要逐根核对 VCC / GND / A / B，别只看一根。

### 42. 左编码器 P3 引脚的特殊要求（PB3 必须串 1 kΩ）

- **现象**：插着下载器上电 / 复位时，PB3 这根线上 JTDO 和编码器两个输出对顶（一个想拉高、一个想拉低）。
- **原因**：左编码器用 TIM2 部分重映射：CH1 = **PA15**、CH2 = **PB3**。这两个脚复位后是 JTAG 的 JTDI / JTDO；代码里靠 `GPIO_Remap_SWJ_JTAGDisable` 关掉 JTAG 才能用，但插着 ST-Link 复位时 JTDO 仍会主动驱动这根线。
- **解决**：**硬件上 PB3 必须串 1 kΩ 电阻** —— 即使对顶，电流也只有 3.3V / 1 kΩ = 3.3 mA，不会损坏任何一方。
- **教训**：用 JTAG 复用脚做编码器输入，一定要在原理图上标注这个电阻。

### 43. 陀螺仪模块偶尔整趟不认

- **现象**：开机 WHO_AM_I（读一次芯片 ID，确认模块在不在）一次没读通，整趟没有陀螺仪。
- **原因**：硬件「时好时坏」（接触 / 上拉 / 供电），**原因未彻底证实**。
- **解决**：开机重试 20 次；停车时每秒再试一次 `Gyro_TryRecover()`。状态：仍是「时好时坏」的硬件，根治要动线（同第 21 条）。
- **教训**：软件兜底只能救回一部分，**根治要动线**。

### 44. 按键和左轮 PWM 抢同一根脚（PA8）

- **现象**：按键一按，左轮电机就抖。
- **原因**：按键原来接在 PA8，而 PA8 是 TIM1_CH1（左轮 PWM）。按键把 PWM 拉低 → 占空比被改 → 电机抖。
- **解决**：按键挪到 PA0。
- **教训**：**STM32 的引脚是复用的，加新功能前必须核对「这根脚还有谁在用」。**

### 45. 摄像头细杆抖动：高度抖 1 厘米，所有半宽偏 3~6%

- **现象**：同一套参数，远处那几行（远行）更容易配对失败，时好时坏。
- **原因**：摄像头装在细杆上会抖；车体高度抖 1 厘米 → 所有半宽偏 3~6%。
- **解决**：**未解决**（记在问题清单里，是那批未修问题里优先级最高的一条）。
- **教训**：**几何参数对安装高度极其敏感** —— 机械不牢，参数怎么调都是浮的。

### 46. 布面褶皱会变高度

- **现象**：同一段赛道，参数今天行、明天不行；画面里出现莫名的宽块 / 阴影。
- **原因**：喷绘布有褶皱，褶皱把布面抬高或压低，相当于相机高度变了。
- **解决**：喷绘布要铺平、四角压住。
- **教训**：**赛道本身也是「参数」** —— 布不平，标定就白做。

## 四、通信（蓝牙 / 有线 / 遥测）

> 这一节把蓝牙链路、K210 有线调试、遥测三件事的坑放在一起。后面第五节还会按「现象」再列一遍速查。

### 47. 跑车的时候一根 USB 线都不许插

- **现象**：插着 USB 线跑车，车往前跑 1 米电脑就得跟着挪 1 米。
- **原因**：K210 和 STM32 的 USB 线同时是「供电 + 通信」。插着线跑车，线就把车和电脑拴在一起 —— 赛道上没人给你拽电脑。
- **解决**：正确的数据获取方式 —— K210 那一侧**靠 SD 卡**（脚本里 `RECORD_TO_FILE = True`，每帧写进 `run_log.txt`，跑完拔卡看）；STM32 那一侧**遥测是蓝牙的**（本来就无线）。
- **教训**：任何「看数据」的方案，先问一句：**要不要插着线跑车？** 要插 → 直接否掉。

### 48. COM3 / COM4 / COM5 / COM15 全是蓝牙串口

- **现象**：以为遥测是走 USB 线的，白折腾了很久；反过来接 K210 板子时，又不知道这四个口里哪个是它。
- **原因**：注册表里 `\Device\BthModem0~3` 分别对应 COM15 / COM3 / COM4 / COM5 —— 这四个口都是蓝牙虚拟出来的串口，所以 **STM32 的遥测一直是走蓝牙的，本来就无线**。
- **解决**：遥测不用插线（车上电、手机端 VOFA+ 断开，电脑上就能抓）；要认 K210 的 USB 串口（一般是 CH340，设备管理器里叫「USB-SERIAL CH340」），就**插上板子前后各列一次串口列表对比**。
- **教训**：**先搞清楚「这个口是谁」，再动手抓数据。**

### 49. 同一个串口只能一个人开（抓包前必须先断开）

- **现象**：报「对端口 COMx 的访问被拒绝」，抓不到任何数据。
- **原因**：同一个串口同时只能被一个程序打开 —— VOFA+、MaixPy IDE、串口助手、抓包脚本，谁先开谁占着。
- **解决**：抓之前先让占用它的程序松手：VOFA+ 要断开连接；MaixPy IDE 要**点「断开连接」**（不是最小化）。
- **教训**：**「端口被拒绝」先看谁占着，不要怀疑线。**

### 50. 蓝牙接收队列会溢出，而且没有任何提示

- **现象**：连续发指令时，偶尔丢字节，顺序还会乱。
- **原因**：队列只有 32 字节（环形队列：写指针追上读指针就绕回去），而主循环 100 毫秒才取一次；115200 的波特率下 100 毫秒能来 1152 字节。队列的判空条件只写了 `head == tail`，**分不出「空」和「满」** —— 满了以后 head 绕一圈追上 tail，程序认为「空」，数据静默丢失、顺序全乱。
- **解决**：**未修**（人手调参一帧只有 13 字节、间隔几百毫秒，不会溢出；用脚本批量发就会丢）。修法：ISR 里先算 next，`next != tail` 才写；满了也必须把 DR 读走（否则 RXNE 永远不消失，中断反复触发）。
- **教训**：**队列一定要能区分「空」和「满」**，少一个状态就会静默丢数据。

### 51. 没有处理 ORE 溢出错误

- **现象**：偶发丢字节，没有任何告警。
- **原因**：中断还没读走上一个字节，下一个字节又到了 → ORE（溢出错误）置位 → 两个字节里丢掉一个；现在的代码没检查 ORE。
- **解决**：**未做**。好消息：读 DR 会自动清 ORE，所以不会卡死；坏消息：偶发丢字节，没有任何告警。
- **教训**：**「不会卡死」不等于「没问题」** —— 静默丢数据比报错更难查。

### 52. 文件里挂着一行用不到的 `#include <stdio.h>`

- **现象**：`BlueTooth.c` 顶部有一行 `#include <stdio.h>`，文件里没有任何 stdio 函数。
- **原因**：**原因未证实**（可能是之前想加 `printf` 重定向留下的）。
- **解决**：不影响功能，删掉即可。
- **教训**：**看到 `<stdio.h>` 别以为这里有 `printf` 输出** —— 这行是摆设，本工程没有。

### 53. 蓝牙的 AT 指令必须走「有线」

- **现象**：在 VOFA+ 里通过蓝牙发 `AT+VERSION`，一点反应都没有。
- **原因**：JDY-31 的 AT 指令只能从模块的 RXD 引脚（有线侧）进入，不能从蓝牙空中进入 —— 空中的 AT 会被当成普通业务数据，原样从 TXD 吐给单片机，AT 解析器根本收不到。
- **解决**：用 USB-TTL 接到模块的 RXD / TXD，从电脑的有线串口发；所有指令以 `\r\n` 结尾（串口助手要勾「发送新行」）。
- **教训**：**蓝牙是对外营业窗口（只传话），RXD 引脚是内部电话（才能下指令）。**

### 54. 配 AT 时模块必须「未连接」

- **现象**：发 AT 指令没回应。
- **原因**：模块处于「已连接」状态时不响应 AT 指令（它认为你在传数据）。
- **解决**：先断开连接，看灯判断：**闪** = 未连接、在广播，能配；**常亮** = 已连接，不能配。
- **教训**：**配置前先看灯**，省得怀疑指令打错。

### 55. 蓝牙串口在设置页显示「未连接」是正常的

- **现象**：Windows / 手机设置页显示「未连接」，以为坏了，反复配对。
- **原因**：耳机、鼠标这类设备连上就一直保持；**蓝牙串口（SPP）只有程序打开 COM 口时才连接，程序关掉就断**。
- **解决**：判断标准只有一条：打开 COM 口后有没有数据。
- **教训**：**别拿「设置页显示什么」当故障判据**，要看实际数据。

### 56. 一个模块只能连一台设备

- **现象**：电脑连不上，或连上就断。
- **原因**：JDY-31 同一时刻只能被一台设备连接。手机连过，电脑就连不上。
- **解决**：先断开手机 —— 并且在手机蓝牙设置里「取消配对」，不只是退出 App。
- **教训**：**「连不上」先问「是不是别人还占着」。**

### 57. 官方明确不支持苹果设备

- **现象**：iPhone / iPad 搜到也连不上、用不了。
- **原因**：JDY-31 是**蓝牙 3.0 SPP 经典蓝牙**，iOS 不支持 SPP 协议。
- **解决**：必须用 Android 或 Windows。
- **教训**：**买模块前先看它支不支持你手里的设备**，别等上电才发现。

### 58. Windows 可能存不住配对密钥

- **现象**：有时连得上、有时连不上；事件日志里出现 `[BTHUSB] Windows 无法在本地适配器上存储蓝牙身份验证代码(链接密钥)`。
- **原因**：Windows 的蓝牙密钥存不住（密钥槽满或驱动有问题）。
- **解决**：① 重启电脑（清蓝牙栈）② 删除不用的配对设备（腾出密钥槽）③ 删除 JDY-31 重新配对 ④ 更新蓝牙驱动。
- **教训**：**「时好时坏」先翻系统日志**，日志里往往直接写着原因。

### 59. 电脑端串口的波特率基本无效

- **现象**：在电脑端把波特率从 9600 试到 115200，怎么改都一样 / 都不通。
- **原因**：蓝牙虚拟串口的本地波特率通常被驱动忽略。真正决定成败的是「**单片机 ↔ 模块**」这一对的波特率是否一致。
- **解决**：别在电脑端波特率上白折腾。去查模块的 UART 波特率：JDY-31 出厂默认 9600，代码里写 115200 就必须先用 `AT+BAUD8` 把模块改成 115200（改完要断电重启才生效）。
- **教训**：**先找「真正决定成败的那一段」**，别在不起作用的地方调。

### 60. 改了电脑上的脚本，板子跑的还是老版本

- **现象**：参数改了、重新跑，车的行为一点没变。
- **原因**：改的是**电脑上**那份 `live_scan_test.py`；板子跑的是**卡上的 `main.py`**。而且电脑上那份也要同步改，不然下次「保存到开发板」会把卡上那份覆盖回去。
- **解决**：MaixPy IDE 里「工具 → 保存打开的脚本到开发板」（文件名 `main.py`），然后拔插一次 USB（或按复位），板子才会跑新版本。
- **教训**：**「改的是哪一份文件」必须说清楚** —— 电脑一份、卡上一份，两份不同步就白改。

### 61. 卡上没有 `main.py`，上电就停在 REPL 不跑程序

- **现象**：板子上电没反应，串口里只有一个 REPL 提示符。
- **原因**：卡上没有 `main.py`，MicroPython 上电找不到要跑的程序，就进 REPL 等你敲命令。
- **解决**：把脚本存成卡上的 `main.py`（文件名必须是这个）。
- **教训**：**「上电不跑」先看卡上有没有 `main.py`**，别先怀疑板子坏。

### 62. 用串口 REPL 远程改卡上的文件，失败会把板子卡在 REPL

- **现象**：想让电脑直接改卡上那两行，结果板子停在 REPL 不动，程序也不跑。
- **原因**：REPL 那条路是「中断当前程序 → 重写文件 → 软重启」，中间任何一步失败，板子就停在 REPL。
- **解决**：失败了只能拔卡用读卡器改，或重新烧录恢复。所以要先「用抓串口的方式跑通一轮」，确认串口能通，再决定要不要直接改。
- **教训**：**能省事的自动化，要先证明它失败时退得回来。**

### 63. 有线抓不到 K210 的日志

- **现象**：脚本抓串口，抓不到任何输出。
- **原因**：四种常见 —— ① MaixPy IDE 还占着串口 ② 端口号选错 ③ 卡上没有 `main.py`（程序根本没跑）④ 板子没在跑那份脚本。
- **解决**：按顺序查：① 确认 IDE 已「断开连接」（不是最小化）② 拔插一次对比串口列表，确认端口号 ③ 确认卡上有 `main.py`（有的话一上电就打印）④ 都不行就退回老办法：拔卡读 `run_log.txt`。
- **教训**：**抓不到数据时，先分「没在跑」和「在跑但没抓到」** —— 这两类的查法完全不同。

## 五、模块故障速查（按键 / 编码器 / 电机 / 蓝牙）

> 用法：先在这里按**现象**找到条目，照着「解决」里的顺序一项项查；条目指到哪个编号，就去那个编号看完整故事。这里的「原因」是「这个现象可能由哪几件事引起」，不是已确认的定论。

### 64. 按键：按下去没反应

- **现象**：按按键，车不启动也不停。
- **原因**：五种可能 —— ① PA0 电平根本没变 ② 按键一端没接 GND ③ `Key_CheckRequest` 没被调用 ④ `Key_GetRequest` 没被调用 ⑤ 消抖逻辑错（第 38 条那个 bug）。
- **解决**：按顺序查：① 万用表量 PA0，松开应为 3.3 V、按下应为 0 V ② 量按键一端是否通 GND ③ Watch 看 `KeyA_Ticks` 是否在变（不变 = 没被调用）④ 断点或加灯看 `Key_GetRequest` ⑤ 对照第 38 条。
- **教训**：**先量电平，再怀疑代码。**

### 65. 按键：按一次触发好几次

- **现象**：按一下，车启动又停止、反反复复。
- **原因**：三种 —— ① 消抖阈值太小（现在 20 毫秒，只相当于「连续 2 次采样一致」）② `Key_Request` 读后没清零 ③ 按键质量差，抖动特别长。
- **解决**：① 阈值 20 → 30 或 50（人按一下会保持 100 毫秒以上，不会有延迟感）② 检查 `Key_GetRequest` 有没有清零 ③ 加硬件 RC 滤波（100 nF 电容对地）。
- **教训**：**「触发多次」先查消抖和清零**，这两处占九成。

### 66. 按键：按住不放一直触发

- **现象**：手指一直按着，事件一直重复。
- **原因**：`KeyStableLevel`（已确认的稳定电平）没有更新，于是每一拍都判成「电平变了」。
- **解决**：检查提交那一段 —— `KeyStableLevel = current_level;` 必须在提交时更新；正确写法下按住只会触发一次。
- **教训**：**状态机要分清「候选」和「已确认」**，两者混用就会每拍都触发。

### 67. 按键：一上电就触发一次

- **现象**：刚上电，车自己启动（或自己停）。
- **原因**：上电瞬间引脚电平会抖一下，被当成一次按键。
- **解决**：初始化时多读几次，或上电后延时 100 毫秒再开始扫描。
- **教训**：**上电的头 100 毫秒不可信**，所有输入都要躲过这一段。

### 68. 编码器：完全读不到数（一直 0）

- **现象**：手转轮子，`Encoder_GetRaw()` 不动，一直是 0。
- **原因**：五种 —— ① 编码器 VCC / GND 没接（很多人只接 A / B 两根）② JTAG 没关（PA15 / PB3 被调试口占着）③ A / B 接到了 TB6612 而不是 STM32 ④ 信号根本没进来（电机转时计数器不变）⑤ PB3 的 1 kΩ 电阻没装。
- **解决**：按顺序：① 量编码器 VCC-GND 有没有 3.3 / 5 V ② 确认 `Encoder_Init()` 里先关了 JTAG ③ 核对 A / B 是不是接到 PA15 / PB3（左）和 PB6 / PB7（右）④ 转电机看 `Encoder_GetRaw()` 变不变 ⑤ 查 PB3 那颗 1 kΩ（见第 42 条）。记法：**粗线（电机电源）走 TB6612，细线（编码器四根）走 STM32。**
- **教训**：**「读不到」先查供电和接线，最后才怀疑定时器配置。**

### 69. 编码器：数值乱跳

- **现象**：速度曲线一直在抖；或每转一圈突然跳一下；或偶尔出现极大值。
- **原因**：三种 —— ① 每转一圈突变一次 = 16 位回绕处理写错了（少 `(uint16_t)` 转换）② 一直抖 = 输入滤波值太小，或引脚接触不良 ③ 偶尔极大值 = 编码器电源不稳，或地线没共好。
- **解决**：① 写成 `(int16_t)((uint16_t)Curr − (uint16_t)Last)`，不能直接相减 ② 滤波用 `0xF`（最大档，连续 8 次一致才认），检查杜邦线 ③ 共地、加去耦。
- **教训**：**「每转一圈跳一次」就是回绕的签名**，看到这个形状直接去看那行减法。

### 70. 编码器：方向反了

- **现象**：车往前走，速度环读出来是负数，越调越飞。
- **原因**：A / B 相位接反，或编码器和电机的「正转」定义不一致。
- **解决**：三种改法，只挑一种 —— ① 软件最简单：在 `Service.c` 里把 `actual` 取负 ② 改极性：把一个 `TIM_ICPolarity_Rising` 改成 `Falling` ③ 改接线：把 A / B 两根线对调。
- **教训**：**方向反了先改一个地方**，三处一起改会互相抵消。

### 71. 编码器：左右轮速度不一样

- **现象**：同样目标，两个轮子实际速度差一截，车跑偏。
- **原因**：两个电机本身有差异（正常）；也可能是编码器线数不同、减速比不同、轮子直径不同。
- **解决**：电机差异正常，用 PID 各自闭环；线数 / 减速比 / 轮径不同就换同型号、量直径。
- **教训**：**先排除「硬件不一样」，再怪 PID。**

### 72. 电机：完全不转

- **现象**：给了目标速度，两个轮子一点不动。
- **原因**：六种 —— ① STBY 没拉高（PB5 拉低则全部关闭）② VM 没有 12.6 V ③ VCC 不是 3.3 V（接 5 V 会导致高电平门限不匹配）④ 没调 `TIM_CtrlPWMOutputs`（高级定时器必需）⑤ PWM 引脚不是 `AF_PP` 模式 ⑥ AIN1 / AIN2 都为 0（真值表里是停止）。
- **解决**：按顺序量：STBY 电平 → VM 12.6 V → VCC 3.3 V → 有没有调 `TIM_CtrlPWMOutputs` → 引脚模式 → 真值表。都正常还不动，再看第 40 条（TB6612 可能已经烧了）。
- **教训**：**「全都不转」先查电源和使能** —— 这两样一错，代码再对也不动。

### 73. 电机：只能单向转

- **现象**：前进正常，倒车不动（或反过来）。
- **原因**：某根方向线接错 / 虚焊，或电机红黑线接反。
- **解决**：对照真值表查方向线；万用表量通断；红黑线对调。
- **教训**：**单向故障一定是「一根线」的问题**，不要改代码。

### 74. 电机：有啸叫

- **现象**：电机发出刺耳声音。
- **原因**：PWM 频率落在可听范围（现在设计成 20 kHz，超出人耳）；或电机机械共振；或电源纹波大。
- **解决**：先确认 `MOTOR_PWM_PSC` / `MOTOR_PWM_ARR` 算出来确实是 20 kHz；再换固定方式、加减震；加大电容。
- **教训**：**先算频率，再拆机械。**

### 75. 电机：低速不转，一给就猛冲（PWM 只有 100 级）

- **现象**：小占空比不动，稍微一加就冲出去；PID 细调半天没反应。
- **原因**：两件事叠在一起 —— ① 电机静摩擦需要约 15~20% 占空比才能启动（这里的「死区」是电机的静摩擦，不是第 24 条那个视觉死区）；② 原来 PWM 只有 100 级（`ARR = 99`，分辨率 1/100 = 1%），而 PID 输出是 0~1000（1000 级），映射到 CCR 只有 0~99 —— **10 个连续的 PID 输出值，映射到同一个 CCR**。
- **解决**：① 靠积分慢慢爬（PID 的 I 项会逐渐积累，最终突破死区，本车现状）；② 或者把分辨率提上去：`PSC = 0, ARR = 3599` → 仍是 20 kHz（72,000,000 / 1 / 3600 = 20,000 Hz），分辨率 1/3600 = 0.028%，提高 36 倍。改完编译通过（0 错误 0 警告），**但未上车实测**。
- **教训**：**「PID 调不动」有时不是算法问题，是输出被量化吃掉了。**

### 76. 电机：一转，单片机就复位

- **现象**：电机一启动，板子重启（或程序跑飞）。
- **原因**：电源跌落 —— 电机启动瞬间拉低电池电压，MCU 掉电复位。
- **解决**：加大电容（1000 µF 以上）、电机电源和 MCU 电源分开走线、加软启动。
- **教训**：**大电流的东西一动作，先看电源掉没掉。**

### 77. 蓝牙：完全收不到字节

- **现象**：手机 / 电脑发数据，`bt_rx_head`（队列的写指针）不涨。
- **原因**：六种 —— ① 模块和单片机波特率不一致（模块出厂 9600，代码写的是多少）② PA2 / PA3 接线错 ③ 没共地 ④ 模块被别的设备占着 ⑤ 没开 RXNE 中断 ⑥ NVIC 没配。
- **解决**：按顺序查：波特率 → 接线（PA2 → 模块 RXD，PA3 ← 模块 TXD，交叉）→ 共地 → 断开别的设备 → `USART_ITConfig(USART2, USART_IT_RXNE, ENABLE)` → `USART2_IRQn` 使能。也可以做回环测试：一根杜邦线短接 PA2-PA3（模块先拔掉），发什么收什么，能把单片机从嫌疑里排除。
- **教训**：**一次只让一个环节成为变量**，别同时改波特率和接线。

### 78. 蓝牙：收到乱码

- **现象**：能收到数据，但全是乱码。
- **原因**：波特率不匹配（最常见）；数据位 / 停止位不一致；干扰。
- **解决**：两档波特率各试一次；确认都是 8N1；缩短接线、加共地。
- **教训**：**乱码 = 时序对不上**，不是数据内容错。

### 79. 蓝牙：偶尔丢字节

- **现象**：大部分数据对，偶尔少一两个字节。
- **原因**：三种 —— ① 队列溢出（32 字节太小，见第 50 条）② ORE 溢出错误没处理（见第 51 条）③ 中断优先级太低被长时间阻塞。
- **解决**：加满判断或加大队列；加 ORE 检测；检查其他中断的耗时（蓝牙是优先级 3，最低）。
- **教训**：**偶发丢包先看「谁占着 CPU 太久」。**

### 80. 蓝牙：VOFA+ 能收但不显示波形

- **现象**：串口助手能看到字节，VOFA+ 里波形框是空的。
- **原因**：四种 —— ① 波特率错 ② 协议选错（要选 **JustFloat**）③ Y 轴量程不对 ④ 帧尾不对。
- **解决**：改对波特率；协议选 JustFloat；点 `Auto` 自动缩放；检查帧尾是不是 `00 00 80 7F`。
- **教训**：**「有字节没波形」是协议层的事**，跟数据本身无关。

### 81. 蓝牙：一个字节都发不出去（初始化顺序反了）

- **现象**：接收正常、也能改参数，但 VOFA+ 一个波形都没有。
- **原因**：初始化顺序反了 —— 先 `Debug_Init()`（配 DMA）后 `BlueTooth_Init()`（开 USART2 时钟）。`USART_DMACmd()` 写的是 USART2 的 `CR3` 寄存器，**外设时钟还没开，这次写是无效的**（写进一个未使能外设的寄存器会被忽略）→ DMA 请求永远不触发。
- **解决**：顺序必须是 `BlueTooth_Init()` → `Debug_Init()`（`Service.c:50-51`）。
- **教训**：**这种错读回寄存器也看不出来**（写过但没生效），只能靠顺序对。

## 六、流程 / 工具

### 82. `mid_delay.c` 被别的 AI 删掉，编译报找不到文件

- **现象**：编译报 `cannot open source input file "MID\Src\mid_delay.c"`。
- **原因**：`bsp_gyro.c` 还在调 `Delay_ms()`（陀螺仪上电等待 / 重试 / 启动等待），工程里也还登记着它 —— 文件被删了，用它的代码还在。
- **解决**：按 git 里的原样恢复，内容一字未改。
- **教训**：**删文件之前先搜谁在用它。**

### 83. `run_log.txt` 取不出来

- **现象**：K210 插上电脑后，SD 卡**不挂成盘符**；发 Ctrl+C 也停不了脚本（主循环被 try 包住 / REPL 不收输入）。
- **原因**：**原因未证实** —— 能看到的只是「USB 不挂成盘符、REPL 也不收输入」这两个现象。
- **解决**：只能把 TF 卡拔出来插读卡器。
- **教训**：**改视觉脚本必须依赖读卡器**，跑车现场要带。

### 84. 只换 `main.c`，不换别的 → 死机

- **现象**：灯一直闪、按键和蓝牙都启动不了。
- **原因**：把 `main.c` 换回正式版（308 字节），但 `Service.c` 还是台架派生出来的。台架 `main()` 是**独立完整**的一套（自己初始化、自己调度、不调 `Voice_Init` / `k210rcv_Init`），正式 `Service_Init()` 则会把蓝牙（USART2）、语音、K210 串口（USART1）**同时**初始化。两套硬拼 → 串口 / 引脚互相干扰。
- **解决**：入口和初始化必须来自同一个版本，不要混着拼。
- **教训**：**不要跨版本拼文件。同一套程序的入口和初始化必须来自同一个状态。**

### 85. 整个 `Control/` 退回旧提交，把两个符号修正也退掉了 → 电机全反

- **现象**：两个轮子转向都反、左轮编码器正转出负数、速度环正反馈（转一会就停）。
- **原因**：台架那次提交里其实**修正了两个符号** —— `Motor.c`：`AIN1/AIN2`、`BIN1/BIN2` 高低电平整个对调（默认正转）；`Encoder.c`：左轮编码器 `TIM_ICPolarity_Rising` → `Falling`。回退时一退到底，把它们一起退掉了。
- **解决**：只把这两个文件从 `a021332` 取回来，其余保持正式版。
- **教训**：**回退前先看清「这次提交里除了你以为的那件事，还改了什么」。**

### 86. 以为方向环是 PI、加 D 要改代码 —— 查了才发现本来就是 PD

- **现象**：想加阻尼，准备改代码给方向环加 D 项。
- **原因**：凭印象记错了环的结构。
- **解决**：先读代码：方向环本来就是 PD，`Kd` 还有现成的蓝牙指令可以改，根本不用编译。
- **教训**：**先查代码再下结论**，别凭印象安排工作量。

### 87. 寄存器读不出来，还拿它当证据 → 浪费一天

- **现象**：为了算帧率 / 曝光，去读摄像头 sensor 的寄存器，`sensor.__read_reg` 全返回 0。
- **原因**：这个 sensor 的读寄存器接口拿不到真值（全 0），而那套 HTS×VTS 理论全靠它。
- **解决**：**读不出来就别拿它当证据** —— 那套理论从头到尾没有证据，白花了一天。
- **教训**：**证据拿不到时，先换一条证据链**，别在一条读不出来的路上耗一天。

### 88. 数据要按「哪一个量在变」来选，不按直觉

- **现象**：想用「数丢的行」当判弯指标，看着直观，实际不单调，判不出来。
- **原因**：丢的行只会在弯里变得更差，**只增不减**，不会自己恢复；**数好的行才是单调的**（进弯变少、出弯变多）。
- **解决**：改用「好行个数」（两条线都认出来的行，一共几条）。
- **教训**：**选指标看它随状态怎么变，不看它看起来像不像。**

## 七、通用教训（压成十句话）

- **先确认「我拧的是不是那个旋钮」** —— 改参数没反应，多半是被另一条路接管了；换文件、回退版本也一样，先看清自己到底改了什么。
- **先治噪声，再谈加阻尼** —— 顺序反了会越调越糟。
- **积分器的 dt 只在样本有效时才推进**；任何「自动重估 / 自动校准」都必须有一个「现在允许吗」的开关，由运行状态来给。
- **死区要用角度换算**，不能只看像素数。
- **轮子转 ≠ 车身转** —— 打滑时编码器不可信。
- **里程判据不要依赖视觉状态。**
- **「沿用旧值」必须限定在「旧值可信」的条件下**；误判比漏判更糟，设计要偏向漏判。
- **看到「九行全灭」先确认车在不在赛道上**，再怀疑硬件；读不出来的寄存器不要当证据。
- **任何「看数据」的方案，先问要不要插线跑车。**
- **只有实车能测的数，直接听实测加减，别自己插值 / 推算。**

### 8.1 五个弯的阈值（`Turn_ThresholdCm`，厘米）
