# 硬件模块详解（按键 / 编码器 / 电机 / 蓝牙）

本文把四份「驱动代码详解」合成一册，一块硬件一章。四份原文的内容都保留，只按「硬件与引脚 → 核心结构 → 函数逐个讲 → 踩过的坑 → 故障速查」重新排了一遍，方便现场翻。

四个模块各管什么，一句话一个：

- **电机驱动（`Motor.c`）**：把上层算好的「千分之几的占空比」变成「方向电平 + PWM 波形」，让 TB6612FNG 按命令驱动两个轮子。
- **编码器（`Encoder.c`）**：让定时器**硬件**去数轮子转过的脉冲，算出「这 5 ms 转了多少 counts」，是速度闭环的眼睛。
- **按键（`Key.c`）**：把手指的一次按下（带 5~20 ms 抖动）消抖成**一个事件标志**，交给状态机去启停。
- **蓝牙（`BlueTooth.c`）**：把 JDY-31 从 USART2 送来的字节塞进环形队列，等主循环慢慢取出来解析，是调参的入口。

四者的关系：**蓝牙**收指令改 PID → PID 算出占空比交给**电机** → **编码器**量出实际转速喂回 PID → **按键**负责启停。互相之间只通过变量和函数调用打交道，不直接碰对方的寄存器。

> **行号说明（重要）**：四份原文都按旧版源文件标行号——`Motor.c` 191 行、`Encoder.c` 165 行、`Key.c` 57 行、`BlueTooth.c` 64 行。现在工程里这几个文件已改名为 `bsp_motor.c`（193 行）、`bsp_encoder.c`（165 行）、`bsp_key.c`（66 行）、`bsp_bluetooth.c`（64 行），行号不完全对得上（按键那份差得最多）。**所以下文所有行号一律是旧版行号（行号为旧版）**，读代码时以语句本身为准，不要拿行号去数。

## 第一部分 电机驱动 Motor.c

### 一句话职责

**把 `-1000`~`+1000` 的占空比指令，翻译成「AIN1/AIN2 的高低电平 + TIM1 的 CCR 值」两组信号，送给 TB6612FNG。** 它不判断车跑得快不快（那是 PID 的事），只保证电机听得懂、不乱动。

### 1.1 硬件与引脚

#### 1.1.1 TB6612FNG 是什么

**一颗双通道 H 桥电机驱动芯片**，负责把 MCU 的弱信号（3.3 V、几 mA）变成能驱动电机的强信号（12.6 V、1 A 级别）。

为什么非要它，而不是 STM32 直接接电机：

| 问题 | 说明 |
|---|---|
| **电压不够** | STM32 输出 3.3 V，电机要 12 V |
| **电流不够** | STM32 一个引脚最多 20 mA，电机堵转要 1 A+ |
| **不能换向** | GPIO 只能输出高低，不能反转极性 |
| **不能调速** | 需要 PWM 调制 |

#### 1.1.2 引脚功能

| 引脚 | 功能 |
|---|---|
| VM | 电机电源（本项目 12.6 V，3S 锂电直通） |
| VCC | 逻辑电源（**必须 3.3 V**） |
| GND | 地 |
| AO1 / AO2 | 左电机输出（接电机红/黑粗线） |
| BO1 / BO2 | 右电机输出（接电机红/黑粗线） |
| PWMA | 左电机调速（PWM 输入） |
| AIN1 / AIN2 | 左电机方向 |
| PWMB | 右电机调速 |
| BIN1 / BIN2 | 右电机方向 |
| STBY | 待机（低 = 全部关闭） |

#### 1.1.3 真值表（单通道）

这张表是全部方向控制的根据，接线查错就靠它：

| AIN1 | AIN2 | PWM | 电机状态 |
|---|---|---|---|
| 0 | 0 | 任意 | **停止（滑行，自由转动）** |
| 0 | 1 | PWM | **正转**，速度 ∝ PWM |
| 1 | 0 | PWM | **反转**，速度 ∝ PWM |
| 1 | 1 | 任意 | **制动（刹车，电机绕组短路）** |

本车只用了「正转」和「反转」，没有用「制动」——因为停车使用 `Motor_SetDuty(0,0)`，走的是 `AIN1=AIN2=0` 的**滑行停车**，不是急刹。

#### 1.1.4 本车引脚分配

| 功能 | 引脚 | 定时器通道 / GPIO |
|---|---|---|
| 左轮 PWM | **PA8** | TIM1_CH1 |
| 右轮 PWM | **PA11** | TIM1_CH4 |
| 左轮方向 AIN1 | **PB12** | GPIO |
| 左轮方向 AIN2 | **PB13** | GPIO |
| 右轮方向 BIN1 | **PB14** | GPIO |
| 右轮方向 BIN2 | **PB15** | GPIO |
| STBY | **PB5** | GPIO |

**为什么左轮用 CH1、右轮用 CH4，中间空两格：**

| 通道 | 引脚 | 能不能用 |
|---|---|---|
| CH1 | **PA8** | ✅ 用 |
| CH2 | PA9 | ❌ 被 USART1_TX 占了 |
| CH3 | PA10 | ❌ 被 USART1_RX 占了（接 K210） |
| CH4 | **PA11** | ✅ 用 |

CH2/CH3 撞了 K210 的串口，所以只能跳着用 CH1 和 CH4。**这也是「先查引脚表再用」的最好例子**——见附录 A。

#### 1.1.5 为什么 PWM 选 20 kHz

| 频率 | 现象 |
|---|---|
| < 1 kHz | 电机发出「嗡嗡」的低频抖动，PID 会被干扰 |
| 1~8 kHz | **人耳最敏感区间，刺耳啸叫** |
| 8~16 kHz | 仍有高频噪音 |
| **20 kHz** | **刚好超过人耳上限**，完全听不到 ✅ |
| > 25 kHz | 开关损耗增加，TB6612 发热 |

**20 kHz 是「听不到」和「开关损耗可接受」的平衡点。** TB6612FNG 数据手册标称开关频率可达 100 kHz，20 kHz 完全在范围内。

### 1.2 核心结构

#### 1.2.1 时钟宏（第 5~7 行，行号为旧版）

```c
#define MOTOR_GPIO_CLK          (RCC_APB2Periph_GPIOA|RCC_APB2Periph_GPIOB)
#define MOTOR_TIM_CLK           RCC_APB2Periph_TIM1
#define MOTOR_TIM               TIM1
```

TIM1 是**高级定时器**（挂在 APB2 上，时钟 72 MHz）。「高级」两个字很关键，后面两个坑（互补输出、MOE）都来自这个身份。

#### 1.2.2 PWM 参数宏（第 9~13 行，行号为旧版）

```c
// PWM参数：72MHz / (PSC+1) / (ARR+1) = 72M/1/3600 = 20kHz
// 分辨率 = 1/3600 ≈ 0.028%，比原来的 1/100 精细 36 倍
// 这样 MOTOR_DUTY_FULLSCALE=1000 的 ‰ 级指令才真正有意义
#define MOTOR_PWM_PSC           0
#define MOTOR_PWM_ARR           3599
```

把数字代进去：

| 项 | 值 | 怎么来的 |
|---|---|---|
| 定时器时钟 | 72 MHz | TIM1 挂 APB2，72 MHz |
| 预分频 | PSC = 0 → 分频 1 | `(PSC+1) = 1` |
| 一个周期计数 | ARR = 3599 → 3600 个计数 | `(ARR+1) = 3600` |
| PWM 频率 | **20 kHz** | 72 000 000 ÷ 1 ÷ 3600 = 20 000 Hz |
| 占空比分辨率 | **1/3600 ≈ 0.028 %** | 一个 CCR 步进就是 1/3600 |

> **历史**：最初是 `PSC=35, ARR=99`（也是 20 kHz），但那时占空比只有 **100 级**分辨率。现已改为 `PSC=0, ARR=3599`，**频率不变、分辨率提高 36 倍**。为什么必须改，见 1.4.6。

#### 1.2.3 占空比满量程（第 14 行，行号为旧版）

```c
#define MOTOR_DUTY_FULLSCALE    1000
```

**语义：占空比指令单位是「‰」（千分之一）。**

- `1000` = 100 % 占空比
- `500` = 50 %
- `0` = 停

**为什么用 ‰ 而不是 %：**

PID 速度环输出是 `float`，直接输出 ‰ 有小数量级的分辨能力（虽然 `Motor_SetDuty` 接收 `int16_t`）。

更重要的是：**和 PID 的输出量纲完全一致**，中间零换算。这是好设计——量纲一致，就不会出现「PI 输出 0~1，电机要 0~1000，中间忘了乘 1000」这种低级错。

#### 1.2.4 五个函数和它们的调用关系

| 函数 | 谁调它 | 它干什么 | 返回 |
|---|---|---|---|
| `Motor_Init()` | 上电初始化时调一次 | 配时钟、引脚、TIM1，最后开 STBY | `void` |
| `MotorLeft_SetDirection(uint8_t isForward)` | `Motor_SetDuty` | 按方向写 AIN1/AIN2 | `void` |
| `MotorRight_SetDirection(uint8_t isForward)` | `Motor_SetDuty` | 同上，写 BIN1/BIN2 | `void` |
| `Motor_DutyToCCR(int16_t duty)` | `Motor_SetDuty` | ‰ → CCR（0~3599） | `uint16_t` |
| `Motor_SetDuty(int16_t left, int16_t right)` | 4 个地方（见 1.2.6） | 对外唯一接口：方向 + 速度 | `void` |

调用链很短：**`Motor_SetDuty` → 方向函数 + `Motor_DutyToCCR` → `TIM_SetCompare1/4`**。写电机的动作全部收在这一个函数里（虽然它被 4 个地方调，见坑 7）。

#### 1.2.5 初始化顺序（九步，顺序本身就是设计）

1. GPIO 时钟
2. PWM 引脚配 `AF_PP`（复用推挽）
3. 方向引脚**先写 ODR、再切输出**
4. STBY **先拉低**（驱动器关闭）
5. 定时器时基（PSC/ARR）
6. **显式关闭互补输出**
7. 启动计数器（`TIM_Cmd`）
8. 置 MOE（`TIM_CtrlPWMOutputs`）
9. **最后拉高 STBY** ← 此时电机才真正启用

这个顺序不是随便排的：**第 4 步到第 9 步之间，驱动器是关的**，中间无论引脚怎么乱跳，电机都不会动。学这一章，最该带走的就是这个顺序。

#### 1.2.6 谁在写电机（4 个调用点）

`Motor_SetDuty` 在整个工程里有 **4 个调用点**：

| 位置 | 用途 |
|---|---|
| `ServiceTask_5ms` | 正常控制输出 |
| `Task_CarStop` | 停车清零 |
| `Task_FetchVisionData` | 丢线急停 |
| `Task_CalculateTargetSpeed` | 终点停车 |

**4 个地方都能直接控制电机，一旦有 bug 很难排查。** 这是架构上的一个弱点：应该收敛成「只有一处能写电机」，其他地方只改状态变量。但比赛前不建议重构（见坑 7）。

### 1.3 函数逐个讲

#### 1.3.1 `Motor_Init()`

**① GPIO 时钟（第 48 行，行号为旧版）**

```c
RCC_APB2PeriphClockCmd(MOTOR_GPIO_CLK, ENABLE);   // GPIOA | GPIOB
```

**② PWM 引脚配成复用推挽（第 50~53 行，行号为旧版）**

```c
GPIO_InitStruct.GPIO_Mode  = GPIO_Mode_AF_PP;     // 复用推挽
GPIO_InitStruct.GPIO_Pin   = MOTOR_LEFT_PWM_PIN | MOTOR_RIGHT_PWM_PIN;
GPIO_InitStruct.GPIO_Speed = GPIO_Speed_50MHz;
GPIO_Init(MOTOR_LEFT_PWM_PORT, &GPIO_InitStruct);
```

**`AF_PP`（复用推挽）** 是 PWM 输出的正确模式——引脚交给定时器外设控制，不由 GPIO 寄存器控制。配成普通 `Out_PP` 的话，定时器再努力也没用，引脚电平只跟 ODR 走。

**③ 方向引脚：先写电平，再切模式（第 56~62 行，行号为旧版）★**

```c
/* 先在ODR写死电平再配成输出，避免切换瞬间出毛刺 */
GPIO_InitStruct.GPIO_Mode = GPIO_Mode_Out_PP;
GPIO_InitStruct.GPIO_Pin  = AIN1 | AIN2 | BIN1 | BIN2;

GPIO_SetBits(MOTOR_LEFT_DIR_PORT, AIN2 | BIN2);     // AIN2=1, BIN2=1
GPIO_ResetBits(MOTOR_LEFT_DIR_PORT, AIN1 | BIN1);   // AIN1=0, BIN1=0

GPIO_Init(MOTOR_LEFT_DIR_PORT, &GPIO_InitStruct);   // 最后才切成输出
```

**这是一个非常正确的顺序，很多人会写反。** 为什么，见坑 2。

**④ STBY 先拉低（第 65~70 行，行号为旧版）★**

```c
/* STBY先拉低，待机，防止初始化期间电机抽动 */
GPIO_ResetBits(MOTOR_STBY_PORT, MOTOR_STBY_PIN);
GPIO_Init(MOTOR_STBY_PORT, &GPIO_InitStruct);
```

**目的**：初始化过程中所有引脚可能乱跳，先把驱动器关掉（STBY 低 = 输出高阻），**电机绝对不动**。最后在所有配置完成后才拉高（第 105 行，行号为旧版）。见坑 3。

**⑤ 定时器时基（第 73~80 行，行号为旧版）**

```c
TIM_TimeBaseInitStruct.TIM_Period    = MOTOR_PWM_ARR;   // ARR = 3599
TIM_TimeBaseInitStruct.TIM_Prescaler = MOTOR_PWM_PSC;   // PSC = 0
TIM_TimeBaseInitStruct.TIM_CounterMode = TIM_CounterMode_Up;
```

源码注释里写了 `//FIX 3：用宏，避免和换算常数脱节`——之前可能是直接写 `99`，改参数时容易和别处不一致。现在时基和 `Motor_DutyToCCR` 用的是同一个 `MOTOR_PWM_ARR` 宏，改一处全对。

**⑥ TIM1 互补输出必须显式关闭（第 83~97 行，行号为旧版）★★ 最重要的坑**

```c
/* TIM1是高级定时器，N通道默认映射在PB13~PB15，必须显式清零
   防止互补输出抢走方向引脚 */
TIM_OCInitStruct.TIM_OutputNState = TIM_OutputNState_Disable;   // ★ 关键
```

这一句只有一行，但它是整个电机模块最容易出人命的地方，完整原理见坑 1。

**⑦ 启动（第 100~101 行，行号为旧版）**

```c
TIM_Cmd(MOTOR_TIM, ENABLE);
TIM_CtrlPWMOutputs(MOTOR_TIM, ENABLE);      // ★ 高级定时器必须
```

`TIM_Cmd` 只启动计数器，**不会让输出真正到达引脚**。必须再调 `TIM_CtrlPWMOutputs` 置 MOE。见坑 4。

**⑧ 最后使能 STBY（第 105 行，行号为旧版）**

```c
/* 所有寄存器配置完毕，最后使能TB6612 */
GPIO_SetBits(MOTOR_STBY_PORT, MOTOR_STBY_PIN);
```

#### 1.3.2 `MotorLeft_SetDirection()` / `MotorRight_SetDirection()`

```c
static void MotorLeft_SetDirection(uint8_t isForward)
{
    if(isForward == 1)
    {
        GPIO_ResetBits(AIN1);   // AIN1 = 0
        GPIO_SetBits(AIN2);     // AIN2 = 1
    }
    else
    {
        GPIO_SetBits(AIN1);     // AIN1 = 1
        GPIO_ResetBits(AIN2);   // AIN2 = 0
    }
}
```

`isForward` 是形参：`1` = 正转，`0` = 反转。没有返回值。

对照真值表：

| `isForward` | AIN1 | AIN2 | 结果 |
|---|---|---|---|
| 1 | 0 | 1 | 正转 |
| 0 | 1 | 0 | 反转 |

右轮的 `MotorRight_SetDirection` 一模一样，只是把 AIN1/AIN2 换成 BIN1/BIN2。

**「正转」的定义取决于电机接线**：如果接线时红黑线接反了，这里的「正转」实际是反转。可以在软件里把 `actual` 取负，或直接对调电机两根线。

#### 1.3.3 `Motor_DutyToCCR()`

```c
static uint16_t Motor_DutyToCCR(int16_t duty)
{
    if(duty > MOTOR_DUTY_FULLSCALE)
    {
        duty = MOTOR_DUTY_FULLSCALE;      // 上限保护
    }
    return (uint16_t)((int32_t)duty * MOTOR_PWM_ARR / MOTOR_DUTY_FULLSCALE);
}
```

形参 `duty` 是 ‰（0~1000，调用方保证非负），返回值是 CCR（0~3599）。

**现在的换算公式（ARR=3599）：**

| duty（‰） | 计算 | CCR | 实际占空比 |
|---|---|---|---|
| 0 | 0 × 3599 ÷ 1000 | 0 | 0 % |
| 100 | 100 × 3599 ÷ 1000 | 359 | 10 % |
| 500 | 500 × 3599 ÷ 1000 | 1799 | 50 % |
| 1000 | 1000 × 3599 ÷ 1000 | 3599 | 100 % |

> **注意**：有的旧笔记里写着 `CCR = duty × 99 / 1000`（`duty=100` → CCR=9）。那是 **ARR=99 时代**的数值，原文第 5 章那张表也是旧数据，这里按现在的 3599 重新算过，别拿旧数去套。

**为什么要乘 `int32_t`**：`duty` 最大 1000，乘 3599 = 3 599 000，早就超过 `int16_t` 的 32767（旧版乘 99 也有 99000，同样超）。不先转 `int32_t` 会溢出，结果完全错误。这类「中间结果溢出」是嵌入式最常见的隐蔽 bug 之一，见坑 5。

**为什么只保护了上限**：函数只在 `duty > 1000` 时夹住，没有处理负数——因为调用方 `Motor_SetDuty` 已经对负数取了绝对值。这是一个「约定式」的隐式契约，必须靠调用方遵守。

#### 1.3.4 `Motor_SetDuty()`

```c
void Motor_SetDuty(int16_t left_duty, int16_t right_duty)
{
    // 左轮
    if(left_duty >= 0)
    {
        MotorLeft_SetDirection(1);                       // 正转
        TIM_SetCompare1(MOTOR_TIM, Motor_DutyToCCR(left_duty));
    }
    else
    {
        MotorLeft_SetDirection(0);                       // 反转
        TIM_SetCompare1(MOTOR_TIM, Motor_DutyToCCR(-left_duty));   // 取绝对值
    }
    // 右轮同理，用 TIM_SetCompare4
}
```

两个形参都是 `int16_t`，单位 ‰，**带符号**：正 = 正转，负 = 反转，0 = 停。

| 设计要点 | 说明 |
|---|---|
| **有符号入参** | 正 = 正转，负 = 反转，0 = 停 |
| **一个函数管两件事** | 方向 + 速度 |
| **取绝对值再换算** | `DutyToCCR` 只接收非负数 |
| **`duty == 0` 走正转分支** | 方向 = 正转，CCR = 0 → 实际停止（滑行） |

右轮就是把 `left_duty` 换成 `right_duty`、`MotorLeft_SetDirection` 换成 `MotorRight_SetDirection`、`TIM_SetCompare1` 换成 `TIM_SetCompare4`。

### 1.4 踩过的坑

#### 1.4.1 坑 1（★★ 最重要）：TIM1 的互补输出会抢走方向引脚

**TIM1 是高级定时器，每个通道有两路输出：**

| 通道 | 正常输出 | **互补输出（N）** |
|---|---|---|
| CH1 | PA8 | **PB13** |
| CH2 | PA9 | **PB14** |
| CH3 | PA10 | **PB15** |
| CH4 | PA11 | （CH4 无互补） |

**而本车的方向引脚正好是 PB12 / PB13 / PB14 / PB15！**

**PB13 / PB14 / PB15 同时是「方向引脚」和「TIM1 互补输出」。**

如果互补输出被使能，定时器会**主动驱动**这三根线 → **方向控制完全失效，电机行为完全不可预测**。

**怎么避免：**

```c
TIM_OCInitStruct.TIM_OutputNState = TIM_OutputNState_Disable;
```

`TIM_OC1Init` 内部会设置 `CCER` 的 `CC1NE` 位。设为 Disable → `CC1NE = 0` → 互补输出关闭 → PB13 保持 GPIO 功能。

**补充：复位后本来就是 0。**

`CCER` 复位值 = 0，所以严格说即使不显式设也应该是关的。但：

- 代码显式设置 → **意图清晰，防止以后有人改错**
- 某些库版本或中断里可能动过 CCER

**这是防御性编程，好习惯。**

#### 1.4.2 坑 2：方向引脚先切模式、后写电平

写反的版本长这样：

```c
// ❌ 错误顺序
GPIO_Init(...);              // 先切输出，此时 ODR 是复位值 0
GPIO_SetBits(...AIN2...);    // 再写电平
```

**中间有一个极短的窗口，AIN1 = AIN2 = 0** → 真值表里这是「停止」，理论上没事。

但如果 ODR 恰好是 `AIN1=1, AIN2=1`（制动），而 PWM 已经在输出 → **瞬间制动一下，电机会「咯噔」抖一下**。

**先写 ODR 再切模式，保证切换瞬间电平就是想要的。** 这就是 1.3.1 ③ 那段代码的顺序理由。

#### 1.4.3 坑 3：STBY 没有先拉低

如果先配完引脚、开了定时器，最后才想起来配 STBY，中间那段时间驱动器是**使能**的，而方向引脚和 PWM 都还没定下来——电机可能抽一下、甚至猛转一下。

**正确做法**：STBY 拉低放在最前面（第 65~70 行，行号为旧版），拉高放在最后一步（第 105 行，行号为旧版）。**初始化期间驱动器全程是关的，电机绝对不动。** 这是一个「安全初始化」的经典套路，值得学。

#### 1.4.4 坑 4：只调 `TIM_Cmd`，忘了 `TIM_CtrlPWMOutputs`

**高级定时器（TIM1/TIM8）多一个 MOE（Main Output Enable）位。**

`TIM_Cmd` 只启动计数器，**不会让输出真正到达引脚**。必须再调 `TIM_CtrlPWMOutputs` 置 MOE。

**这是新手最常踩的坑之一**：CCR 设了、计数器转了，但引脚上什么都没有，示波器一片静。查半天以为是引脚配置错，其实是 MOE 没开。

#### 1.4.5 坑 5：`duty × ARR` 中间结果溢出 `int16_t`

```c
(int32_t)duty * MOTOR_PWM_ARR
```

`duty` 最大 1000，乘 3599 = 3 599 000，**远远超过 `int16_t` 的 32767**。旧版乘 99 也有 99000，同样超。

如果不先转 `int32_t`，编译器会按 16 位算，高位被截掉，结果完全错误——而且**只在占空比大的时候错**，小占空比测不出来，最坑。

#### 1.4.6 坑 6：PWM 曾经只有 100 级分辨率（已修）

**问题**：`ARR = 99` → PWM 分辨率 = 1/100 = 1 %。

而 PID 输出是 **0~1000（1000 级）**，映射到 CCR 只有 **0~99（100 级）**。

**结果是：10 个连续的 PID 输出值，映射到同一个 CCR。**

| duty（‰） | CCR（ARR=99） |
|---|---|
| 500 | 49 |
| 501 | 49 |
| 502 | 49 |
| … | 49 |
| 509 | 50 |

**后果：**

| 场景 | 影响 |
|---|---|
| **中高占空比** | 影响小（1 % 相对误差） |
| **低占空比**（如 30 ‰ → CCR = 2） | **影响极大**，2 % 的分辨率意味着几乎无法微调 |
| **PID 细调** | 积分器辛苦积累半天，输出没有变化 → 表现为「响应迟钝」 |

举例：duty 从 20 涨到 29，CCR 一直是 1（`20 × 99 / 1000 = 1`），只有 29 才跳到 2。**低速时 PID 的精细调节被「量化」吃掉了。**

**已应用的改进**：保持 20 kHz 不变，提高计数分辨率。

| 项 | 改前 | 改后 |
|---|---|---|
| `MOTOR_PWM_PSC` | 35 | **0** |
| `MOTOR_PWM_ARR` | 99 | **3599** |
| 频率 | 20 kHz | 20 kHz（72M ÷ 1 ÷ 3600） |
| 分辨率 | 1/100 | **1/3600 ≈ 0.028 %**，精细 36 倍 |
| 低速例子 | 30 ‰ → CCR = 2 | 30 ‰ → CCR = 107 |

改动位置是 `Motor.c` 第 9~13 行。`Motor_DutyToCCR` 用的是 `MOTOR_PWM_ARR` 宏，**自动适配，不用改**（`duty=1000 → CCR=3599`）。

**安全性**：频率没变，只是每个周期内的计数更细，对驱动器和电机没有任何额外压力。

**验证状态**：编译通过（0 错误 0 警告），**但未上车实测**。第一次上车时留意电机是否有异常噪音或抖动。

#### 1.4.7 坑 7：4 个地方都能直接写电机

`Task_CarStop`、`Task_FetchVisionData`、`Task_CalculateTargetSpeed`、`ServiceTask_5ms` 都会调 `Motor_SetDuty`。出事时你看到的现象是「车突然停了一下」，但要在这 4 个地方里找是谁写的，**只能一个个加打印**。

**治本办法**：只留一处真正写 CCR，其他地方只改「期望速度」或「运行状态」变量。**但赛前不建议重构**——动架构的风险比这个坑本身大。

#### 1.4.8 还没做的事（知道，但没加）

| 缺失 | 影响 | 为什么没加 |
|---|---|---|
| **死区补偿** | 低占空比时电机不转（静摩擦），PID 积分要慢慢爬上来 | 积分会自己处理，可不做 |
| **软启动（斜坡）** | duty 突变 → 电流冲击 → 电池电压瞬降 → 其他模块复位 | 赛前只做「能编译 + 能上车验证」的改动 |
| **堵转保护** | 电机卡死时电流过大，长期会烧 TB6612 | 同上 |
| **电流限制** | 由 TB6612 自己限流（没有可编程限流） | 硬件限制 |

#### 1.4.9 做得好的地方 / 还能改的

| # | 做法 | 价值 |
|---|---|---|
| 1 | **STBY 先拉低、最后拉高** | 初始化期间电机绝不抽动 |
| 2 | **方向引脚先写 ODR 再切模式** | 消除切换毛刺 |
| 3 | **显式关闭 TIM1 互补输出** | 避免 PB13~15 被抢占 |
| 4 | **`TIM_CtrlPWMOutputs`** | 高级定时器必须，否则无输出 |
| 5 | **输出直接是 ‰，与 PID 量纲一致** | 中间零换算，不易出错 |
| 6 | **`int32_t` 防中间溢出** | 隐蔽 bug 的预防 |
| 7 | **20 kHz 超出人耳** | 无啸叫 |

还能改的（按性价比排）：

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | 无死区补偿 | 低占空比不转 | 积分会自己处理，可不做 |
| 2 | 无软启动 | 电流冲击 | 赛前不做 |
| 3 | 4 个调用点 | 难排查 | 收敛成单点写入 |
| 4 | 无堵转保护 | 长期烧驱动器 | 加电流检测或超时 |
| 5 | `Motor_DutyToCCR` 只保护上限 | 依赖调用方约定 | 加负值保护 |

### 1.5 故障速查

| 现象 | 先去查哪里 |
|---|---|
| 两个轮子都不转 | 先看 STBY（PB5）有没有拉高——低电平=驱动器全关；再量 VM 有没有 12.6 V、VCC 是不是 3.3 V |
| 一个轮子转、一个不转 | 查不转那一路的 PWM 引脚（PA8/PA11）是不是 `AF_PP`、方向线（PB12~15）有没有虚焊 |
| 只能单向转 | 对照真值表查 AIN1/AIN2（左）或 BIN1/BIN2（右），看有没有一根线接错/虚焊 |
| CCR 有值、计数器也在跑，引脚上没波形 | 查 `TIM_CtrlPWMOutputs` 调没调（MOE 没开） |
| 方向控制完全失效、电机乱转 | 查 TIM1 互补输出有没有显式关（`TIM_OutputNState_Disable`），PB13~15 被定时器抢走了 |
| 上电/复位瞬间电机「咯噔」一下 | 查 STBY 是不是先拉低、方向引脚是不是先写 ODR 再切输出 |
| 有刺耳啸叫 | 确认 `MOTOR_PWM_PSC=0`、`MOTOR_PWM_ARR=3599` 算出来是 20 kHz；再看机械共振、电源纹波 |
| 低速给一点不转、给多一点猛冲 | 主要是死区：约 15~20 % 占空比才启动，本车靠 PID 积分慢慢爬；分辨率问题见坑 6（已修） |
| PID 输出变了、电机没反应（迟钝） | 看 CCR 是不是连着好几个 duty 都不变——分辨率被量化吃掉 |
| 电机一转单片机就复位 | 电源跌落：加大电容（1000 µF 以上）、电机电源和 MCU 电源分开走线、加软启动 |

## 第二部分 编码器 Encoder.c

### 一句话职责

**让 TIM2 / TIM4 的硬件计数器去数编码器的 A、B 两相脉冲，每个控制周期算出「左轮、右轮这一周期各转了多少 counts」。** 它不管车往哪走（那是视觉和状态机的事），只管老老实实报「转了多少」。

### 2.1 硬件与引脚

#### 2.1.1 带编码器的电机有六根线，只有两根接 TB6612

带编码器的 TT 电机是 **6 根线**：

| 线 | 长相 | 是什么 | 接到哪 |
|---|---|---|---|
| M+ | 红粗 | 电机电源 + | TB6612 的 AO1 或 BO1 |
| M− | 黑粗 | 电机电源 − | TB6612 的 AO2 或 BO2 |
| A | 细 | 编码器 A 相 | STM32 的定时器引脚 |
| B | 细 | 编码器 B 相 | STM32 的定时器引脚 |
| VCC | 细 | 编码器电源 3.3 V | 3.3 V |
| GND | 细 | 地 | GND |

**只有前两根（粗线）接 TB6612，后四根（细线）全部接 STM32。**

本车的实际接法：

| 从哪来 | 信号 | 接到哪 |
|---|---|---|
| 左电机 M+（红粗） | 电机电源 | **TB6612 AO1** |
| 左电机 M−（黑粗） | 电机电源 | **TB6612 AO2** |
| 左编码器 A | 编码器信号 | **PA15**（TIM2_CH1） |
| 左编码器 B | 编码器信号 | **PB3**（TIM2_CH2） |
| 编码器 VCC | 3.3 V | 3.3 V |
| 编码器 GND | 地 | GND |
| 右电机 M+（红粗） | 电机电源 | **TB6612 BO1** |
| 右电机 M−（黑粗） | 电机电源 | **TB6612 BO2** |
| 右编码器 A | 编码器信号 | **PB6**（TIM4_CH1） |
| 右编码器 B | 编码器信号 | **PB7**（TIM4_CH2） |
| 编码器 VCC | 3.3 V | 3.3 V |
| 编码器 GND | 地 | GND |

**记法：粗线走 TB6612，细线走 STM32。** 接错会怎样，见坑 1。

#### 2.1.2 编码器的物理原理

**结构**：电机轴上装一个多极磁环（跟着轴一起转），旁边两个霍尔元件 A、B，相距 90° 电角度。磁环一转，两个霍尔就轮流输出方波。

**为什么两个霍尔**：只数脉冲只能知道「转了多少」，不知道「往哪转」。比较 A、B 谁先谁后，才知道方向。

| 转向 | 相位关系 |
|---|---|
| **正转** | A 领先 B 90° |
| **反转** | B 领先 A 90° |

**A 和 B 的相位关系决定方向。**

**为什么叫「4 倍频」：**

| 计数方式 | 每周期计数次数 | 倍频 |
|---|---|---|
| 只数 A 上升沿 | 1 | 1 倍 |
| 数 A 上升 + 下降沿 | 2 | 2 倍 |
| **A、B 的所有边沿都数** | **4** | **4 倍** |

本车用的是 `TIM_EncoderMode_TI12` = **4 倍频**。

**硬件自动完成**：`TI12` 模式下定时器**同时监视 A 和 B**，每次任一输入变化：

- 若另一路为高 → **+1**
- 若另一路为低 → **−1**

**这一切是纯硬件行为，CPU 完全不参与。** 这就是引脚表里写「**不占用 CPU**」的原因。

#### 2.1.3 引脚宏定义与引脚选择

```c
/* 左编码器：TIM2 部分重映射1 -> CH1=PA15, CH2=PB3
 *   注意1：PA15/PB3 复位后默认是 JTAG 的 JTDI/JTDO，
 *          必须在 main 里先关 JTAG，再调用 Encoder_Init()
 *   注意2：PB3 硬件上必须串 1kΩ 电阻，否则插着下载器复位时会和 JTDO 对顶
 * 右编码器：TIM4 -> CH1=PB6, CH2=PB7（无重映射）
 */
```

**为什么左轮要用「部分重映射 1」：** STM32F103 的 TIM2 引脚如下。

| 通道 | 默认引脚 | 部分重映射 1 后 | 全重映射后 |
|---|---|---|---|
| CH1 | PA0 | **PA15** | PA15 |
| CH2 | PA1 | **PB3** | PB3 |
| CH3 | PA2 | PA2 | PB10 |
| CH4 | PA3 | PA3 | PB11 |

**PA0 被按键占了**，所以选了部分重映射 1。（按键原来就接在 PA8，也撞了 TIM1_CH1——见第三部分坑 1。）

**为什么选 TIM2 和 TIM4：**

| 定时器 | 用途 |
|---|---|
| TIM1 | 电机 PWM（高级定时器） |
| **TIM2** | **左编码器** |
| TIM3 | 1 ms 系统时基 |
| **TIM4** | **右编码器** |

只有 TIM1~TIM8 中的 TIM2~TIM5 支持「编码器接口模式」，而 TIM3 已被时基占用。

**PB3 为什么必须串 1 kΩ：** PB3 复位后默认是 **JTDO**。插着 ST-Link 上电/复位时，JTDO 会主动驱动这根线；同时编码器也在驱动它 → **两个输出对顶**。

串 1 kΩ 后，即使对顶，电流也只有 `3.3 V / 1 kΩ = 3.3 mA`，不会损坏任何一方。

### 2.2 核心结构

#### 2.2.1 四个 `int16_t` 变量（增量缓存）

```c
static int16_t EncLeft_LastCounter = 0;
static int16_t EncRight_LastCounter = 0;
static int16_t EncLeft_DeltaCounter = 0;
static int16_t EncRight_DeltaCounter = 0;
```

| 变量 | 含义 |
|---|---|
| `EncLeft_LastCounter` | 左轮**上一次**读到的计数值（用来相减） |
| `EncRight_LastCounter` | 右轮同上 |
| `EncLeft_DeltaCounter` | 左轮**这一周期**的增量（PID 要的就是它） |
| `EncRight_DeltaCounter` | 右轮同上 |

**为什么需要**：定时器的计数器是**累计值**，不是**增量**。

| 时刻 | 计数器 | 这 5 ms 转了多少 |
|---|---|---|
| t=0 ms | 1000 | — |
| t=5 ms | 1050 | 50 |
| t=10 ms | 1080 | 30 |

PID 要的是「**这一周期转了多少**」，所以必须记住上次值再相减。

#### 2.2.2 为什么缓存而不是现算

```c
/* 增量缓存：由 Encoder_Update() 刷新，避免上层重复调用把增量清零 */
```

如果每次 `Encoder_GetDelta()` 都现算并清零，**上层调用两次就会丢数据**（第二次得 0）。

现在的设计是「一个周期算一次，之后可以反复读」。服务层可能在多处使用同一周期值（PID、VOFA+ 波形、蓝牙调参），如果读一次就清零，后面全是 0。

#### 2.2.3 算一算：counts 到底代表多快

**本车参数：**

| 参数 | 值 |
|---|---|
| 编码器线数 | 13 PPR（常见值，**请按实物核对**） |
| 倍频 | 4 倍频 |
| **减速比** | **1:28** |

**每转计数：**

| 位置 | 计算 | counts |
|---|---|---|
| 电机轴转一圈 | 13 × 4 | **52** |
| 输出轴转一圈 | 52 × 28 | **1456** |

**换算速度**（目标速度 `Speed_Straight = 40 counts/5 ms`）：

| 步骤 | 计算 | 结果 |
|---|---|---|
| 每秒计数 | 40 × (1000 / 5) | 8000 counts/s |
| 输出轴转速 | 8000 ÷ 1456 | 5.49 转/秒 |
| 换成 RPM | 5.49 × 60 | **329.7 RPM** |

**换算成车速**（假设轮径 **65 mm**，常见 TT 电机轮，请按实物核对）：

| 步骤 | 计算 | 结果 |
|---|---|---|
| 轮周长 | π × 0.065 | 0.2042 m |
| 线速度 | 5.49 × 0.2042 | 1.12 m/s |
| 换成 km/h | 1.12 × 3.6 | **4.04 km/h** |

**三档基速对应：**

| 变量 | counts/5 ms | 输出轴转速 | 线速度 |
|---|---|---|---|
| `Speed_Straight` | 40 | 329.7 RPM | 1.12 m/s |
| `Speed_SmallAngle` | 25 | 206.0 RPM | 0.70 m/s |
| `Speed_LargeAngle` | 15 | 123.6 RPM | 0.42 m/s |

**分辨率（5 ms 一个周期）：**

| 实际速度（counts/5ms） | 5 ms 内 counts | 量化误差 |
|---|---|---|
| 40 | 40 | ±1 count = **±2.5 %** |
| 15 | 15 | ±1 count = **±6.7 %** |

**速度越低，量化噪声占比越大**——这就是速度环不能加 D 项的核心原因。D 项是对误差求差分，噪声会被放大。

### 2.3 函数逐个讲

#### 2.3.1 `Encoder_Init()`

**① 关 JTAG（第 40~41 行，行号为旧版）**

```c
RCC_APB2PeriphClockCmd(RCC_APB2Periph_AFIO, ENABLE);
GPIO_PinRemapConfig(GPIO_Remap_SWJ_JTAGDisable, ENABLE);
```

**为什么必须做**：复位后 PA15/PB3 的默认功能是 JTAG 调试口。

| 引脚 | 默认功能 |
|---|---|
| PA13 | SWDIO |
| PA14 | SWCLK |
| **PA15** | **JTDI** |
| **PB3** | **JTDO** |
| PB4 | NJTRST |

不关 JTAG，这两根线被调试口占着，配成定时器输入也读不到。

`GPIO_Remap_SWJ_JTAGDisable` = **关掉 JTAG，保留 SWD**（仍可下载调试）。

**② TIM2 部分重映射（第 49 行，行号为旧版）**

```c
GPIO_PinRemapConfig(GPIO_PartialRemap1_TIM2, ENABLE);
```

代码注释（踩过坑的记录）：

```c
//  必须用库函数，禁止 AFIO->MAPR |= ... 这种裸寄存器写法：
//  SWJ_CFG 是只写位，读回值未定义，读-改-写会随机制造"重新上电就坏"
```

`AFIO->MAPR` 里的 `SWJ_CFG[2:0]` 是**只写位**，读回来是垃圾值。写 `AFIO->MAPR |= x` 会先读、或、再写——**把垃圾值写回去，随机破坏 JTAG 配置**。

**③ 引脚模式（第 52~64 行，行号为旧版）**

```c
GPIO_InitStruct.GPIO_Mode = GPIO_Mode_IPU;    // 上拉输入
```

**编码器输出有两种类型：**

| 类型 | 输出方式 | 需要上拉吗 |
|---|---|---|
| 开漏输出（很多霍尔编码器） | 只能拉低 | **必须上拉** |
| 推挽输出 | 能拉高能拉低 | 不需要 |

**用上拉输入是两种都兼容的稳妥做法。**

**④ 时基（第 71~78 行，行号为旧版）**

```c
TIM_TimeBaseInitStruct.TIM_Period = 65535;      // ARR = 65535
TIM_TimeBaseInitStruct.TIM_Prescaler = 0;       // 不分频
```

**ARR = 65535**：16 位计数器最大值，每转满一圈才回绕一次。

**不分频**：分频会降低分辨率。5 ms 内可能只有几十个 counts，再分频就测不准。

> **低速时分辨率越高，速度环越稳。**

**⑤ 输入滤波（第 81~83 行，行号为旧版）**

```c
TIM_ICInitStruct.TIM_ICFilter = 0xF;   // 最大滤波
```

`0xF` = 采样频率 f_DTS/32，连续 8 次一致才认。

**作用**：抑制电机换向电刷火花产生的高频干扰。

**代价**：约 1~2 µs 延迟，对 5 ms 控制周期可忽略。

**⑥ 编码器接口（第 91~92 行，行号为旧版）**

```c
TIM_EncoderInterfaceConfig(ENCODER_LEFT_TIM, TIM_EncoderMode_TI12,
                           TIM_ICPolarity_Rising, TIM_ICPolarity_Rising);
```

**`TIM_EncoderMode_TI12`** = 4 倍频（A、B 所有边沿都计数）。

**两个 `Rising`** = 两通道都不反相。若改成一个 Rising 一个 Falling，可以反转计数方向（不用改接线）。

#### 2.3.2 `Encoder_Update()`：16 位回绕技巧

```c
CurrCounter = (int16_t)TIM_GetCounter(ENCODER_LEFT_TIM);
EncLeft_DeltaCounter = (int16_t)((uint16_t)CurrCounter - (uint16_t)EncLeft_LastCounter);
EncLeft_LastCounter = CurrCounter;
```

**问题：计数器会回绕。** 16 位计数器范围 0~65535，转满就回绕到 0。

从 65530 正转到 3：实际转了 9。但朴素写法 `3 − 65530 = −65527`，**完全错误**。

**解法：无符号减法 + 有符号解释。**

正向（实际 +9）：

| 步骤 | 计算 | 结果 |
|---|---|---|
| 转成无符号 | `(uint16_t)3` | `0x0003` |
| 转成无符号 | `(uint16_t)65530` | `0xFFFA` |
| 无符号 16 位减法（自动模 65536） | `0x0003 − 0xFFFA` | `0x0009` = 9 |
| 转回有符号 | `(int16_t)9` | **9** ✅ |

反转（实际 −9）：

| 步骤 | 计算 | 结果 |
|---|---|---|
| 转成无符号 | `(uint16_t)65530` | `0xFFFA` |
| 转成无符号 | `(uint16_t)3` | `0x0003` |
| 无符号 16 位减法 | `0xFFFA − 0x0003` | `0xFFF7` = 65527（无符号） |
| 转回有符号 | `(int16_t)0xFFF7` | **−9** ✅ |

**为什么一定正确**：无符号 16 位减法的结果天然是「模 65536 的差值」，而 `int16_t` 的范围正好是 −32768~32767。**只要一个周期内增量不超过 ±32767**，结果永远正确。

> **代码必须写 `(int16_t)((uint16_t)Curr − (uint16_t)Last)`，不能直接相减。**
> 少这层转换，会出现「每转一圈速度突然反向」的诡异 bug。

#### 2.3.3 读取接口

```c
int16_t Encoder_GetDeltaLeft(void)  { return EncLeft_DeltaCounter; }
int16_t Encoder_GetDeltaRight(void) { return EncRight_DeltaCounter; }
```

**可重复读取，不会清零。**

还有调试接口：

```c
int16_t Encoder_GetRawLeft(void)  { return (int16_t)TIM_GetCounter(ENCODER_LEFT_TIM); }
```

直接读累计值，用于判断编码器方向、是否丢脉冲。

这三个函数都**没有形参**，返回值是 `int16_t`（`GetRaw` 返回的是 16 位累计计数，会回绕，只适合看趋势，不要拿去相减）。

### 2.4 踩过的坑

#### 2.4.1 坑 1（最贵的一个）：编码器不接 TB6612

**TB6612FNG 是一颗纯 H 桥（电机驱动），没有任何编码器接口。** 它的全部引脚里，没有一个脚是给编码器用的：

| 引脚 | 功能 | 性质 |
|---|---|---|
| VM | 电机电源（本项目 12.6 V） | 电源输入 |
| VCC | 逻辑电源（3.3 V） | 电源输入 |
| GND | 地 | 电源 |
| **AO1 / AO2** | **左电机输出** | ⚠️ 功率输出，20 kHz、12.6 V |
| **BO1 / BO2** | **右电机输出** | ⚠️ 功率输出，20 kHz、12.6 V |
| PWMA / AIN1 / AIN2 | 左电机控制 | 数字输入 |
| PWMB / BIN1 / BIN2 | 右电机控制 | 数字输入 |
| STBY | 待机使能 | 数字输入 |

若把编码器信号接到 AO1/AO2/BO1/BO2：

| 后果 | 原因 |
|---|---|
| 💀 编码器瞬间烧毁 | 12.6 V 打进 3.3 V 的霍尔/光耦 |
| 💀 TB6612 可能烧毁 | 编码器输出端顶 H 桥功率输出脚 |
| 电机完全不转 | 电机电源线被挪走 |

**正确接法只有一种：粗线（M+/M−）接 TB6612，四根细线（A/B/VCC/GND）全接 STM32。** 完整表见 2.1.1。

#### 2.4.2 坑 2：PA15/PB3 不关 JTAG，读到的永远是 0

复位后 PA15 = JTDI、PB3 = JTDO，被调试口占着。**必须先 `GPIO_Remap_SWJ_JTAGDisable`，再配 TIM2 重映射**，顺序反了也读不到。

#### 2.4.3 坑 3：用 `AFIO->MAPR |=` 裸寄存器，会「重新上电就坏」

`SWJ_CFG[2:0]` 是只写位，读回值未定义。`|=` 会先读出垃圾值、或上要写的位、再写回去——**把垃圾值写回 SWJ_CFG，随机破坏 JTAG 配置**。

症状特别像接触不良：同一份固件，拔电重插几次，有时好有时坏。**只用库函数 `GPIO_PinRemapConfig`，别图省事。**

#### 2.4.4 坑 4：PB3 不串 1 kΩ，插着下载器复位就对顶

PB3 复位时是 JTDO，下载器在驱动它；编码器也在驱动它。两个推挽输出对顶，电流没有限制，**谁烧不一定**。串 1 kΩ 后最坏 3.3 mA，安全。

#### 2.4.5 坑 5：回绕少写 `uint16_t` 转换，每转一圈速度突然反向

直接 `Curr − Last` 在回绕那一刻得到 −65527 之类的值。现象是**轮子明明匀速转，速度环每转一圈就抽一下**，PID 输出跟着抖。

#### 2.4.6 坑 6：增量读一次就清零，第二个使用者永远读到 0

这是设计时特意避开的：`Encoder_Update()` 一个周期算一次，接口只读不清。如果改成「读的时候现算并清零」，PID 拿走了，VOFA+ 和蓝牙调参就只能看到 0。

#### 2.4.7 坑 7：左右轮速度不一样

| 原因 | 处理 |
|---|---|
| 两个电机本身有差异 | 正常，用 PID 各自闭环 |
| 编码器线数不同 | 换同型号 |
| 减速比不同 | 换同型号 |
| 轮子直径不同 | 量一下 |

### 2.5 故障速查

| 现象 | 先去查哪里 |
|---|---|
| 编码器一直读 0 | 先看编码器 VCC/GND 接没接（很多人只接 A/B），再看 JTAG 关没关（PA15/PB3） |
| 还是 0 | 确认 A/B 接的是 STM32 而不是 TB6612，转电机看 `Encoder_GetRawLeft()` 会不会变 |
| 只有左轮读 0（右轮正常） | 左轮走 PA15/PB3，查 JTAG 关没关、PB3 的 1 kΩ 电阻装没装 |
| 每转一圈速度突变一次 | 回绕处理写错了，少 `uint16_t` 转换（见 2.3.2） |
| 数值一直抖 | 滤波值太小，或引脚接触不良 |
| 偶尔出现极大值 | 编码器电源不稳，或地线没共好 |
| 方向反了（前进报负数） | 软件最简单：在 `Service.c` 里把 `actual` 取负；或把一个 `Rising` 改 `Falling`；或 A/B 对调 |
| 左右轮同样占空比速度差很多 | 电机个体差异（正常，靠 PID 闭环）、线数不同、减速比不同、轮径不同 |

## 第三部分 按键 Key.c

### 一句话职责

**把「物理按键被按下」这个动作，消抖成一个可以查询的事件标志位。** 它不决定按下之后干什么（那是状态机的事），只负责「确认真的按了一下，并且只算一次」。

完整链路是这样的：

1. 手指按下去（机械动作）
2. PA0 引脚电平从 1 变 0（并伴随 5~20 ms 的抖动）
3. `Key_CheckRequest()` 每 10 ms 检查一次，做消抖
4. `Key_Request = 1`
5. `Key_GetRequest()` 被 `Service.c` 取走，取走后清零
6. `CarRun_State` 翻转（启动 / 停止）

### 3.1 硬件与引脚

#### 3.1.1 引脚定义

```c
#define KEY_CLK             RCC_APB2Periph_GPIOA
#define KEY_PORT            GPIOA
#define KEYA_PIN            GPIO_Pin_0   // 原为 PA8，与左轮 PWM(TIM1_CH1) 撞脚，已挪到 PA0
```

#### 3.1.2 配置

```c
GPIO_InitStruct.GPIO_Mode  = GPIO_Mode_IPU;      // 上拉输入
GPIO_InitStruct.GPIO_Pin   = KEYA_PIN;
GPIO_InitStruct.GPIO_Speed = GPIO_Speed_50MHz;
GPIO_Init(KEY_PORT, &GPIO_InitStruct);
```

`IPU` = 内部上拉。芯片内部有一个电阻把引脚拉到 3.3 V，外面不用再接上拉电阻。

#### 3.1.3 接线与电平

按键的一端接 PA0，另一端接 GND。**不需要外接电阻**：上拉由芯片内部完成。

| 按键状态 | PA0 电平 | 为什么 |
|---|---|---|
| **松开** | 上拉 → **1** | 按键没通，内部电阻把引脚拉到 3.3 V |
| **按下** | 通 GND → **0** | 按键把引脚直接短到地 |

**所以代码里判断「按下」是 `current_level == 0`。**

量电压验证：松开应该是 3.3 V，按下应该是 0 V。

#### 3.1.4 历史上的 PA8 撞脚

```c
// 原为 PA8，与左轮 PWM(TIM1_CH1) 撞脚，已挪到 PA0
```

**PA8 是 TIM1_CH1（左轮 PWM）。** 曾经按键和 PWM 抢同一根引脚——按键会把 PWM 拉低，电机就抖。**挪到 PA0 后解决。** 完整故事见坑 1。

### 3.2 核心结构

#### 3.2.1 为什么必须消抖

机械按键的触点在闭合瞬间会弹跳，不是干净的 1→0。

| 阶段 | 你以为的 | 实际发生的 |
|---|---|---|
| 松开时 | 一直是 1 | 一直是 1 |
| 按下瞬间 | 立刻变成 0 | **5~20 ms 内 0/1 乱跳**，被 10 ms 采样读成 3~5 次 |
| 按住时 | 一直是 0 | 一直是 0 |

**不消抖会怎样**（假设你按了一下）：

1. 第 1 次读：0 → 认为按下 → 车启动
2. 第 2 次读：1 → 认为松开 → 无动作
3. 第 3 次读：0 → 认为按下 → 车停止
4. 第 4 次读：1 → 无动作
5. 第 5 次读：0 → 认为按下 → 车启动

**一次按键，车反复启停 3 次。** 这是不能接受的。

> **消抖的本质：只在电平「稳定保持一段时间」之后，才承认它变了。**

#### 3.2.2 四个状态变量

```c
static uint8_t  Key_Request    = 0;    //待处理的按键事件(0=无 1=有一次按下)
static uint8_t  KeyStableLevel = 1;    //已确认的稳定电平(1=松开 0=按下)
static uint8_t  KeyLastSample  = 1;    //上一次采样值,用于判断电平是否变化
static uint32_t KeyA_Ticks     = 0;    //采样值最后一次变化的时刻
```

四个变量，四句话：

| 变量 | 类型 | 初值 | 含义 |
|---|---|---|---|
| `Key_Request` | `uint8_t` | 0 | **事件标志**，`Key_GetRequest` 读后清零 |
| `KeyStableLevel` | `uint8_t` | 1 | **已确认**的稳定电平（这个才是「当前按键状态」） |
| `KeyLastSample` | `uint8_t` | 1 | **上一次采样值**，用于判断「电平有没有变化」 |
| `KeyA_Ticks` | `uint32_t` | 0 | 用于计时的时刻戳 |

#### 3.2.3 为什么需要两个「电平」变量

| 角色 | 用途 | 变化频率 |
|---|---|---|
| **`KeyLastSample`** | 判断「要不要重置计时器」 | 每 10 ms 可能变 |
| **`KeyStableLevel`** | 判断「要不要提交事件」 | 只在确认稳定后变 |

**这两个变量分工明确，缺一不可。** 合成一个会怎样，见坑 2——那是本册最值得看的一段。

#### 3.2.4 `static` 的作用

**这四个变量只在本文件可见。** 外部不能直接改，只能通过三个函数：

```c
void    Key_Init(void);
void    Key_CheckRequest(uint32_t current_tick);
uint8_t Key_GetRequest(void);
```

**好处**：状态封装，外部改不坏。别人想「偷偷把 `Key_Request` 置 1」也做不到，只能老实地按按键。

#### 3.2.5 为什么不需要 `volatile`

```c
static uint8_t Key_Request = 0;
```

**这些变量只在主循环里读写，不在中断里。** 所以不需要 `volatile`。

对比 `SysTicks`（中断里改、主循环里读）就必须加 `volatile`。判断标准只有一条：**这个变量会不会在中断里被改**。会 → 加；不会 → 不加。

### 3.3 函数逐个讲

#### 3.3.1 `Key_Init()`

原文没有单独逐行讲这个函数。它要做的事就是把 3.1.2 那几行执行一遍：开 GPIOA 时钟（`KEY_CLK` 就是 `RCC_APB2Periph_GPIOA`）、把 PA0 配成上拉输入。没有形参，没有返回值。

#### 3.3.2 `Key_CheckRequest()`：消抖算法（正确版）

```c
void Key_CheckRequest(uint32_t current_tick)
{
    uint8_t current_level = GPIO_ReadInputDataBit(KEY_PORT, KEYA_PIN);

    //1.采样值与上次不同 -> 重新开始计时
    if (current_level != KeyLastSample)
    {
        KeyA_Ticks    = current_tick;
        KeyLastSample = current_level;
    }

    //2.连续 20ms 采样值没变 -> 认为电平真的稳定了
    if ((current_tick - KeyA_Ticks) >= 20)
    {
        //3.稳定电平与"已确认电平"不同 -> 提交这次变化
        if (current_level != KeyStableLevel)
        {
            KeyStableLevel = current_level;
            if (current_level == 0)      //低电平 = 按下
            {
                Key_Request = 1;
            }
        }
    }
}
```

**三步逻辑：**

| 步 | 判断 | 动作 |
|---|---|---|
| **①** | 采样值和上次不同？（电平在动） | **重置计时器** |
| **②** | 计时器已经过了 20 ms？（电平不动了） | 继续 |
| **③** | 稳定的电平和已确认的不一样？ | **提交，更新 `KeyStableLevel`** |

**完整推演（按下过程，10 ms 调一次）。** 初始：`KeyLastSample=1`，`KeyStableLevel=1`，`KeyA_Ticks=0`。

| 时刻 | 电平 | ① 执行？ | `KeyA_Ticks` | ② 成立？ | ③ 执行？ | `Key_Request` |
|---|---|---|---|---|---|---|
| t=0（松开） | 1 | 否（1==1） | 0 | 是 | 否（1==1） | 0 |
| t=100（按下） | **0** | ✅ 是 | **100** | 否（0≥20 假） | — | 0 |
| t=110 | 0 | 否（0==0） | 100 | 否（10≥20 假） | — | 0 |
| t=120 | 0 | 否 | 100 | ✅ **是** | ✅ **是** | **1** ✅ |

**按下后 20 ms 触发一次。**

> 校注：原文 t=0 那一行把 ② 记成「是」。严格按式子算 `0 − 0 = 0 < 20`，这一拍 ② 应为「否」，不过那时 ③ 本来也不会执行，结论不变。此处保留原文。

**按住不放会重复触发吗？** 从 t=120 之后：

| 时刻 | 电平 | ① | ② | ③ | `Key_Request` |
|---|---|---|---|---|---|
| t=130 | 0 | 否 | 是 | 否（0==0） | 保持 1 |
| t=200 | 0 | 否 | 是 | 否 | 保持 1 |
| t=1000 | 0 | 否 | 是 | 否 | 保持 1 |

**因为 `KeyStableLevel` 已经是 0，③ 不再成立 → 不会重复触发。** ✅

**松开时会不会误触发？**

| 时刻 | 电平 | ① | ② | ③ | `Key_Request` |
|---|---|---|---|---|---|
| t=2000（松开） | **1** | ✅ 是 | 否 | — | 不变 |
| t=2020 | 1 | 否 | ✅ 是 | ✅ 是（1≠0） | `KeyStableLevel=1`，**但不置 `Key_Request`**（只有 0 才置） |

**松开只更新状态，不触发事件。** ✅

**逐句看，有四个要点：**

**① 读电平**

```c
uint8_t current_level = GPIO_ReadInputDataBit(KEY_PORT, KEYA_PIN);
```

返回 `Bit_SET`（1）或 `Bit_RESET`（0）。

**这只读一次**，后面所有判断都用这个快照——避免在函数内部两次读之间电平变化造成不一致。

**② 变化检测与计时**

```c
if (current_level != KeyLastSample)
{
    KeyA_Ticks    = current_tick;
    KeyLastSample = current_level;
}
```

**两个动作必须成对：**

| 动作 | 作用 |
|---|---|
| `KeyA_Ticks = current_tick` | 重置计时器（抖动期间不断重置） |
| `KeyLastSample = current_level` | **更新采样值，防止下一拍又进这个分支** |

**只做前一个 → 就是坑 2 那个 bug。**

**③ 稳定判定**

```c
if ((current_tick - KeyA_Ticks) >= 20)
```

**为什么用 `>=` 而不是 `==`：** 调用周期是 10 ms，计时值可能是 10、20、30……如果写 `== 20`，某次因为中断延迟跳到 30 就直接错过了。**用 `>=` 永远不会漏。**

**④ 提交**

```c
if (current_level != KeyStableLevel)
{
    KeyStableLevel = current_level;

    if (current_level == 0)      //低电平 = 按下
    {
        Key_Request = 1;
    }
}
```

**注意：只有「按下」才置 `Key_Request`，松开只更新状态。**

| 事件 | 更新 `KeyStableLevel` | 置 `Key_Request` |
|---|---|---|
| 按下（1→0） | ✅ | ✅ |
| 松开（0→1） | ✅ | ❌ |

#### 3.3.3 `Key_GetRequest()`：消费型接口

```c
uint8_t Key_GetRequest(void)
{
    if (Key_Request == 1)
    {
        Key_Request = 0;    // ★ 读后清零
        return 1;
    }
    return 0;
}
```

没有形参。返回 `1` = 有一次按下（并且已经把它吃掉），返回 `0` = 没有。

**「消费型」vs「生产型」：**

| 类型 | 行为 | 本工程例子 |
|---|---|---|
| **消费型** | 读一次就清掉 | `Key_GetRequest()`、`Voice_GetCommand()` |
| **生产型** | 读后不清零，可重复读 | `Encoder_GetDeltaLeft()`、`SysTimer_GetTick()` |

**怎么选：**

- **事件**（一件事发生了一次）→ 消费型
- **测量值**（持续存在的量）→ 生产型

**按键是事件，所以用消费型。**

**为什么不直接返回 `Key_Request`：**

```c
// ❌ 错误：外部读到 1 之后不清零，会一直读到 1
uint8_t Key_IsPressed(void) { return Key_Request; }
```

`Task_StartStopCmd` 每 100 ms 调一次，如果不清零，**车会每 100 ms 启停一次**。

#### 3.3.4 调用位置与参数

**调用位置：**

```c
// Service.c
void ServiceTask_10ms(uint32_t curr_ms)
{
    if(curr_ms - task_last_10ms < 10) return;
    task_last_10ms = curr_ms;
    Key_CheckRequest(curr_ms);        // ← 每 10ms 调一次
}
```

```c
// Service.c
static void Task_StartStopCmd(void)
{
    if(Key_GetRequest() == 1)          // ← 每 100ms 查一次
    {
        CarRun_State = !CarRun_State;
    }
}
```

**参数评价：**

| 参数 | 值 | 评价 |
|---|---|---|
| 检查周期 | 10 ms | ✅ 够快 |
| 消抖阈值 | 20 ms | ⚠️ **偏小**，只相当于「连续 2 次采样一致」 |
| 典型机械按键抖动 | 5~20 ms | 可能刚好卡在边界 |

**建议 30~50 ms 更稳**（人按下按键会保持 100 ms 以上，不会有延迟感）。**但当前 20 ms 可用，不必改。**

**为什么不用 EXTI 外部中断：** 技术上可以（PA0 支持 EXTI0），但——

| 方式 | CPU 占用 | 消抖 | 复杂度 |
|---|---|---|---|
| **轮询（现在）** | 每 10 ms 查一次，几乎为 0 | 软件消抖，简单 | 低 |
| EXTI 中断 | 每次抖动都触发中断 | 中断里还得软件消抖 | 高 |

**轮询更简单、更稳。10 ms 的响应延迟人感觉不到。**

**为什么 `KeyA_Ticks` 用 `uint32_t`：** 因为要接收 `SysTimer_GetTick()` 的返回值（32 位毫秒）。减法 `(current_tick - KeyA_Ticks)` 天然免疫 49.7 天回绕（无符号减法自动模 2³²）。

#### 3.3.5 扩展：加第二个按键

现在的代码是「硬编码单个按键」，加第二个要复制一遍逻辑。改成结构体数组的写法：

```c
typedef struct {
    GPIO_TypeDef *port;
    uint16_t      pin;
    uint8_t       stable;
    uint8_t       last;
    uint32_t      ticks;
    uint8_t       request;
} key_t;

static key_t keys[2] = {
    { GPIOA, GPIO_Pin_0, 1, 1, 0, 0 },
    { GPIOA, GPIO_Pin_1, 1, 1, 0, 0 },
};

void Key_CheckRequest(uint32_t now)
{
    uint8_t i;
    for (i = 0; i < 2; i++)
    {
        uint8_t lv = GPIO_ReadInputDataBit(keys[i].port, keys[i].pin);

        if (lv != keys[i].last)
        {
            keys[i].ticks = now;
            keys[i].last  = lv;
        }

        if ((now - keys[i].ticks) >= 20 && lv != keys[i].stable)
        {
            keys[i].stable = lv;
            if (lv == 0) keys[i].request = 1;
        }
    }
}
```

**加第三个按键只需在数组里加一行。**

**但赛前不建议改**——现在的单键够用，重构会引入风险。

### 3.4 踩过的坑

#### 3.4.1 坑 1：PA8 与左轮 PWM 撞脚

按键原来接在 PA8。**PA8 是 TIM1_CH1，左轮 PWM 的输出脚。**

结果：按下按键时，GPIO 把引脚拉低，PWM 波形被破坏，**电机跟着抖**。松开又好了，所以一开始很容易误判成「电机驱动有问题」。

**挪到 PA0 后解决。**

> **教训：STM32 的引脚是复用的，加新功能前必须核对「这根脚还有谁在用」。** 本工程一共撞过四次：PA8（按键 vs PWM）、PB13~15（方向 vs TIM1 互补）、PA15/PB3（编码器 vs JTAG）、PA9/PA10（TIM1_CH2/CH3 vs K210 串口），全都记在附录 A。

#### 3.4.2 坑 2（本册最值钱的一段）：一个变量扛两个职责，按键永久失效

**原始代码：**

```c
static uint8_t  Key_Request    = 0;
static uint8_t  KeyAPastLevel  = 1;    // ← 一个变量扛了两个职责
static uint32_t KeyA_Ticks     = 0;

void Key_CheckRequest(uint32_t current_tick)
{
    uint8_t current_level = GPIO_ReadInputDataBit(KEY_PORT, KEYA_PIN);

    if (current_level != KeyAPastLevel)      // ① 变了就计时
    {
        KeyA_Ticks = current_tick;
    }

    if ((current_tick - KeyA_Ticks) >= 20)   // ② 稳定 20ms
    {
        if (current_level != KeyAPastLevel)  // ③ 再确认
        {
            KeyAPastLevel = current_level;
            if (current_level == 0)
            {
                Key_Request = 1;
            }
        }
    }
}
```

**看起来逻辑很合理，实际上按键永久失效。**

**推演：**

| 时刻 | 电平 | `KeyAPastLevel` | ① 执行？ | `KeyA_Ticks` | ② 成立？ |
|---|---|---|---|---|---|
| t=100（按下） | **0** | 1 | ✅ 是 | **=100** | 否（0≥20 假） |
| t=110 | **0** | 1 | ✅ 是 | **=110** | 否 |
| t=120 | **0** | 1 | ✅ 是 | **=120** | 否 |
| t=130 | **0** | 1 | ✅ 是 | **=130** | 否 |
| … | … | … | **永远执行** | **永远=当前时刻** | **永远不成立** |

**死循环是这样形成的：**

1. ① 执行 —— 因为 `current_level != KeyAPastLevel`
2. `KeyA_Ticks` 被清成当前时刻
3. ② 的差值恒为 0，永远 < 20
4. ③ 永远不执行 → `KeyAPastLevel` 永远不更新
5. `current_level` 永远 != `KeyAPastLevel`
6. 回到 ①，继续执行

**`Key_Request` 永远是 0 → 按键完全无效。**

**根因：一个变量扛了两个职责。**

| 需要的角色 | 原始代码由谁承担 |
|---|---|
| **上一次采样值**（判断「有没有变化」） | `KeyAPastLevel` |
| **已确认的稳定电平**（判断「要不要提交」） | `KeyAPastLevel`（同一个） |

**同一个变量不能既当「候选」又当「已确认」。**

**修复：拆成两个变量。**

```c
static uint8_t KeyStableLevel = 1;   // 已确认
static uint8_t KeyLastSample  = 1;   // 上次采样（新增）
```

```c
if (current_level != KeyLastSample)   // 用"采样值"判断变化
{
    KeyA_Ticks    = current_tick;
    KeyLastSample = current_level;    // ← 关键：更新采样值
}

if ((current_tick - KeyA_Ticks) >= 20)
{
    if (current_level != KeyStableLevel)   // 用"稳定值"判断提交
    {
        KeyStableLevel = current_level;
        ...
    }
}
```

**这类 bug 的通用特征：**

| 特征 | 说明 |
|---|---|
| **编译不报错** | 语法完全正确 |
| **不崩溃** | 只是行为错误 |
| **难以察觉** | 表现是「功能没反应」，容易怀疑硬件 |
| **根因是状态机设计** | 一个变量承担多重语义 |

> **写状态机时，先列出「需要记住哪些状态」，每个状态一个变量，不要复用。**

### 3.5 故障速查

**先花两分钟定位，四种方法：**

- **看标志位**：Keil 调试，Watch 窗口加 `Key_Request`、`KeyStableLevel`、`KeyLastSample`、`KeyA_Ticks`，按下看 `Key_Request` 是否变 1。
- **用灯**：在 `ServiceTask_100ms` 里临时加 `if (Key_GetRequest() == 1) Indicator_Toggle();`，按一下灯翻一下就是正常。
- **VOFA+**：把 `Key_Request` 塞进一个通道，按下时应该看到 0→1 的跳变。
- **万用表**：量 PA0 对地电压，松开 3.3 V、按下 0 V。如果按下还是 3.3 V，是按键或接线问题，不是代码问题。

| 现象 | 先去查哪里 |
|---|---|
| 按下去没反应 | 依次查：PA0 电平会不会变（万用表）→ 按键一端是否接 GND → `Key_CheckRequest` 有没有被调（Watch 看 `KeyA_Ticks` 变不变）→ `Key_GetRequest` 有没有被调 → 最后才怀疑消抖逻辑 |
| 按一次触发好几次 | 消抖阈值太小（20 → 30 或 50）；或 `Key_Request` 没清零（查 `Key_GetRequest`）；或按键质量差、抖动特别长（加 100 nF 电容对地） |
| 按住不放一直触发 | `KeyStableLevel` 没更新，查 3.3.2 的「④ 提交」那段 |
| 一上电就触发一次 | 上电瞬间引脚抖动，初始化时多读几次，或上电后延时 100 ms 再开始扫描 |
| 按一下车启停两三次 | 同「按一次触发好几次」，优先怀疑 `Key_Request` 没被消费掉 |

## 第四部分 蓝牙 BlueTooth.c

### 一句话职责

**把 USART2 收到的字节，用最短的时间塞进一个 32 字节的环形队列，等主循环来取。** 它只管「搬字节」，完全不懂协议——解析是中间层 `Protocol.c` 的事。

### 4.1 硬件与引脚

#### 4.1.1 它在整个链路里的位置

1. 手机 / 电脑（VOFA+ 或串口助手）
2. 蓝牙（空中，2.4 GHz）
3. JDY-31 模块
4. 串口（有线，USART2）
5. STM32 的 PA3 引脚
6. 硬件把字节搬进 DR 寄存器
7. USART2 中断
8. 32 字节环形队列
9. 主循环 `Task_BtTuning()`（每 100 ms）
10. `Protocol_BtParse()`（中间层解析）
11. 改 PID 的 Kp / Ki / Kd

**本文件只负责「收字节」，完全不懂协议。** 解析是中间层 `Protocol.c` 的事。

#### 4.1.2 引脚：只配接收脚 PA3

```c
// BlueTooth.c —— 只配接收脚 PA3
RCC_APB2PeriphClockCmd(RCC_APB2Periph_GPIOA, ENABLE);

/* 本文件只负责接收脚 PA3。
 * 发送脚 PA2 由 Debug.c 的 Debug_Init() 配置（对应 VOFA+ 波形输出）。 */
GPIO_InitTypeDef GPIO_InitStruct;
GPIO_InitStruct.GPIO_Mode  = GPIO_Mode_IPU;        // 上拉输入
GPIO_InitStruct.GPIO_Pin   = GPIO_Pin_3;           // PA3 = USART2_RX
GPIO_InitStruct.GPIO_Speed = GPIO_Speed_50MHz;
GPIO_Init(GPIOA, &GPIO_InitStruct);
```

| 引脚 | 功能 | 模式 | 为什么这个模式 | 谁配置的 |
|---|---|---|---|---|
| **PA2** | USART2_TX | `AF_PP` 复用推挽 | 交给串口外设控制 | **`Debug.c`** |
| **PA3** | USART2_RX | `IPU` 上拉输入 | 没接设备时保持高电平，不会收到乱码 | **`BlueTooth.c`** |

#### 4.1.3 接线

| STM32 | 方向 | 模块 | 说明 |
|---|---|---|---|
| PA2（TX） | → | 模块 RXD | 单片机发、模块收 |
| PA3（RX） | ← | 模块 TXD | 模块发、单片机收 |
| GND | — | 模块 GND | **必须共地** |

**TX 接 RXD、RX 接 TXD，要交叉。** 同名相接（PA2 接 TXD）是常见接线错。

#### 4.1.4 串口参数

```c
USART_InitStruct.USART_BaudRate = 115200;
USART_InitStruct.USART_Mode = USART_Mode_Tx | USART_Mode_Rx;
USART_InitStruct.USART_WordLength = USART_WordLength_8b;
USART_InitStruct.USART_StopBits = USART_StopBits_1;
USART_InitStruct.USART_Parity = USART_Parity_No;
USART_InitStruct.USART_HardwareFlowControl = USART_HardwareFlowControl_None;
```

**标准「115200 8N1」。**

| 参数 | 值 | 必须和谁一致 |
|---|---|---|
| 波特率 | **115200** | **模块的 UART 波特率** |
| 数据位 | 8 | 模块 |
| 停止位 | 1 | 模块 |
| 校验 | 无 | 模块 |

> ⚠️ **这个值必须等于模块的波特率。**
> JDY-31 出厂默认 **9600**。如果模块没改过 AT，这里写 115200 就通不了。
> 模块是多少，这里就要改成多少。

#### 4.1.5 中断配置

```c
USART_ITConfig(USART2, USART_IT_RXNE, ENABLE);

NVIC_InitStruct.NVIC_IRQChannel = USART2_IRQn;
NVIC_InitStruct.NVIC_IRQChannelPreemptionPriority = 3;   // 最低
NVIC_InitStruct.NVIC_IRQChannelSubPriority = 1;
```

**为什么只开 RXNE：**

| 中断 | 用途 | 本文件开不开 |
|---|---|---|
| `RXNE`（接收寄存器非空） | 收到一个字节 | ✅ **开** |
| `TXE`（发送寄存器空） | 可以发下一个字节 | ❌ 不开（发送由 `Debug.c` 用 DMA 做） |
| `ORE`（溢出错误） | 字节被覆盖 | ❌ 没开（见坑 4） |

**注意：`TXE` 不用开，是因为「发送」根本不归这个文件管。**

**什么时候才需要开 TXE 中断：**

| 发送方式 | 需要 TXE 中断吗 | 本工程谁在用 |
|---|---|---|
| 轮询（阻塞） | ❌ 不需要 | 测试固件 `Test_SendByte` |
| **DMA** | ❌ 不需要 | **`Debug.c`（正式固件）** |
| 中断逐字节 | ✅ 需要 | 没人用 |

**为什么优先级是 3（最低）：**

| 中断 | 抢占优先级 | 说明 |
|---|---|---|
| USART1（K210 视觉） | 0 | 最高 |
| TIM3（1 ms 时基） | 1 | |
| USART3（语音） | 2 | |
| USART2（蓝牙） | **3** | **最低** |

**蓝牙调参不是实时任务，晚几微秒处理完全没关系。**

### 4.2 核心结构：环形队列

#### 4.2.1 为什么需要队列

**中断里不能做耗时的事。**

| 做法 | 中断里干什么 | 耗时 | 后果 |
|---|---|---|---|
| ❌ 错误 | 收到字节**立刻解析协议**（13 字节帧要做 13 次状态机判断） | 中断持续几十微秒 | 影响其他更重要的中断 |
| ✅ 正确 | 收到字节**塞进队列**立刻退出 | 约 0.14 µs | 主循环慢慢取出来解析 |

#### 4.2.2 三个变量

```c
#define BT_QUEUE_SIZE  32          // 必须是 2 的幂！

static uint8_t bt_rx_queue[BT_QUEUE_SIZE];   // 32 字节的盒子
static volatile uint16_t bt_rx_head = 0;     // 写指针（中断动）
static volatile uint16_t bt_rx_tail = 0;     // 读指针（主循环动）
```

| 名字 | 是什么 | 谁改它 |
|---|---|---|
| `bt_rx_queue` | 32 格的数据盒子 | 中断写、主循环读 |
| `bt_rx_head` | **写指针**：下一个字节放第几格 | 中断 |
| `bt_rx_tail` | **读指针**：下一个字节从第几格取 | 主循环 |

#### 4.2.3 环形队列怎么转

| 步骤 | `head` | `tail` | 队列里有什么 | 说明 |
|---|---|---|---|---|
| 初始 | 0 | 0 | 空 | **判空条件：`head == tail`** |
| 中断写入 A、B、C | 3 | 0 | A B C | 分别写进第 0、1、2 格 |
| 主循环读出 1 个 | 3 | 1 | B C | 取走第 0 格的 A，`tail` 前进一格 |
| 一直写、写到第 31 格之后 | **绕回 0** | 0 | 满 32 个 | `head` 追上 `tail`，看起来又「空」了——这就是坑 3 |

**数组只有 32 格，但 head/tail 一直加、加到 32 就 `& 31` 绕回 0**，所以叫「环形」。

#### 4.2.4 为什么必须是 2 的幂

```c
bt_rx_head = (bt_rx_head + 1) & (BT_QUEUE_SIZE - 1);
                                 ↑
                            & 31 等价于 % 32
```

| 写法 | 汇编指令 | 周期数 |
|---|---|---|
| `head % 32` | `UDIV` | **2~12 周期** |
| `head & 31` | `AND` | **1 周期** |

**在中断里，1 周期和 12 周期是有区别的。**

`& 31` 只对 2 的幂成立（31 = `0b11111`），所以 `BT_QUEUE_SIZE` 必须是 2、4、8、16、32、64……

#### 4.2.5 为什么用 `uint16_t` 而不是 `uint8_t`

队列只有 32 个元素，`uint8_t` 完全够（0~31）。

用 `uint16_t` 是为将来「放大队列」留余量——如果改成 256 或更大，`uint8_t` 就溢出了。

**代价**：多占 2 字节 RAM。可忽略。

#### 4.2.6 `volatile` 为什么必须加

```c
static volatile uint16_t bt_rx_head = 0;
```

`volatile` 告诉编译器：**这个变量可能被中断异步修改，每次都要从内存重新读，不许缓存到寄存器。**

**没有 `volatile` 会怎样：**

```c
// BlueTooth_ReadByte 里
if(bt_rx_head == bt_rx_tail) return 0;
```

编译器可能把 `head` 缓存在寄存器里，然后 `while` 循环里永远读到旧值 → **队列里明明有数据，程序认为一直是空的**。

**这是新手最常见、最难查的 bug 之一。**

### 4.3 函数逐个讲

#### 4.3.1 `BlueTooth_Init()`：执行顺序

1. GPIOA 时钟
2. PA3 配 IPU（RX）
3. USART2 时钟
4. `USART_Init`（115200 8N1，Tx|Rx）
5. 开 RXNE 中断
6. 配 NVIC（优先级 3/1）
7. `USART_Cmd(ENABLE)` ← **最后才使能**

**为什么最后才 `USART_Cmd`：** 先使能串口再配中断的话，中间可能已经有字节进来但中断还没配好 → 丢数据。**先配好一切，最后开门。**

#### 4.3.2 `USART2_IRQHandler()`：中断服务

```c
void USART2_IRQHandler(void)
{
    if(USART_GetITStatus(USART2, USART_IT_RXNE) == SET)
    {
        bt_rx_queue[bt_rx_head] = USART_ReceiveData(USART2);
        bt_rx_head = (bt_rx_head + 1) & (BT_QUEUE_SIZE - 1);
    }
}
```

**只有 2 条有效语句：**

| 语句 | 作用 |
|---|---|
| `bt_rx_queue[head] = USART_ReceiveData(USART2)` | 读出字节并存入队列 |
| `head = (head + 1) & 31` | 写指针前进一格（绕回） |

**注意：`USART_ReceiveData()` 这个读操作会自动清除 `RXNE` 标志。** 不需要额外清标志。

**执行时间 ≈ 10 个 CPU 周期 ≈ 0.14 µs。**

> 1 个字节在 115200 下是 87 µs 到达（10 bit ÷ 115200），处理只花 0.14 µs —— 余量极大。

#### 4.3.3 `BlueTooth_ReadByte()`：主循环取数据

```c
uint8_t BlueTooth_ReadByte(uint8_t *data)
{
    if(bt_rx_head == bt_rx_tail) return 0;                  // 空，返回 0

    *data = bt_rx_queue[bt_rx_tail];                        // 取出
    bt_rx_tail = (bt_rx_tail + 1) & (BT_QUEUE_SIZE - 1);    // 读指针前进
    return 1;                                                // 成功，返回 1
}
```

形参 `data` 是指针：取到的字节写在 `*data` 里。

| 返回 | 含义 |
|---|---|
| `1` | 取到一个字节，放在 `*data` 里 |
| `0` | 队列空，`*data` 未修改 |

**调用方式：**

```c
// Service.c 的 Task_BtTuning
uint8_t rx_byte;
BtCommand_t bt_cmd;

while (BlueTooth_ReadByte(&rx_byte) == 1)    // 一直取到空为止
{
    if (Protocol_BtParse(rx_byte, &bt_cmd) == 1)
    {
        // 解析出一帧，处理
    }
}
```

**用 `while` 一次把队列抽干**，避免积压。

### 4.4 踩过的坑

#### 4.4.1 坑 1：和 `Debug.c` 共用 USART2，初始化顺序不能反

**事实：**

| 文件 | 对 USART2 做什么 | 方向 |
|---|---|---|
| **`BlueTooth.c`** | 配 PA3、串口参数、RXNE 中断、环形队列 | **RX** |
| **`Debug.c`** | 配 PA2、DMA1_Channel7 → `USART2->DR` | **TX** |

**这是有意的设计**：一根无线链路，既是「调参通道」（收），又是「波形通道」（发）。手机/电脑连上 JDY-31 后：

- 发数据 → STM32 收 → 改 PID
- STM32 发 → 手机/电脑收 → VOFA+ 画波形

**省了一根线，也省了一个 USB-TTL。**

**带来的两个约束：**

| 约束 | 原因 |
|---|---|
| **不能在 PA2/PA3 上再接第二个设备** | 会和蓝牙模块抢引脚 |
| **初始化顺序必须是 `BlueTooth_Init()` → `Debug_Init()`** | USART2 必须先于 DMA 配置使能 |

**为什么顺序不能反：**

```c
// Service_Init（Service.c:50-51）
BlueTooth_Init();    // ① 先把 GPIO 和 USART2 配好
Debug_Init();        // ② 再配 DMA
```

如果先 `Debug_Init`：

```c
USART_DMACmd(USART2, USART_DMAReq_Tx, ENABLE);
```

这次操作写的是 USART2 的 `CR3` 寄存器。**如果 USART2 时钟还没开，这次写是无效的**（写进一个未使能外设的寄存器会被忽略）。

**后果：DMA 请求永远不会触发 → 一个字节都发不出去。而且读回寄存器也看不出问题**（写过但没生效），极其隐蔽。

#### 4.4.2 坑 2：PA2 曾经是「配的人不用、用的人不配」

重构前的 `BlueTooth.c`：

```c
// BlueTooth.c —— 重构前
GPIO_InitStruct.GPIO_Mode = GPIO_Mode_AF_PP;
GPIO_InitStruct.GPIO_Pin  = GPIO_Pin_2;      // ← PA2 是【发送】脚
GPIO_Init(GPIOA, &GPIO_InitStruct);
```

**`BlueTooth.c` 配置了 PA2（发送脚），但它自己从不发数据。** PA2 实际是 `Debug.c` 在用它往外发 VOFA+ 波形。

**责任边界错位**：配的人不用，用的人不配。这种错不会立刻炸，但后面谁改都想不通「为什么蓝牙文件要管发送脚」。

**重构后的分工：**

| 文件 | 只负责 |
|---|---|
| **`BlueTooth.c`** | PA3（RX）+ USART2 参数 + 接收中断 + 队列 |
| **`Debug.c`** | PA2（TX）+ DMA 发送 |

**为什么这样拆是安全的：**

| 风险点 | 为什么没问题 |
|---|---|
| **调用顺序** | `Service.c:50-51` 是 `BlueTooth_Init()` → `Debug_Init()`，PA2 在需要前就配好了 |
| **两函数之间有没有发送** | 没有。中间没有任何代码往 USART2 写数据 |
| **`USART_Init` 的收/发模式** | **完全没动**，`Tx` 和 `Rx` 都还开着 |
| **`DEBUG_ENABLE=0` 时** | `Debug_Init` 变成空宏 → PA2 不配置 → 但那时也没有发送代码，不影响 |
| **GPIOA 时钟被开了两次** | 幂等操作，无副作用 |

**为什么没把 `USART_Mode_Tx | USART_Mode_Rx` 也拆开：** 想彻底「每个文件只管自己那一半」，就得在 `BlueTooth.c` 里只置 `USART_Mode_Rx`，再在 `Debug.c` 里单独把 TE 打开——但 **StdPeriph 库没有单独的 `USART_TXCmd()` / `USART_RXCmd()`**。

| 函数 | 能单独控制 TE/RE 吗 |
|---|---|
| `USART_Cmd(USARTx, ENABLE)` | ❌ 只控制 `UE`（整个串口总开关） |
| `USART_Init(...)` | ⚠️ 能，但会**把其他参数一起重写** |

**只有两条路，都有问题：**

**路 1：裸寄存器**

```c
USART2->CR1 |= USART_CR1_TE;
```

| 风险 | 说明 |
|---|---|
| 绕过库函数 | 全工程其他地方用库函数，突然冒一句裸寄存器，风格不一致 |
| 容易写错位 | `USART_CR1_TE` 是 bit3，写错可能改到 `M`（数据位）或 `PCE`（校验） |

> 本工程已经有踩过同类坑的记录（`Encoder.c:47`）：
> ```c
> //  必须用库函数，禁止 AFIO->MAPR |= ... 这种裸寄存器写法：
> //  SWJ_CFG 是只写位，读回值未定义，读-改-写会随机制造"重新上电就坏"
> ```

**路 2：再调一次 `USART_Init`**

| 风险 | 说明 |
|---|---|
| 波特率要写两遍 | 改了一个忘另一个 → 一个发对、一个收错 |
| **可能清掉 `RXNEIE`** | `USART_Init` 重写 CR1，接收中断使能位可能被清 → **蓝牙收不到数据** |
| 顺序敏感 | 必须在 `BlueTooth_Init` 之后调 |

**结论：收益只是「名字更纯」，成本是真实 bug 风险。不值得。** 串口参数集中在一处配，反而是好事——改波特率只改一个地方。

#### 4.4.3 坑 3：队列满和空分不清

```c
if(bt_rx_head == bt_rx_tail) return 0;   // 只区分"空"，不区分"满"
```

**溢出会怎样**：队列满时 `head` 绕一圈追上 `tail`，两个指针相等 → 程序认为「空」。但实际 32 个字节还在里面，**读不出来，数据静默丢失，顺序也全乱**。

**实际会溢出吗：**

| 参数 | 值 |
|---|---|
| 队列大小 | 32 字节 |
| 主循环读取周期 | **100 ms** |
| 115200 下 100 ms 能来 | **1152 字节** |
| 结论 | **理论上一溢出就完蛋** |

**但人手调参一帧只有 13 字节，间隔几百毫秒 → 不会溢出。** 如果用脚本批量发指令就会丢。

**怎么修（可选）：**

```c
// ISR 里加满判断
uint16_t next = (bt_rx_head + 1) & (BT_QUEUE_SIZE - 1);
if (next != bt_rx_tail)               // 没满才写
{
    bt_rx_queue[bt_rx_head] = USART_ReceiveData(USART2);
    bt_rx_head = next;
}
else
{
    (void)USART_ReceiveData(USART2);  // 满就丢弃，但必须读走清标志
}
```

**注意：满了也必须读 DR，否则 `RXNE` 永远不消失，中断会反复触发。**

#### 4.4.4 坑 4：没有处理 ORE（溢出错误）

STM32 的 USART 有一个 `ORE`（Overrun Error）标志：中断还没读走上一个字节，下一个字节又到了 → ORE 置位 → 两个字节里丢掉一个。

**现在的代码没检查 ORE。**

**好消息**：读 DR 会自动清 ORE，所以不会卡死。
**坏消息**：偶发丢字节，没有任何告警。

#### 4.4.5 坑 5：`#include <stdio.h>` 是无用的

```c
#include <stdio.h>
```

文件里没有用到任何 stdio 函数。可能是之前想加 `printf` 重定向留下的。**不影响功能，只是多一行。**

#### 4.4.6 坑 6：模块与上位机的坑（实战总结）

> 这一节不是代码问题，是实际调试中踩过的坑，记下来避免重复。详细的排查记录另有 `问题记录.md` 收录。

**（1）AT 指令必须走「有线」。**

JDY-31 的 AT 指令只能从模块的 RXD 引脚（有线侧）进入，不能从蓝牙空中进入。

| 做法 | 结果 |
|---|---|
| ❌ 在 VOFA+ 里通过蓝牙发 `AT+VERSION` | 模块把它当成普通业务数据，原样从 TXD 吐给单片机，AT 解析器根本收不到 |
| ✅ 用 USB-TTL 接到模块的 RXD/TXD，从电脑的有线串口发 | 模块正常响应（回 `OK` 或版本号） |

**打个比方：蓝牙是对外营业窗口（只传话），RXD 引脚是内部电话（才能下指令）。**

**（2）配 AT 时模块必须「未连接」。**

模块处于「已连接」状态时不响应 AT 指令（它认为你在传数据）。

| 模块灯 | 状态 | 能配 AT 吗 |
|---|---|---|
| **闪** | 未连接，在广播 | ✅ 能 |
| **常亮** | 已连接 | ❌ 不能，先断开 |

**（3）蓝牙串口显示「未连接」是正常的。**

Windows / 手机设置页里显示「未连接」不代表故障。

| 设备类型 | 连接方式 | 设置页显示 |
|---|---|---|
| 耳机、鼠标 | 连上就一直保持 | 已连接 |
| **蓝牙串口（SPP）** | **只有程序打开 COM 口时才连接，程序关掉就断** | **未连接（正常）** |

**判断标准只有一条：打开 COM 口后有没有数据。**

**（4）一个模块只能连一台设备。**

JDY-31 同一时刻只能被一台设备连接。如果你用手机连过，电脑就连不上。必须先断开手机（并且在手机蓝牙设置里「取消配对」，不只是退出 App）。

**（5）官方文档明确：不支持苹果设备。**

JDY-31 是**蓝牙 3.0 SPP 经典蓝牙**，iOS 不支持 SPP 协议。**必须用 Android 或 Windows。**

**（6）Windows 可能存不住配对密钥。**

如果事件日志里出现：

```
[BTHUSB] Windows 无法在本地适配器上存储蓝牙身份验证代码(链接密钥)
```

会导致「有时连得上、有时连不上」。处理方法：

1. 重启电脑（清蓝牙栈）
2. 删除不用的配对设备（腾出密钥槽）
3. 删除 JDY-31 重新配对
4. 更新蓝牙驱动

**（7）电脑端串口软件的波特率基本无效。**

蓝牙虚拟串口的本地波特率通常被驱动忽略。真正决定成败的是 **「单片机 ↔ 模块」** 这一对的波特率是否一致。**别在电脑端波特率上白折腾。**

**（8）模块的 EN 脚。**

| 模块灯状态 | EN 怎么接 |
|---|---|
| 亮 / 闪 | 已有内部上拉，不接也行 |
| 不亮 | **必须接 3.3 V** |

**接 3.3 V 无副作用，不确定就接上。**

**（9）常见模块参数（JDY-31）。**

| 项目 | 出厂值 |
|---|---|
| 波特率 | **9600** |
| 广播名 | `JDY-31-SPP` |
| 配对码 | `1234` |
| 供电 | 1.8~3.6 V（**推荐 3.3 V，不能接 5 V**） |

**常用 AT 指令：**

| 指令 | 作用 |
|---|---|
| `AT` | 测试连通，回 `OK` |
| `AT+BAUD` | 查询当前波特率 |
| `AT+BAUD8` | 改成 115200（`4`=9600、`8`=115200） |
| `AT+NAMEJC01` | 改广播名 |
| `AT+PIN1234` | 改配对码 |
| `AT+DEFAULT` | 恢复出厂 |
| `AT+RESET` | 软复位 |

**所有指令以 `\r\n` 结尾**（串口助手要勾「发送新行」）。**波特率改完需要断电重启才生效。**

### 4.5 故障速查

**先做分步隔离，一次只让一个环节成为变量：**

1. 单片机自己在发吗？短接 PA2-PA3（模块先拔掉），能收到 = UART 正常
2. 模块 UART 好吗？短接模块 RXD-TXD，手机收到回显 = 模块正常
3. 两根线接对了吗？RXD→PA2、TXD→PA3
4. 波特率一致吗？模块多少，代码就写多少
5. 协议对吗？看帧尾 `00 00 80 7F`

| 现象 | 先去查哪里 |
|---|---|
| 完全收不到字节 | 波特率（模块出厂 9600，代码写的是多少）→ PA2/PA3 有没有交叉 → GND 共地 → 模块是不是被别的设备占着 → RXNE 使能 → NVIC 使能 |
| 收到乱码 | 波特率不匹配（最常见，两档各试一次）→ 数据位/停止位是不是 8N1 → 干扰（缩短接线、加共地） |
| 偶尔丢字节 | 队列溢出（32 字节太小，加满判断或加大队列）→ ORE 没处理 → 中断优先级太低被长时间阻塞 |
| 一个字节都发不出去（VOFA+ 没波形） | 先看 `BlueTooth_Init()` 是不是在 `Debug_Init()` 之前（顺序反了 CR3 写不进去）→ 再看 DMA 配置 |
| VOFA+ 能收但不显示波形 | 波特率 → 协议要选 **JustFloat** → Y 轴量程点 `Auto` → 帧尾是不是 `00 00 80 7F` |
| 设置页显示「未连接」 | 正常，SPP 只有在程序打开 COM 口时才连；判断标准是打开 COM 口后有没有数据 |
| 手机/电脑连不上模块 | 模块已被别的设备连着（先断开并在设置里取消配对）→ 苹果设备不支持 SPP → Windows 配对密钥存不住（重启、删旧配对、重配） |
| 发 AT 指令没反应 | AT 只能从模块 RXD 有线进入 → 模块必须处于未连接状态（灯闪） |
| 改了波特率不生效 | 断电重启模块 |
| 模块灯不亮 | 查 EN 脚有没有接 3.3 V（灯不亮时必须接）→ 再看供电是不是 3.3 V（不能接 5 V） |

|---|---|---|

### A.4 四处引脚复用冲突（记在墙上）

1. **PA8**：按键 vs TIM1_CH1（左轮 PWM）→ 按键改到 PA0。
2. **PA15 / PB3**：编码器 vs JTAG 的 JTDI / JTDO → 关 JTAG（保留 SWD）+ PB3 串 1 kΩ。
3. **PB13 / PB14 / PB15**：方向脚 vs TIM1 互补输出 → 显式 `TIM_OutputNState_Disable`。
4. **PA9 / PA10**：TIM1_CH2 / CH3 vs K210 串口 → 放弃 CH2/CH3，右轮跳到 CH4。

**规律**：四次冲突里，**两次是「定时器引脚 vs 普通 GPIO」**（PA8、PB13~15），**两次是「外设 vs 外设」**（PA15/PB3 vs JTAG、PA9/PA10 vs USART1）。**查引脚不能只看 GPIO 表，要看「这个脚还能被哪个外设拿去用」。**

## 附录 B 四个模块共通的坑（一页看完）

这一页按「症状」把四份文档里的坑归了类：同一个症状往往在不止一个模块里冒出来，**记住症状，比记住代码更有用**。

| # | 坑 | 长什么样（症状） | 出现在 | 通用解法 |
|---|---|---|---|---|
| 1 | **引脚复用冲突** | 加了新功能，旧功能坏：按键一按电机抖、方向乱、编码器读 0 | 按键（PA8）、电机（PB13~15）、编码器（PA15/PB3） | 加功能前先查附录 A；能换脚就换，不能换就关掉抢脚的外设 |
| 2 | **只写位被读-改-写** | 同一份固件「重新上电就坏」，时好时坏 | 编码器（`AFIO->MAPR` 的 `SWJ_CFG`） | 这种位只用库函数写，禁止读-改-写（读回来是垃圾值） |
| 3 | **先开门、后配参数** | 偶尔丢第一帧、丢字节 | 蓝牙（`USART_Cmd` 放最后）、电机（STBY 最后拉高） | 全部配好，最后一步再使能 |
| 4 | **高级定时器忘了 MOE** | CCR 有值、计数器在转，引脚上没波形 | 电机（`TIM_CtrlPWMOutputs`） | TIM1/TIM8 必须调 |
| 5 | **中断里干重活 / 忘了 `volatile`** | 队列明明有数据却读到空；主循环卡顿 | 蓝牙（head/tail）、按键（对比 `SysTicks`） | 中断只搬字节；中断会改的变量加 `volatile` |
| 6 | **中间结果溢出** | 小数值正常，大数值突然错 | 电机（`duty × ARR` 超 `int16_t`）、编码器（16 位回绕） | 中间结果先转 `int32_t`；回绕用无符号减再转有符号 |
| 7 | **一个变量扛两个职责** | 功能「没反应」，编译不报错、不崩溃 | 按键（`KeyAPastLevel`）、蓝牙（PA2 配的人不用） | 一个状态一个变量；谁用谁配 |
| 8 | **增量读一次就清零** | 第二个使用者永远读到 0 | 编码器（增量缓存） | 一个周期算一次，接口只读不清 |
| 9 | **量纲 / 分辨率被吃掉** | PID 输出变了，执行器没反应 | 电机（曾经 100 级 PWM）、编码器（低速量化 ±6.7 %） | 输出量纲和指令量纲一致；提高分辨率 |
| 10 | **外设时钟没开就写寄存器** | 写了不生效，读回也看不出 | 蓝牙（USART2 时钟开之前写 CR3） | 先开时钟，再配寄存器 |
| 11 | **初始化顺序敏感** | 单独测都正常，一起上电就不行 | 蓝牙（`BlueTooth_Init` → `Debug_Init`）、编码器（关 JTAG → 配 TIM2） | 把顺序写进注释，别靠记忆 |
| 12 | **初始化瞬间的毛刺（「理论没事」）** | 上电时电机「咯噔」一下、偶尔抽动 | 电机（方向引脚先切模式） | 初始化期间先关驱动器（STBY 拉低），最后再开 |
