# 现场跑哪份代码 + 这份代码在干什么

> 写给 2026-11-19 现场用。看完就知道：跑哪个文件、看哪几行数字、哪里容易踩坑。

---

## 一、现场只跑两份

| 文件 | 什么时候跑 | 干什么 | 跑多久 |
|---|---|---|---|
| **`VisualTest\live_scan_test.py`** | 全程主力 | 采数据，每 2.5 秒打一块（8 行） | 一直跑 |
| **`VisualTest\fps_probe.py`** | 只跑一次 | 试 3 个配置，看帧率能不能提 | 3 分钟 |

**`config.py` / `vision.py` / `judge.py` / `main.py` 那四个，现场不跑。** 它们是要上车跑的比赛程序，明天不装车。

### 为什么 `live_scan_test.py` 能单跑

因为它把 `config.py` 里的参数**抄了一份**放在自己第 20–51 行。板子上只放这一个文件就行。

**代价：抄的那份必须和 `config.py` 一致。** 改了 `config.py` 忘了改这里，采回来的数据就对不上车上的程序了。这是最容易犯的错，没有之一。

### 怎么弄到板子上（没有 TF 卡）

MaixPy IDE → 连板子 → 文件 → 打开 `live_scan_test.py` → 点运行。改完第 16 行的组名，再点一次运行。

### ② 几何：算出扫哪 5 行（56–116 行）

**`FOCAL_LENGTH_PX`（59 行）= 80 ÷ tan(93° ÷ 2) = 75.9 像素**
80 是画面半宽（160 的一半），93° 是镜头水平视场角。

**`axial_distance_of_row(row)`（65–71 行）**
"第 row 行的那条光线打到地面，沿着光轴量有多远（米）。"
`vertical` 是那条光线朝下的分量，镜头高 0.2 米 ÷ 朝下分量 = 斜边长度。
光线朝上或水平（`vertical > 0`）就是打到天上，返回 0。

**`horizontal_distance_of_row(row)`（74–81 行）**
同一个点，改成"在车前多远"（地上量的水平距离）。
轴向距离 × 朝前分量 = 水平距离。

**`half_lane_width_of_row(row)`（84–89 行）**
`75.9 × 0.275 ÷ 轴向距离`，就是**半车道宽在这一行占几个像素**。
这就是「深度翻倍、像素减半」那条式子。

**`choose_scan_rows()`（92–112 行）**
在所有行里，把半宽落在 22~62 像素之间的行挑出来，再等间隔取 5 个，从近到远排。

结果（开机时第 360–364 行会打出来）：

| 行号 | 车前距离 | 理论半宽 | 权重 | 1 厘米占几像素 |
|---|---|---|---|---|
| 68 | 0.28 米 | 62 像素 | 3 | 2.25 |
| 60 | 0.35 米 | 52 像素 | 3 | 1.89 |
| 52 | 0.45 米 | 43 像素 | 2 | 1.56 |
| 43 | 0.64 米 | 32 像素 | 2 | 1.16 |
| 35 | 0.96 米 | 22 像素 | 1 | 0.80 |

### ③ 扫一行：`scan_one_row(img, row, row_index)`（120–189 行）

**传进去**：画面 `img`、行号 `row`、这一行是第几行 `row_index`（0=最近）
**返回**：8 个值，顺序固定：中心列、单线标记、合格段数、实测半宽、暗点数、最暗、最亮、段列表

一步步走：

| 步 | 行号 | 干什么 |
|---|---|---|
| 1 | 135–137 | 把第 4 列到第 155 列共 **152 个像素**读进一个列表 |
| 2 | 138–139 | 找这一行最暗、最亮的灰度 |
| 3 | 140–141 | 最亮减最暗 **小于 70** → 这行根本没有线，直接返回"没线" |
| 4 | 142 | 分界线 = 最暗 + (最亮 − 最暗) × **0.40** |
| 5 | 143–170 | 扫过去，连续低于分界线的算一个"黑段" |
| 6 | 159 | 段长 **3~26 像素**才算线（太细是噪点，太宽是阴影或横线） |
| 7 | 163 | 每段的中心列 = （起列 + 止列）÷ 2 |
| 8 | 176–182 | 找到 **两段以上**：中心 = 左右两条线的平均；实测半宽 = (右 − 左) ÷ 2 |
| 9 | 178–180 | 实测和理论差 ≤ **14 像素**，就把理论值往实测挪 **1/16** |
| 10 | 183–185 | 只有**一段**，且在 68 列以左 → 那是外侧线，中心 = 左线列 + 半宽 |
| 11 | 186–188 | 只有**一段**，且在 92 列以右 → 那是内圈线，中心 = 右线列 − 半宽 |
| 12 | 189 | 只有一段但夹在 68~92 之间 → 分不清是哪条，返回 −1（这行作废） |

**举个具体例子**：某一行扫出来两段，20–25 和 140–145。

- 左线中心 = (20+25) ÷ 2 = 22
- 右线中心 = (140+145) ÷ 2 = 142
- 这一行的车道中心 = (22 + 142) ÷ 2 = **82**
- 实测半宽 = (142 − 22) ÷ 2 = **60**
- 这一行对偏差的贡献 = 82 − 80 = **+2**

**68 和 92 这两个数怎么来的**：中心列 80 ± 单线死区 12 = 68 / 92。
一条线如果离画面中心不到 12 像素，程序分不清它是左线还是右线，所以放弃这一行。

### ④ 扫一帧：`scan_frame(image)`（203–294 行）

**传进去**：一张 160×120 的灰度图
**返回**：10 个值：五行结果、偏差、远偏差、找到行数、远处找到行数、弯道信号、触发弯道的行、状态、实际发出的误差、备注

| 步 | 行号 | 干什么 |
|---|---|---|
| 1 | 229–232 | 5 行挨个调 `scan_one_row()` |
| 2 | 234–236 | 在预览画面上画扫描线和圆心（只是显示，方便你看着调） |
| 3 | 239–243 | **弯道信号**：见下面单独讲 |
| 4 | 245–255 | 每行算出 (中心列 − 80)，乘权重累加 |
| 5 | 257 | 偏差 = 加权和 ÷ 权重和 |
| 6 | 258–259 | 远偏差 = 只用**最远两行**（第 4、5 行，权重 2 和 1）同样算 |
| 7 | 262–270 | 一行都没找到 → 10 帧内沿用上次，超过 10 帧降档 |
| 8 | 273–287 | 按 `judge.py` 的规则算出"实际会发出什么" |

**弯道信号（239–243 行）—— 这就是"直角/锐角识别"的全部，只有 5 行**

```
条件一：这一行"只剩外侧"（标记 = 1）
条件二：只允许最近两行（row_index ≤ 1）触发
条件三：推出来的左线列号在 0 ~ 49 之间（小于 50）
三条同时成立 → 弯道信号 = 1
```

**注意条件二**：只有最近两行能触发。也就是说，这个信号是**车已经压到弯口上**才出现的，不是提前看到的。这就是你说"估计不来直角和锐角"的地方——不是几何错了，是这个判据本身就只在最后一刻才亮。

**偏差怎么合成**：五行偏差 +10、+8、+4、0、−2，权重 3、3、2、2、1

```
(3×10 + 3×8 + 2×4 + 2×0 + 1×(−2)) ÷ (3+3+2+2+1)
= (30 + 24 + 8 + 0 − 2) ÷ 11
= 60 ÷ 11
= +5
```

**"实际发出"和"偏差"不是一回事**（272–294 行）：

| 步 | 干什么 |
|---|---|
| 先校准：偏差 × 1.0 − 0 | 校准值现在是 0 |
| 弯道顶：弯道信号 = 1 且 偏差 < 8 → 偏差直接改成 **40** | 强行打满方向 |
| 判档：远偏差绝对值 < 10 → 状态 0；< 22 → 状态 1；否则 2 | 决定基速 25 / 20 / 15 |
| 远处一行都没找到 → 至少状态 1 | 前面看不见了，先减速 |
| 弯道信号亮了 → 直接状态 2 | 最慢 |

### ⑤ 打印一块（315–339 行）

一块 8 行，长这样：

```
===== 采样#3  组=1 直道正中  运行 7.5 秒  fps 19.2  用时 12.4 ms =====
行  68 | 暗 25 亮200 | 段 16-21* 139-144*          | 中心   79 | 两条 | 实61 理61
行  60 | 暗 28 亮195 | 段 18-22* 136-141*          | 中心   78 | 两条 | 实59 理52
...
偏差 +1 | 远偏差 -3 | 弯道 0 | 状态 0 | 找到 5/5 | 远 2/2
实际发出 +1
```

| 位置 | 名字 | 什么意思 | 明天怎么用 |
|---|---|---|---|
| 第 1 行 | 采样号、组名、运行时长、**fps**、**用时 ms** | fps 是实际帧率，用时是 `scan_frame` 花多少毫秒 | fps 应该 19.2；用时如果超过 30 ms 就是太慢 |
| 2–6 行 | `暗` `亮` | 这一行最暗、最亮灰度 | 对比度 < 70 就认不出线 |
| | `段` | 所有黑段的起止列，带 `*` 的是被当成线的 | **看这里判断"这一行到底看到了什么"** |
| | `中心` | 这一行算出来的车道中心列，`---` = 没算出来 | |
| | `两条` / `只剩外侧` / `只剩内圈` / `没线` | 单线标记 | **弯道就靠这一列看** |
| | `实61 理61` | 实测半宽 / 算法当前用的半宽 | **两个数差 ≤3 说明安装参数对** |
| 第 7 行 | `偏差` `远偏差` `弯道` `状态` `找到` `远` | 五行合成后的原始测量结果 | 这是要抄回表格的主力 |
| 第 8 行 | `实际发出` | 加上弯道顶、丢线沿用之后，真正会发给 STM32 的那个数 | 后面可能带 `<<< 弯道顶生效` |

### ⑥ 主循环（342–400 行）

开机（346–349 行）：`sensor.reset()`、灰度、QQVGA（160×120）、丢掉前 2 秒的画面（等自动曝光稳定）。

开机表（351–369 行）：焦距、镜头参数、分界线规则、5 行行号表、判档阈值。

然后死循环（377–400 行）：

```
拍一张 → 计时 scan_frame → 累加用时和帧数
→ 到了 2500 毫秒 → 打一块 → 计时清零
```

帧率是这么算的（397 行）：`这一窗口的帧数 × 1000 ÷ 这一窗口的毫秒数`。

## 四、现场操作顺序

1. 上电，等开机表打完（约 2 秒，十几行）
2. **先核对开机表**：五行行号是不是 68 / 60 / 52 / 43 / 35，焦距是不是 75.9
3. 车摆到第 1 组位置，把第 16 行改成 `GROUP_NAME = "1 直道正中"`，运行
4. **等 8 秒**（正好 3 块），**板子不许动**，截屏
5. 换位置 → 改组名 → 重新运行 → 再等 8 秒 → 截屏
6. 七组采完，再跑一次 `fps_probe.py`（3 个配置，一次一个）

## 六、三个最容易犯的错

1. **改了 `config.py` 忘了改 `live_scan_test.py` 第 20–51 行** → 数据对不上车上程序
2. **截屏的时候板子在动** → 数据作废，白跑一趟
3. **`GROUP_NAME` 忘了改** → 回去分不清哪张截图是哪组
