**帧率的两个铁律（实测，别再试别的）：**

1. **帧率是"模式"的属性，跟像素多少无关**：80×60 / 160×120 = 19.23；320×240 / 640×480 = 38.46。

2. **单缓冲 + 任何处理都会砍半**：单缓冲+处理 20ms = 19.23；双缓冲+处理 20ms = 38.46。

**无效方向（已排除，别再试）**：`freq=27MHz`、`set_framerate()`、单独开 `dual_buff`（空转时无变化）、寄存器读写（`sensor.__read_reg` 全返回 0，不可用）。

### 3.4 阈值规则（全部按距离/比例自动算，不手填）

| 参数 | 式子 | 说明 |
|---|---|---|

| 分界线 | `最暗 + (最亮−最暗) × **0.55**` | **2026-11-19 从 0.40 抬上来**：0.40 时远处胶带只露出中间一条芯，76 厘米处左线只剩 2 个像素，84 厘米以后一个都不剩。抬到 0.55 后 9 行全部认得出。**注意：这个数越大，被判成"黑"的像素越多；超过 0.65 地面会开始变黑，别超。** |
| 并段 | 相邻黑段之间能填的洞 ≤ 线宽 20%（最少 2 像素） | 填反光白点 |

### 3.5 扫描窗口（ROI）

```python
span = 半宽 + ROI_MARGIN_PX(**15** = 30 像素)
列范围 = 上一帧的车道中心 ± span，夹在 [8, 311]
```

- **2026-11-19 从 40（=80 像素）收到 15**：留 80 会把场地右侧的墙根（240~311 那一大片）罩进窗口，远处 5 行要么被当成"太宽"丢掉、要么和右边的线错配
- **收到 30 之后**：每帧读像素 2355 → 1455（少 38%），**扫描时间 25 ms → 17 ms，帧率 23 → 38**
- **兜底**：窗口内一条线都没找到 → 退回全宽重扫这一行（**这条兜底如果频繁触发会明显拖慢，看到"用时"超过 20 ms 就是它在干活**）
- **窗口跟着偏差走**：偏差 +10 时窗口右移


### 3.6 输出换算

- 内部全在 **320 尺度**算
- **发出去前 `÷2`** 回到 160 尺度 → **STM32 侧一个数都不用改**
- 顺序不能反：**先除再夹 ±127**（先夹会把范围砍到 ±63）

## 10. 今天的核心教训（别再犯）

1. **报出来的帧率是"空转帧率"，带负载的才作数。** 19.2 不是相机的极限，是单缓冲 + 处理的代价。
2. **配对不能取最左+最右。** 画面里任何杂物都会把右线挤掉。
3. **绝对像素阈值出不了近处。** 线宽、容差、段长全部要按距离/比例算。
4. **寄存器读不出来就别拿它当证据。** `sensor.__read_reg` 全返回 0，那套 HTS×VTS 理论从头到尾没证据，浪费了一天。
5. **IDE 的"数据传输"会吃掉 5 ms。** 开着 28 ms / 20 帧，关掉 23 ms / 38 帧。
6. **布面褶皱会变高度。** 喷绘布要铺平、四角压住。

## 11. 弯道状态机（已写进 `live_scan_test.py`）

### 11.1 分工（用户 2026-11-19 定）

- **近四行 → 偏差 → 方向环 P 控制**（贴线）
- **九行特征 → 状态机只分三档**：直道 30 / 预警 20 / 进弯 15
- **弯道由状态机用 if 强行接管方向**（用户明确要求，不是几何判弯）
- **不搞几何判弯**：九行推不出整条路，算力也撑不住逆透视（见 §13）

### 11.2 用的特征只有一个：**好行个数**

**定义：从最近那行(129)往远数，连续有几个「两条都在」。**

| 图案 | 好行个数 |
|---|---|
| `#########` | 9 |
| `########L` | 8 |
| `######LLL` | 6 |
| `######xxx` | 6 |
| `xxxxxxxxx` | 0 |

**为什么不是「数丢了几行」（这条很重要，别走回头路）**

实测模拟（车按 0.84 m/s 往前开），**数 L 是不行的**：

| 车距拐点 | 图案 | L 的个数 | 好行个数 |
|---|---|---|---|
| 1.05 m | `#####LLLL` | 4 | 5 |
| 0.92 m | `###LLLLLx` | **5** | 3 |
| 0.77 m | `###LLLxxx` | **3** | 3 |
| 0.57 m | `#LLLxxxxx` | **3** | 1 |
| 0.36 m | `LLxxxxxxx` | **2** | **0** |

**原因**：远端那些 `L` 会被 `x` 顶掉（卡在锐角尖上和扫出锐角都是 `x`），
所以 L 的数量不增，只往近处挪。

**好行个数才是单调的：9 → 7 → 4 → 1 → 0。**
而且它天然抗光照：光照坏的是远处的行，近处那几行还是好的。

### 11.3 两层滤波（代价约 10 微秒，占 17.8 ms 的 0.06%）

1. **下降限速**：一帧最多降 `SM_GOOD_MAX_DROP = 2` 行
   → 挡「反光打在近处，9 一次掉到 0」
   → 真弯一帧只降 1 行，限速完全不影响它
2. **最近 5 帧取最小值**
   → 挡 ±1 回退
   → 出弯时窗口滑过去自动恢复，不会卡住

### 11.4 真假判据（抗光照）

进弯（状态 0/1 → 2）要求：**坏行里至少有 `SM_MIN_SINGLE = 1` 行的标记是 `L`（只剩左线）**。

- **真弯**：内圈线拐走了，外圈那条还在 → `L`
- **光照 / 反光**：两条都认不出来 → `x`

**分不清的时候：只降一档减速，绝不接管方向。**

理由（两害相权）：
- 把光照当弯 → 直道上强行往右打死 → **必死**，而且没信息能救
- 漏判一个弯 → 偏差还在（近四行还可靠）→ **还能靠偏差硬拐，还有机会**

**注意**：这个挡板要一直有效到进弯为止（`sm_state < 2`），
只在状态 0 生效的话，进了状态 1 就绕过去了。

### 11.5 方向接管（方案 A + 来不及强制）

状态 2 时：

```
偏差 < 0          → 原样发（让它先往左回中，别硬顶出赛道）
0 ≤ 偏差 < 30     → 补到 30
偏差 ≥ 30         → 原样发（已经更狠了）
```

**但**：连续 `SM_LATE_FRAMES = 10` 帧（约 260 ms）偏差还是负的
→ 判定「来不及回中」→ **改为强制补到 30**，不再等。
同时日志打 `<<< 弯中一直偏右没回中，怀疑来不及（考虑降速）`。

**出弯防抖期间**（证据已消失但状态还没退回来）：**只减速，不补方向**。
否则车都回直道了还在往右顶（实测会多顶 130 ms ≈ 11 厘米）。

**方向接管用的是【没滤波】的原始好行数**：滤波为了稳，速度要稳；
方向要跟得快，不然出弯松手太晚。

## 12. STM32 侧确认过的（2026-11-19 查代码，别再记错）

- **方向环是 PD，不是 PI**：`PID_LineLoop_Init(pid, Kp, Kd, max, min)`，**没有 Ki**
- `PID_L_Calc` 输出 = `Kp*err + Kd*(err - err_last)`，首周期有对齐，避免 D 项冲击
- **蓝牙可调**：`0x05` 方向环 Kp、`0x06` 方向环 Kd、`0x07/0x08/0x09` 三档基速、`0x0A` 启停
- **`turn` 被夹到 ±base_speed**（`Service.c` 345~348 行）→ 两轮目标不会变负
- 偏差 40、Kp 0.175 → `turn = 7`：
  - 弯中 base 15 → 左 22 / 右 8（电机上限 37，很宽松）
  - 直道 base 30 → 左 37 / 右 23（左边正好顶住 37）
  - **真正吃紧的是直道满舵，不是弯道**
- `Service.c` 有死区：`|偏差| ≤ 3` 直接当 0

## 14. 这一轮新增的教训

1. **单行判断不了对错，序列才能。** 九行连起来 + 时间，才能回答「是不是弯、多近、真的假的」。
2. **「没看见」和「看见它没了」必须分开。** `x` 是没看见，`L` 是少了一条。把它们混在一起，
   光照会冒充弯道。
3. **误判和漏判不是一样糟。** 误判（把光照当弯）= 直道上打死方向 = 必死；
   漏判（把弯当没事）= 还能靠偏差硬拐 = 还有机会。**设计要偏向漏判。**
4. **数据要按「哪一个量在变」来选，不按直觉。** 数丢的行看着直观，实际只增不减；
   数好的行才单调。
5. **模拟能替代一部分路测。** 上面这些结论（144 种拐角、逐帧推进）都是在电脑上算的，
   一次没上板。
6. **先查代码再下结论。** 我以为方向环是 PI、加 D 要改代码，查了才发现它本来就是 PD，
   Kd 还有现成的蓝牙指令。

### 15.6 暴露出的真问题：近处偏差变负（已改）

```
75 cm  +3
60 cm  +1
45 cm  −10
15 cm  −52
```

**原因**：只剩左线时，程序用「中心 = 左线 + 半宽」推。车越接近弯道，左边那条线在画面里越靠左，
推出来的中心反而越小 → **偏差变负 → 程序以为该往左打**，正好反了。

而"方案 A"规定「偏差 < 0 就不补方向」→ **在最该打方向的时候不打。**

**改法**：`SM_LATE_FRAMES` 10 → **3**。原来要连续 260 毫秒为负才强制，15 档下那是 11 厘米；现在 78 毫秒就抢。

### 15.7 ⚠️ 必须知道的坑：**静态测试时保险丝会误烧**

```
t≈24 秒   状态 2
t≈54 秒   状态 1    ← 车根本没动
```

保险丝按「状态 2 期间走了多少米」记账，**它假设车在以 15 档正常行驶（0.42 米/秒）**。
车停着不动，它照样每秒记 0.42 米 → **6 秒就"走"了 2.5 米 → 烧断 → 封锁。**

**所以静止测量时：**
- **图案、好行、偏差** → 可信
- **状态、发出** → 只有每个停点前 6 秒可信

**这不是 bug。** 但它提醒一件真事：**实车比赛时如果车被卡住不动，保险丝会在 6 秒后解锁。**

## 17.4 关键补充：手推比实车慢 15 倍（用户 09:40 提出，已算清）

### 手推速度反推

好行从 9 掉到 0 花了 15.3 秒。这段路**物理上必然走多远**是几何定死的：

```
最远那行看 112.1 厘米
最近那行看  27.7 厘米
过渡距离 = 112.1 − 27.7 = 84.4 厘米
```

所以手推速度 = 84.4 ÷ 15.3 = **5.5 厘米/秒**。

### 实车速度对比

| | 速度 | 走完 84.4 厘米 | 多少帧（36 帧/秒） |
|---|---|---|---|
| 手推 | 5.5 厘米/秒 | 15.3 秒 | 约 550 帧 |
| 20 档 | 56.2 厘米/秒 | 1.5 秒 | 54 帧 |
| **30 档** | **84.3 厘米/秒** | **1.0 秒** | **36 帧** |
| 15 档（弯里） | 42.2 厘米/秒 | 2.0 秒 | 72 帧 |

- 九行实/理 半宽全部对上 —— 纯几何
- 好行 9→0 的**顺序**（最远先坏、逐行往近处吃）—— 由 84.4 厘米这条距离决定
- 丢 3 / 丢 5 / 丢 7 三个门槛 —— 门槛是**行数**不是时间
- 弯间能恢复 —— 由距离决定

### 受影响（时间够不够，全部待实车）

| 项目 | 手推时 | 实车 30 档 |
|---|---|---|
| 状态机确认 2 帧 | 0.6 厘米 | 4.7 厘米 |

## 19.2 下午的三个关键发现

### 发现一：帧率是 36，不是 10（我之前算错了）

日志里 `已跑 X 秒` 的间隔是 **0.100 秒**，但那不是帧周期 —— 是 `PATTERN_LOG_MIN_MS = 100`（图案变了才打印，最少隔 100 毫秒）。

日志里每 2.5 秒打一块采样，那块里写着真实数据：

```
===== 采样#3  组=3 锐角弯  运行 20.5 秒  fps 36.5  用时 16.5 ms =====
```

**496 个采样统计：fps 中位 36.1（每帧 27.7 毫秒），处理用时中位 16.6 毫秒。**

所以：
- 每帧 27.7 毫秒，**不是 100 毫秒**
- 30 档 84.3 厘米/秒 → 每帧走 **2.3 厘米**（不是 8.4）
- Kd 0.53 ÷ Kp 0.231 = 2.29 帧 = **64 毫秒**提前量（不是 230）
- 视觉超时 330 毫秒 = **12 帧**（很宽松）

### 发现二：视觉「盲开」会冒充状态 2（起跑线后转圈的元凶）

`live_scan_test.py` 原来有一行：一行线都找不到、持续超过 10 帧 → **报状态 2**。

早上这没问题（状态 2 只表示降速）。但下午 STM32 把状态 2 当成「准备转 90 度」的触发信号 → **相机一瞎，车就转圈**。

实测：Kp=Kd=0 时车照样在起跑线后约 5 厘米就转 —— 证明转的不是 PD，是这条盲开分支。

**已改成报状态 1（降速），不再冒充弯道。**

### 发现三：相机一直是自动曝光

脚本里只做了 reset / 灰度 / QVGA / skip_frames，**没有关自动曝光和自动增益**。

后果：换个场地亮度基准变了，所有按亮度算的分界线跟着偏 —— 这就是「参数一换场地就得重调」的根子。

## 20.1 原话（按赛道上行驶顺序重新排列，内容没改）

1. **起跑线那一段开头时有微弱画龙，此后不再画龙。**
2. **直角弯**：似乎**提前转弯**，然后**压线**，之后**过度掉头**了，掉头回来继续跑。
3. 从**钝角弯处往锐角弯开**的时候，**画龙严重**。
4. **在弯道前提前转弯**。
5. 压线过的**锐角弯**：踩在线上过弯，过完之后**纠正**了回来。

## 20.2 初步线索（**下次验证用，不是结论**）

| 观察 | 可能的原因 | 怎么验证 |
|---|---|---|
| ① 起跑线开头微弱画龙，之后不画 | 不是稳态问题。指向**启动瞬间**：速度环从 0 起步的过渡，或第一帧视觉的基线没对齐 | 看日志开头 1~2 秒的偏差序列 |
| ② 直角弯提前转 + 压线 + 过度掉头 | 三选一：**(a)** `TURN_ARM_CM` 偏小（该晚点转）；**(b)** `TURN_DIFF_TARGET` 偏大（转多了）；**(c)** 转完没有视觉收尾（那时 `LIMIT_LINE_ERR_MAX` 还是 20） | 先量**实际转角**，再量**开始转的位置**，两个分开调 |
| ③ 钝角弯→锐角弯之间画龙严重 | 如果那段是**刚出弯的恢复段**，说明交回视觉后 PD 在振荡；如果是**长直道**，说明 Kp/Kd 本身不行 | 看日志里那段的偏差摆动周期和幅度 |
| ④ 弯道前提前转弯 | `TURN_ARM_CM` 偏小，或视觉报弯点比预期早 | 同上，先量位置 |
| ⑤ 锐角弯压线过、出弯后纠正回来 | **这是好消息** —— 说明"编码器粗转 → 视觉收尾"这条链在工作 | 保留，不要动 |
| ⑥ 没能过钝角弯 | ⚠️ **设计层面的新发现**：钝角弯按设计**不触发转向**（只降速，靠 PD 硬拐）。如果它过不去，说明钝角弯**需要真实转向** | 单独测钝角弯：日志里看它到底有没有报状态 2 |

## 23.3 陀螺仪（现场第一件要做的事）

**模块是 ICM-20602，不是 MPU6050。** 三处差异已在代码里处理：
1. `WHO_AM_I`（0x75）应该读回 **0x12 = 十进制 18**（MPU6050 才是 0x68=104）
2. 上电后要约 **100 毫秒**才开始应答（已加延时 + 重试 5 次）
3. 唤醒写 `PWR_MGMT_1 = 0x01`（切 PLL 时钟）；若角速度一直读 0，改回 `0x00` 再试

**接线：**

| 模块 | 主控 |
|---|---|
| VCC | 3.3V |
| GND | GND |
| **SCL / SPC** | **PB0** |
| **SDA / SDI** | **PB1** |
| **SAO / SDO** | **GND**（地址 = 0x68） |
| CS | 悬空（= I2C 模式） |
| INT / FSY | 不接 |

**怎么测**：上电时长按按键进台架模式，VOFA+ 看五个通道：

| 通道 | 含义 | 正常值 |
|---|---|---|
| ch1 | WHO_AM_I | **18**（或 104） |
| ch2 | Z 轴原始读数 | 静止时固定值附近小幅抖 |
| ch3 | 累计角度（度） | **手转 90° 应该走到 ±90 左右** |
| ch4 | 零偏 | 上电 1 秒后自动算出 |
| ch5 | 读失败次数 | 一直 0 |

**保险**：模块不在/读不到 → `Gyro_Ok=0`，后面全跳过，**不影响现在跑车**。
**软件 I2C**（PB0/PB1），每一位固定时钟数，**不会卡死**；硬件 I2C 那套没碰。

## 23.13 2026-11-21 18:10 手推标定永久取消 + `CM_PER_COUNT` 定为理论值

### 从此不许再提

### `CM_PER_COUNT` 怎么定

**保持理论值 `0.01402` 厘米/计数，不改。**

- 霍尔 13 线 × 4 倍频 = 52 计数/电机圈
- 减速比 1:28 → 1456 计数/轮子圈
- 轮径 65 毫米 → 周长 π × 6.5 = 20.42 厘米
- 20.42 ÷ 1456 = **0.01402**

理论值不依赖任何一次手推或卷尺判点，本来就被判定比手推值可信（手推值 0.01610 高 14.8%，用户当时已确认那次不准）。所以这次取消手推，**没有丢掉任何可靠信息**。

### 这个常数不准会怎样（为什么可以不管它）

`Turn_ThresholdCm`（200 / 350 / 350）在代码里**只当一个窗口用，不是精确尺子**：

| 用途 | 代码位置 | 刻度错 5% 的后果 |
|---|---|---|
| 判「视觉报的弯是不是假的」 | `fabsf(Corner_SegMileage − 阈值) > 55` | 350 那个判断点挪 17.5 厘米，仍在 ±55 窗口内 |
| 报弯后还要走多少才开转 | `TURN_ARM_CM = 20` 厘米 | 20 → 21 厘米，挪 1 厘米 |

**真正决定「什么时候开始转」的是「视觉报弯之后再走 20 厘米」，不是里程表。** 里程表只负责「这个弯是不是真的」和「该转多少度」（按 `Corner_Index` 查表）。所以刻度偏差只会让转弯点前后挪几厘米，不会指错弯。

- 三个数 ≈ **200 / 350 / 350** → 常数对
- 三个数都同比例偏大 15%（230 / 402 / 402）→ 常数小了 15%，一次改全对

不需要为这件事单独安排实验。

## 23.14 2026-11-21 18:55 语音模块协议定案 + 旧接口为什么不能用

**用户给的帧（3 个字节）：**

- 启动 `AA 01 55`
- 停车 `AA 02 55`

**按键保留**：用户明确「按键控制启停功能我不打算删」。现在是按键和语音两条路并存，都落到 `CarRun_Set()`。

### 旧接口为什么不能用

`BSP/Src/Voice.c` 原来的中断是这样的：

```c
uint8_t data = USART_ReceiveData(USART3);
Voice_Cmd = data;              // 来一个字节就覆盖一次
```

一帧有 **3 个字节**，最后进来的永远是帧尾 **0x55**。所以主循环每次取到的都是 0x55：

- 说「启动」→ 取到 0x55
- 说「停车」→ 取到 0x55
- 上层判断 `== 0x01` / `== 0x02` **永远不成立**，语音等于没接

结论：**接口名字和返回值设计是对的（0x01 / 0x02），坏在「没有按帧收」**。

### 新协议（写在 `MID/Protocol.c` + `Protocol.h`）

和视觉、蓝牙共用帧头 `0xAA` / 帧尾 `0x55`，但跑在**另一个串口**（USART3，PB10/PB11），三方互不干扰。

**两种帧，靠指令字节的大小区分，不用额外字段：**

| 类型 | 结构 | 例子 |
|---|---|---|
| 短帧（无参数） | `AA \| 指令(0x01~0x7F) \| 55` | `AA 01 55` |
| 长帧（带参数） | `AA \| 指令(0x80~0xFF) \| 长度 n \| n 个字节 \| 55` | 留给以后 |

**指令表：**

| 指令 | 含义 | 帧 |
|---|---|---|
| `0x01` | 启动 | `AA 01 55` |
| `0x02` | 停车 | `AA 02 55` |
| `0x03~0x7F` | **空闲，以后加新功能** | 在 `Protocol.h` 加一行 `#define` 即可，解析代码不用动 |
| `0x80~0xFF` | 长帧（带参数） | 解析已经写好，带最多 8 个参数（`VOICE_PAYLOAD_MAX`） |

**为什么这样留余地**：加一个「暂停」「报第几号弯」这种只带一个指令的，改一行 `#define`；万一以后要「把参数从语音端发下来」，长帧的路已经铺好，`Protocol.c` 一个字都不用改。

### 抗干扰规则

- 任何时刻又收到 `0xAA` → 当成新一帧的开头，重新收
- 帧尾对不上 → 整帧作废，回等帧头
- 长帧的「长度」大于 8 → 整帧作废，**不会越界写内存**

| 文件 | 改了什么 |
|---|---|
| `MID/Inc/Protocol.h` | 加语音段：指令表、`VoiceCommand_t`、两个函数声明 |
| `MID/Src/Protocol.c` | 加语音状态机 `Protocol_VoiceParse()` + 取指令 `Protocol_GetVoice()` |
| `BSP/Src/Voice.c` | 中断改成把字节喂给 Protocol；`Voice_GetCommand()` 改成转发 |

**编译：0 错误 0 警告，Code=12444，RW-data=236（比之前多 24 字节，就是语音那两个缓冲区）。**

### 启动门禁（和按键同一条）

语音说「启动」时也要查 `Vision_EverSeen`：视觉没起来就先忽略，不启动。
理由和按键那条完全一样 —— 免得「说了启动、人走开，10 秒后车突然窜出去」。

停车**不需要门禁**：停车是安全方向，任何条件下都该生效。

### 现场怎么验（两步）

1. **先用串口助手**：接 USB-TTL 到 PB11（RX），波特率 **9600**，发十六进制 `AA 01 55` → 车应该启动（要先让视觉跑起来，否则被门禁挡掉，灯会快闪）；再发 `AA 02 55` → 停车
2. **再上语音模块**：说「启动」「停车」

### 两个必须核对的硬件点

1. **波特率**：代码里是 `VOICE_UART_BAUD 9600`（`BSP/Src/Voice.c` 顶部）。模块说明书写 115200 的话，只改这一行。波特率不对的表现是**完全没反应**（收到的是乱码，永远凑不成合法帧）
2. **接线要交叉**：模块 TX → 单片机 **PB11**；模块 RX → 单片机 **PB10**；共地
