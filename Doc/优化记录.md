# 第 0 节　仓库建立之前（无提交记录）

## 0.1 PID 输出限幅全为 0

**现象**　编译通过、电机有供电、PWM 也在输出，但上电后车**一动不动**。

**原因**　初始化时把输出的上下限传成了 0：

```c
PID_VelocityLoop_Init(&pid_v_left, 0, 0, /*上限*/0, /*下限*/0);
```

而 `PID_V_Calc()` 末尾有限幅语句，任何输出都会被压到 0：

```c
if (output > pid->output_max) output = pid->output_max;   // 永远是 0
```

**改法**　速度环上下限改为 `±MOTOR_DUTY_FULLSCALE`（±1000‰，与占空比量纲一致）；方向环改为 `±Speed_Straight`。

**现状**（可在 `Service.c` 第 55~57 行核对）

```c
PID_VelocityLoop_Init(&pid_v_left,  0, 0,  (float)MOTOR_DUTY_FULLSCALE, -(float)MOTOR_DUTY_FULLSCALE);
PID_VelocityLoop_Init(&pid_v_right, 0, 0,  (float)MOTOR_DUTY_FULLSCALE, -(float)MOTOR_DUTY_FULLSCALE);
PID_LineLoop_Init    (&pid_l,       0, 0,  Speed_Straight,              -(float)Speed_Straight);
```

**为什么值得记**　这是全工程最隐蔽的一个 bug——代码没错、编译没错、就是不动。排查时先怀疑硬件，实际上问题在参数初始化。

## 0.2 按键从 PA8 挪到 PA0

**原因**　`KEYA_PIN` 最初定义在 **PA8**，而 PA8 同时是 **TIM1_CH1（左轮 PWM）** 的输出脚。按键初始化把 PA8 配成上拉输入，会覆盖掉 PWM 复用功能。

**改法**　按键挪到 **PA0**，PA8 专供 TIM1_CH1。

**证据**　代码里保留了当时的结论：

```c
// Control/BSP/Src/Key.c:5
#define KEYA_PIN  GPIO_Pin_0   // 原为 PA8，与左轮 PWM(TIM1_CH1) 撞脚，已挪到 PA0
```

---

## 0.3 OLED 整体移除

**现象**　接上 OLED 显示后，电机出现周期性顿挫和啸叫。

**原因**　OLED 用软件 I2C，全屏刷新一次约 **5–10ms**，而内环周期就是 5ms。刷新那一拍直接把控制周期拉长一倍以上，速度环等于「走走停停」。

**改法**　**删掉整个 OLED 模块**，状态信息改由两条路径表达：

- 板载 LED（PC13）—— 现场肉眼可见，见第 7 节
- 蓝牙 / VOFA+ —— 需要细节时接上看，见第 3 节

**结果**　5ms 内环恢复确定性；PB8 / PB9 两个引脚释放，目前全工程无引用。

> 这是「宁可少一个显示，也不能让控制周期抖」的典型取舍。后来做的 PC13 状态灯，本质上是它的替代品。

## 0.4 浮点误用 `abs()` 与编译期错误

| 问题 | 现象 | 原因 | 改法 |
|---|---|---|---|
| `abs()` 用于 float | 方向环在部分误差下输出异常 | `abs()` 是**整型**函数，传 `float` 会被隐式截断成 `int`，小数位丢失 | 改 `fabsf()`，并补 `#include <math.h>` |
| `USART_Cmd(...)` 缺分号 | 编译不通过 | 笔误 | 补分号 |

**现状**　`PID.c` 第 3 行为 `#include <math.h>`，第 45 行使用 `fabsf(pid_v->err)`。

## 1. `33caf6e` 初始导入：确立分层

**内容**　101 个文件，包含 STM32 控制工程、K210 MaixPy 视觉工程、设计说明文档。

**分层结构**

```
User/           main 与中断入口
AppLayer/       业务调度（Service）
MiddleLayer/    协议解析（Protocol）
AlgorithmLayer/ PID
HardwareLayer/  电机、编码器、串口、按键、蓝牙、语音、看门狗、状态灯
SystemLayer/    1ms 时基
DebugLayer/     VOFA+ 输出
Library/ Start/ ST 标准外设库与启动文件
```

> **2026-11-21 重排后（提交 `67122c4`）**：下面五个目录已经合并成三层，每组再分 `Src/`（源文件）和 `Inc/`（头文件）——
>
> - `APP/` ← 原来的 `AppLayer/`（Service）
> - `MID/` ← 原来的 `MiddleLayer/` + `AlgorithmLayer/`（Protocol、Delay、PID）
> - `BSP/` ← 原来的 `HardwareLayer/` + `SystemLayer/` 的 SysTimer
> - `DebugLayer/` 原地不动（调试件，`DEBUG_ENABLE` 可整块关掉）
>
> **源码零改动**：所有 `#include` 只写文件名，靠头文件搜索路径解析。
> 上面那张图保留了当时的原样，作为历史记录。

**为什么这样分**　依赖方向单一：上层可以调下层，下层**不允许**反向 `include` 上层。这条约束后面所有改动都没有破坏，是整个工程还能维护的根本原因。

## 2. `49b70e3` 调度上移到 Service 层 + 可选看门狗

**问题**　`main()` 里原来有一份 timeslice 结构，调度逻辑和业务混在一起——每加一个任务都要改 `main.c`。

**改法**

- `main()` 变成 14 行循环，每次只取**一个共享时间戳**，交给四个任务：

```c
while(1)
{
    ServiceTask_Idle();
    uint32_t timestamp = Service_Clock();
    ServiceTask_5ms(timestamp);
    ServiceTask_10ms(timestamp);
    ServiceTask_30ms(timestamp);
    ServiceTask_100ms(timestamp);
}
```

- 每个 `ServiceTask_XX` 自己管自己的周期闸门（`curr_ms - task_last_xx < 周期` 就 `return`）
- 新增 `WatchDog` 模块：IWDG，LSI/64，重装值 625（约 1s），由 `WATCHDOG_ENABLE` 控制，**默认关闭**

**效果**　加任务只改 `Service.c`，`main.c` 从此没再动过。

**为什么留一个开关**　1s 内任何阻塞都会触发复位。赛前没在实车验证过最坏情况，所以先关着——模块留好，赛后打开。

## 3. `976d708` 调试输出改二进制帧

**问题**　原来用 `printf` + `%.1f` 发文本，依赖 MicroLIB，格式化耗时随浮点位数变化，不可控。

**改法**　改用 VOFA+ 的 **JustFloat** 协议，定长 24 字节：

```
5 个 IEEE-754 小端 float（20 字节） + 帧尾 0x00 0x00 0x80 0x7F
通道顺序：左目标 / 左实际 / 右目标 / 右实际 / 视觉误差
```

发送走 `DMA1_Channel7` → USART2。

**附带改动**　`Debug_log()` 改成无条件调用，车停着的时候波形也照发。

**效果**　彻底摆脱 `printf`；100ms 一帧，115200 下约 2ms 发完，几乎不占 CPU。

## 4. `3215a30` 编码器采样顺序

**现象**　速度环响应偏迟钝，内环有额外相位滞后。

**原因**　`Encoder_GetDeltaLeft/Right()` 返回的是**上一次** `Encoder_Update()` 算出来的增量。原代码先读、后更新：

```c
actual_left = (float)Encoder_GetDeltaLeft();   // 拿到的是上个 5ms 的数据
Encoder_Update();                              // 这时候才更新
```

等于给速度环喂了一份「过期 5ms」的测量值，白送一拍延迟。

**改法**　把 `Encoder_Update()` 提到读取之前。

**附带**　删掉 `Debug.c` 里一段已经过时的帧格式注释。

**效果**　内环相位滞后减少一个控制周期；在这类串级控制里，内环延迟直接决定带宽上限。

## 5. `85ae41e` 协议重构 + 手机在线调参（最大的一次改动）

**问题**

1. `Protocol.c` 直接暴露全局变量，中断和主循环共享且没有任何保护
2. 蓝牙接收在主循环里同步轮询，会阻塞
3. 调一个 PID 参数要改代码 → 编译 → 烧录 → 试车，单次几分钟

**改法**

| 项 | 做法 |
|---|---|
| 数据封装 | 对外只暴露 `VisionData_t` / `BtCommand_t` 结构体和 `Protocol_GetVision()` |
| 临界区 | 读取时保存/恢复 PRIMASK，保证结构体读到的是完整一帧 |
| 蓝牙接收 | USART2 增加 32 字节环形缓冲，中断只负责存字节 |
| 参数校验 | 两层：先拦 NaN / Inf，再按参数类型做上下限 |
| 可调参数 | 基速与 PID 增益改为**运行期变量** |
| 差速限幅 | 改为跟随当前基速，保证左右轮目标速度不为负 |
| 代码组织 | `Service.c` 拆成 6 个命名 handler |

**效果**　调参从「改代码 → 编译 → 烧录 → 试车」变成「手机发一帧 → 立刻生效」，单次从分钟级降到秒级。这是后面能快速试出 PID 参数的前提。

## 6. `c0978bf` 全工程转 UTF-8

**现象**　GitHub 上所有中文注释显示为乱码。

**原因**　源文件是 **GBK** 编码，而 GitHub 一律按 **UTF-8** 解码。

**改法**

- 21 个 `.c/.h` 转为 **UTF-8 with BOM**（带 BOM 是为了让 Keil 和 VS Code 都能自动识别）
- `Key.c` 原本是 UTF-8 但缺 BOM，补上
- `.vscode/settings.json` 固定 `files.encoding = utf8`，并**关闭** `files.autoGuessEncoding`

> `autoGuessEncoding` 是关键：它会让编辑器「自己猜」编码，并**覆盖**显式设置的 `files.encoding`。之前改了设置却不生效，就是它在抢。

**验证**　逐字符比对转换前后文本完全一致；重编译后镜像**完全相同**（`Code=8676 RO=272 RW=116 ZI=1172`），证明只动了字节、没动逻辑。

## 7. `73e2ea2` PC13 状态灯

**目的**　赛场上不可能一直连着串口。需要一个**远距离**一眼可见的状态指示。

**改法（分层）**

- 硬件层 `IndicatorLED.c`：只做四件事 `Init / TurnOn / TurnOff / Toggle`，不参与任何决策
- 策略层 `Service.c` 的 `Task_Indicate`：跑在 100ms 任务里，和其他 `Task_*` 并列

**状态表**

| 条件 | 灯 |
|---|---|
| 停车 / 上电 | 慢闪（500ms 翻转） |
| 运行中，视觉正常 | 常亮 |
| 视觉断线 | 快闪（100ms 翻转） |

**两个关键设计**

1. **故障锁存**
   视觉断线会让程序自动停车。如果「停车就变慢闪」，故障信号等于被藏起来了。
   所以故障标志只在**重新收到真实数据**时清除——断线后车停了，灯仍然快闪。

2. **启动边沿重新计时**
   `Vision_LastTick` 初值是 0。若上电 30 秒后才按启动，`30000 - 0 > 120` 会立刻误报断线。
   因此在 `CarRun_State` 的 0→1 边沿重新打时间戳。

**阈值**　断线判定 120ms，与 `Task_FetchVisionData` 的丢包判定（4 × 30ms）对齐，灯和车同时反应。

# 第 8 节　评估过但**没有做**的改动

> 「不做」也是设计决策，需要理由。

| 候选改动 | 结论 | 理由 |
|---|---|---|
| 电机低速死区补偿（给占空比加下限） | **不做** | 速度环是闭环 PI，积分项本来就在逐步顶穿静摩擦；硬加下限会在低速段制造极限环（车一顿一顿地抽） |
| 目标速度斜坡 | **不做** | 若直接作用在 `target` 上，急停会延迟约 200ms；且 30ms 与 5ms 两个任务会抢同一个变量。正确做法要用独立变量 + 非对称斜率，赛前来不及验证 |
| 蓝牙环形缓冲加 `count` 区分满/空 | **不做** | 人手发送间隔 ≥300ms，缓冲 100ms 排空一次，丢包成本几乎为零 |
| 使能 IWDG 看门狗 | **暂缓** | 模块已就绪，但任何一次 >1s 阻塞都会复位；未在实车充分验证前开启，风险大于收益 |
| `CarRun_State` 单写入点重构 | **赛后** | 能显著降低现场排障成本，但要动 5ms 内环和所有写状态的位置，赛前来不及完整验证 |

**判断标准**　赛前只接受「编译能验证 + 上车能立刻验证」的改动；纯结构性收益的改动一律推迟。

# 第 10 节　中断与优先级

分组：`NVIC_PriorityGroup_2`（2 位抢占 + 2 位子优先级）

| 中断 | 抢占 | 子 | 职责 |
|---|---|---|---|
| USART1（K210 视觉） | 0 | 0 | 收 1 字节并解析 |
| TIM3（1ms 时基） | 1 | 1 | 系统 tick |
| USART3（语音） | 2 | 1 | 收 1 字节 |
| USART2（蓝牙） | 3 | 1 | 存环形缓冲 |

**排序依据**　115200 下一个字节只有 87µs 窗口，视觉必须最高；时基被视觉打断的代价仅几 µs，可忽略；语音 / 蓝牙只需「收下再说」。

**注意**　`Protocol_GetVision()` 里的关中断段只允许做赋值，加任何耗时操作都会丢字节。

# 第 11 节　已知限制

1. **77° 急角**　摄像头在最后约 0.3m 会丢线，目前靠「保持上一次误差 + 最低速」通过，不是真正解出来的。
2. **视觉断线**　超过 120ms 无数据即自动停车，属于保护而非容错。
3. **看门狗关闭**　程序卡死不会自动复位，这是已知取舍。
4. **参数不持久化**　蓝牙调的参数掉电后丢失，需要手动写回 `Service_Init()`。
5. **PID 初始增益为 0**　上电后必须先通过蓝牙下发参数，车才会动。
