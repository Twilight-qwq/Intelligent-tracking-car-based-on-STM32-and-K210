# 1. 整体架构：谁负责什么

## 1.1 一句话分工

**K210 只负责"看"，把"车偏了多少"变成一个数字丢给 STM32；方向盘在 STM32 手里。**

K210 不碰电机，它甚至不知道轮子转多快。它每秒钟回答 25~30 次同一个问题：

> "在我眼里，车道中心线和我正前方差了几个像素？"

## 1.2 数据流

```
摄像头拍照 (160×120 灰度图)
   │
   ▼
vision.py   找出车道中心在第几列  ──→ "偏了 37 像素"
   │
   ▼
judge.py    拍板：平滑吗？丢线吗？要提前打方向吗？  ──→ err=37, state=1
   │
   ▼
main.py     塞进 4 个字节发出去     ──→ AA 25 01 55
   │
   ▼  串口 115200 8N1
STM32       PID 算出左右轮各转多快  ──→ 电机
```

## 1.3 为什么这么分

| 好处 | 说明 |
|---|---|
| 换转向算法不用动 K210 | 所有"怎么转"的逻辑都在 STM32，K210 只报告事实 |
| K210 不用管电机型号 | 换轮子、换减速比、换电机，视觉端一行不改 |
| 出问题好定位 | "看不见线"找 K210，"看见了但走歪"找 STM32 |

> 这个原则很重要：**测量和决策要分开**。
> `vision.py` 是纯测量（客观），`judge.py` 和 STM32 才是决策（主观）。

## 1.4 四个文件的分工

| 文件 | 行数 | 干什么 | 类比 | 什么时候动它 |
|---|---|---|---|---|
| `config.py` | ~160 | 全是数字和开关，没有逻辑 | **遥控器面板** | 调参只动它 |
| `vision.py` | ~420 | 相机几何 + 在照片里找线 | **眼睛** | 基本不动 |
| `judge.py` | ~130 | 判断、滤波、丢线处理 | **小脑** | 改策略才动 |
| `main.py` | ~120 | 开串口、开摄像头、死循环 | **心跳** | 基本不动 |

依赖方向是单向的：

```
main.py  ──>  vision.py  ──>  config.py
   │                            ▲
   └────────>  judge.py  ───────┘
```

**不会绕圈**，所以改哪个文件的影响范围是可预测的。

# 2. 基本概念（新手必读）

## 2.1 像素坐标怎么数

画面 160 宽 × 120 高，坐标原点在**左上角**：

```
        x = 0                                    x = 159
y = 0   ┌──────────────────────────────────────────┐
        │                                          │
        │                 画面顶部                  │  ← 拍的是远处 / 天空
        │                                          │
y = 59  │────────────── 画面中心行 ────────────────│
        │                                          │
        │                 画面底部                  │  ← 拍的是车脚下
y=119   └──────────────────────────────────────────┘
                        ↑
                     x = 80
                  画面中心列
```

| 概念 | 含义 |
|---|---|
| **行（y）** | 越大越靠近车，越小越远 |
| **列（x）** | 越大越靠右 |
| **画面中心列** | `CENTER_X = 160 // 2 = 80` |

代码里 `IMG_W, IMG_H = 160, 120`。

> ⚠️ 注意：**y 增大 = 靠近车**。这和数学课的坐标系是反的（屏幕坐标系的通病），
> 第一次看容易搞混。

## 2.2 灰度值是什么

彩色照片每个像素有 RGB 三个数。灰度图只有一个数：

| 值 | 含义 |
|---|---|
| 0 | 纯黑 |
| 255 | 纯白 |
| 中间 | 不同程度的灰 |

**为什么不用彩色？**

| | 灰度 | 彩色 RGB565 |
|---|---|---|
| 每像素字节 | 1 | 2 |
| 处理量 | 小 | 大一倍 |
| 帧率 | 高 | 低 |

找黑线本来就用不上颜色，用灰度能**快一倍**。这是 `main.py` 里
`sensor.set_pixformat(sensor.GRAYSCALE)` 的原因。

## 2.3 差速转向：为什么"偏差"能变成"转向"

小车没有方向盘，靠左右轮转速不同来转弯：

| 想要 | 左轮 | 右轮 |
|---|---|---|
| 直走 | 一样快 | 一样快 |
| 往右转 | 快 | 慢 |
| 往左转 | 慢 | 快 |
| 原地右转 | 正转 | 反转 |

用公式写就是：

```
左轮目标速度 = 基础速度 + 转向量
右轮目标速度 = 基础速度 - 转向量
```

所以 K210 只要告诉 STM32"偏差多大、往哪边"，STM32 就能算出两个轮子各转多快。

**K210 完全不需要知道这个公式**——这是分层的意义。

## 2.4 常见名词对照

| 名词 | 英文 | 白话 |
|---|---|---|
| 帧 | frame | 一张照片 |
| 帧率 | fps | 每秒处理几张 |
| 阈值 | threshold | 判断"黑还是白"的分界线 |
| 噪点 | noise | 不是线、但看起来像线的干扰 |
| 丢线 | lost | 画面里找不到车道中心 |
| 自适应 | adaptive | 参数会自己跟着环境变 |

# 3. 相机几何：画面第几行 = 车前多少米

对应 `vision.py` 第 22~100 行。

## 3.1 为什么需要这一节

摄像头装 20cm 高、低头 30°，那么**画面上的第 71 行，对应车前面 0.26 米**；
第 34 行对应 0.94 米。

问题是：如果你不知道这个换算，怎么决定"扫哪几行"？

- 靠人肉一个个试？那换个安装高度、换个镜头，全部重试一遍。
- 所以让程序**上电自己算**：读 `config.py` 里的高度、角度、视场角，
  推算出每一行在车前多少米、两条黑线在那行隔多少像素。

## 3.2 针孔相机模型

想象光线从镜头中心直着射出去，落在感光元件上形成一个点。

关键规律：**同一个物体，离得越远，成像越靠近画面中心**。这就是"近大远小"。

描述这个比例的常数叫**焦距**（单位：像素），代码里是 `F0`。

```
F0 = 画面半宽 / tan(半个视场角)
   = 80 / tan(90° / 2)
   = 80 / tan(45°)
   = 80.0 像素
```

| 量 | 值 | 来自哪 |
|---|---|---|
| 画面半宽 | 80 像素 | `IMG_W / 2` |
| 半视场角 | 45° | `HFOV_DEG / 2`，`HFOV_DEG = 90` |
| 焦距 `F0` | 80.0 | 上式计算 |

> ⚠️ `HFOV_DEG` 填错的直接后果：所有扫描行的位置都会偏。
> 判断方法见 9.2 节。

## 3.3 斜距与水平距离

`row_slant(v)` 和 `row_dist(v)` 算的是**两种不同的距离**：

```
        镜头 ●
             │╲
             │  ╲   ← 斜距（光线本身有多长）
             │    ╲
             │      ╲
    ─────────┼────────●───── 地面
             │← 水平距离 →│
             车
```

| 函数 | 返回什么 | 用在哪 |
|---|---|---|
| `row_slant(v)` | 斜距（米）：镜头到地面那点的直线距离 | 算横向像素间距要用 |
| `row_dist(v)` | 水平距离（米）：车前面多远 | 打印表、判断视野 |

**当光线朝上（射到天上）时，两者都返回 0**，表示"这一行没有地面"。
代码里判断条件是 `wz > -1e-6`。

## 3.4 为什么每一行的"像素间距"都不一样

关键概念：**同一个 25 厘米，在不同距离下占的像素数完全不同。**

```
远处（靠近地平线）        近处（画面底部）
   █  █                     █        █
   ↑ 22 像素                ↑   62 像素
```

所以 `row_gap_of(v)` 必须**每一行单独算**：

```
像素间距 = F0 × (实际长度 / 距离)
         = 80 × (0.25 / 斜距)
```

那个 `0.25` 是什么？**半车道宽 0.25 米**（赛道宽 50cm，一半 25cm）。

> 以后换更宽的赛道，只改 `0.25` 这一个数。

## 3.5 为什么只扫 5 行

| 方案 | 计算量 | 问题 |
|---|---|---|
| 120 行全扫 | 18240 次读像素 | 太慢 |
| 扫 5 行 | 760 次 | 够用 |

为什么 5 行够用？因为赛道在任意时刻都是"直"的——弯道也是圆弧，
5 个不同距离的采样点足以推算出"车偏了多少 + 前面往哪弯"。

`pick_rows()` 的挑选逻辑：

1. 把 120 行全算一遍，只留下"间距在 `GAP_MIN ~ GAP_MAX` 之间"的行
2. 在这段合格行里**等间隔**取 5 个（保证近处远处都有样本）
3. 反转顺序，变成"由近到远"

| 参数 | 作用 | 太小时 | 太大时 |
|---|---|---|---|
| `GAP_MIN` | 最远那行的最小间距 | 把太远的糊行也算进来 | 视野变窄 |
| `GAP_MAX` | 最近那行的最大间距 | 视野变窄 | 把撑出画面的行也算进来 |

## 3.6 `print_table()`：上车前必看

程序启动时会打印这样一张表：

```
焦距 F=80.0 px   地平线在第 14 行   最近能看 0.09 m
  行  71  车前 0.26 m  间距  62 px  权重 3
  行  62  车前 0.33 m  间距  52 px  权重 3
  行  53  车前 0.43 m  间距  42 px  权重 2
  行  43  车前 0.62 m  间距  32 px  权重 2
  行  34  车前 0.94 m  间距  22 px  权重 1
```

**怎么用这张表：**

1. 拿卷尺量一下"第 71 行大概在车前多远"，和表里的 0.26m 对得上吗？
2. 差很多 → `CAM_H_CM` 或 `CAM_PITCH_DEG` 填错了
3. 行号跑到地平线以上（小于 14）→ 参数错得很离谱

> 这一步没做对，后面怎么调 PID 都是白费。

# 4. 找线：从灰度图到车道中心

对应 `vision.py` 的 `scan_row()`。

## 4.1 整行处理的三步

```
① 读一整行 152 个像素
        ↓
② 自己算一个黑白分界线（自适应阈值）
        ↓
③ 找连续的黑色段，过滤掉不像线的
        ↓
④ 两根线取中点 / 一根线推算
```

## 4.2 手法一：自适应阈值

### 为什么不用固定值

最笨的办法是"像素值 < 100 就算黑"。问题是：

- 灯光一边亮一边暗 → 一边判对一边判错
- 摄像头自动曝光慢慢漂移 → 跑一会儿就不准了
- 换场地 → 全部重调

### 这里的做法

**每一行单独算一个分界线**：

```
阈值 = 这一行最暗的值 + (最亮 - 最暗) × 40%
```

代码：

```python
lo = min(vals)                                  # 这一行最暗
hi = max(vals)                                  # 这一行最亮
if hi - lo < C.CONTRAST_MIN:                    # 对比度太低，放弃这一行
    return -1, 0, -1
thr = lo + int((hi - lo) * C.BLACK_RATIO)       # 分界线
```

相当于每一行都在问自己：**"我这一行里，相对偏暗的那部分在哪？"**

### 为什么还要 `CONTRAST_MIN`

如果一行里最亮和最暗只差 5，说明这一行**根本没看到黑线**（比如全是白地），
继续算只会算出一堆噪声。直接放弃，省时间也避免误判。

## 4.3 手法二：黑段要"长度合适"才算线

一行里连续几个发黑的点，叫一个**黑段**。但黑段不一定是线：

```
像素:  230 240 235 20 18 22 19 240 238 ...
                  └──────┬──────┘
                    长度 4 的黑段  ✅ 算线
```

| 情况 | 判断 | 原因 |
|---|---|---|
| 长度 < `RUN_MIN`（3） | ❌ 丢掉 | 地面污点、反光噪点 |
| 3 ~ 26 像素 | ✅ 算线 | 正常黑线宽度 |
| 长度 > `RUN_MAX`（26） | ❌ 丢掉 | 两根线糊成一片，或横线/阴影 |

黑段的**中心**就是这条线的位置：

```python
c = (i + j - 1) // 2 + C.X_MIN
```

## 4.4 两根线都在：取中点

最理想的情况：

```
     左线         车道中心        右线
      █               ▼              █
  ────┼───────────────┼──────────────┼────
    first      (first+last)/2      last
```

但还要做一道检查：**两线间距和理论值差多少？**

```python
half = (last - first) // 2      # 实测的半间距
d = abs(half - gap)             # 和理论值比
if d <= C.GAP_TOL:              # 差在容差内，认
```

| `GAP_TOL` 太小 | `GAP_TOL` 太大 |
|---|---|
| 老是判不合格，白丢数据 | 旁边的桌子腿、门框也会被当成线 |

## 4.5 一根线都不剩：直接放弃

```python
if cnt == 0:
    return -1, dark, -1
```

返回 `-1` 表示"这一行没结果"，上层会跳过它，不参与平均。

## 4.6 只剩一根线：推断 + 间距表自愈

**这是整个文件最巧妙的地方。**

### 为什么必须支持"只剩一根"

顺时针跑的时候：

| 线 | 位置 | 连续性 |
|---|---|---|
| 外侧线 | 永远在车左边 | **永远连续，不会消失** |
| 内圈线 | 过弯时拐走 | 过弯前半米左右就消失 |

只靠"两根取中点"，**每个弯口都会瞎掉**。

### 怎么推断

先判断剩下的这根是外侧还是内圈——靠它**偏左还是偏右**：

```python
if first < CENTER_X - C.SIDE_DEAD:      # 明显偏左 = 外侧线
    return first + gap, dark, 1         # 中心 = 外侧线 + 间距
if last > CENTER_X + C.SIDE_DEAD:       # 明显偏右 = 内圈线
    return last - gap, dark, 2          # 中心 = 内圈线 - 间距
return -1, dark, -1                     # 太靠中间，分不清，放弃
```

### 为什么"分不清"时要放弃

如果这根线几乎在画面正中间，那它可能是外侧也可能是内圈，
**猜错方向就是反的**——车会往完全错误的方向打。

> **宁可没有，也不要错。** 没有数据只是丢一帧，错了会直接冲出赛道。

`SIDE_DEAD = 12` 就是"不敢判断区"的宽度。

### 间距表自愈

凡是两根线都看到的行，会拿实测间距**慢慢修正**那张表：

```python
ROW_GAP[gi] = (gap * 15 + half) >> 4     # 相当于 (15*旧 + 实测) / 16
```

每帧只改 1/16，所以就算 `CAM_H_CM` 量错了 2cm，跑一会儿也会自己纠回来。

> `>> 4` 是右移 4 位，等于除以 16。比除法快，在单片机上常用。

## 4.7 返回值

`scan_row()` 返回三个数：

| 返回值 | 含义 |
|---|---|
| `mid` | 车道中心的列号，`-1` 表示没找到 |
| `dark` | 这一行一共多少个黑像素（判断横线用） |
| `only` | `0`=两根都在，`1`=只剩外侧，`2`=只剩内圈，`-1`=一根都没有 |

# 5. 多行合成：加权平均

对应 `vision.py` 的 `find_lane()`。

## 5.1 为什么要加权

5 行各自算出一个偏差，不能简单平均——因为**可靠性不一样**：

| 行 | 距离 | 一个像素代表 | 可靠性 | 权重 |
|---|---|---|---|---|
| 第 71 行 | 0.26 m | 约 4 mm | 高 | 3 |
| 第 62 行 | 0.33 m | 约 5 mm | 高 | 3 |
| 第 53 行 | 0.43 m | 约 6 mm | 中 | 2 |
| 第 43 行 | 0.62 m | 约 9 mm | 中 | 2 |
| 第 34 行 | 0.94 m | 约 13 mm | 低 | 1 |

```
err = (3×近 + 3×次近 + 2×中 + 2×远 + 1×最远) ÷ 11
```

代码里 `SCAN_WEIGHT = (3, 3, 2, 2, 1)`。

## 5.2 顺手统计的四个附加信号

| 信号 | 怎么算 | 用途 |
|---|---|---|
| `hits` | 有几行成功找到中心 | `0` = 完全丢线 |
| `far` | 只看最远两行的加权平均 | 判断"前面弯有多急" |
| `far_hits` | 最远两行成功几行 | `0` = 前面看不见了 |
| `bars` | 有几行"整行八成都是黑的" | 终点横线检测 |

### `corner`：右弯信号

```python
if only == 1 and i <= 1:                        # 最近两行只剩外侧线
    if 0 <= mid - ROW_GAP[i] < C.CORNER_X:      # 推出来的中心很靠左
        corner = 1
```

翻译成人话：

> 最近两行里内圈线不见了，但按外侧线推出来的车道中心还在画面很靠左的位置
> → 说明内圈线已经拐到右边去了 → **前面是个右弯**。

这个信号专门给"提前打方向"用，见 6.4 节。

## 5.3 找不到任何线时

```python
if sum_w == 0:
    return 0, 0, 0, bars, 0, corner
```

返回全 0、0 命中，让上层走"丢线"逻辑（不是立刻停车）。

# 6. 拍板：`judge.py`

## 6.1 为什么用"类"而不是普通函数

有些东西必须**跨帧记住**：

| 要记的 | 为什么要记 |
|---|---|
| 上一帧的误差 | 滤波要用，丢线也要用 |
| 连续丢了几帧 | 决定"照旧走"还是"降速盲开" |
| 连续几帧看到横线 | 决定是不是真到终点了 |

普通函数里的变量每次调用都会清零，记不住。所以放进一个**对象**：

```python
j = Judge()          # 造一次，之后一直用
...
err, state = j.step(...)   # 每帧调一次，它自己记着上次的值
```

`self.xxx` 就是"这个对象自己的变量"，两次调用之间一直存在。

## 6.2 丢线是常态，不是故障

25~30 帧/秒，过弯、反光、压线的时候丢几帧太正常了。
**一丢就停车，车会一路顿挫。**

分级处理：

| 连续丢线帧数 | 怎么办 | 代码 |
|---|---|---|
| ≤ `LOST_KEEP`（10） | 假装没事，**照上一帧的结果继续发** | `return self.last_err, self.last_state` |
| > 10 | 降到状态 1（低速盲开），赌一把 | `return (self.last_err if C.LOST_ERR_HOLD else 0), 1` |

> ⚠️ **丢线时绝不发状态 3。**
> 3 是"到达终点"，丢线不能冒充终点，否则车会莫名其妙停在半路。

## 6.3 误差校准与增益

```python
err = int((err_raw - C.CALIB_OFFSET) * C.ERROR_GAIN)
```

| 参数 | 作用 |
|---|---|
| `CALIB_OFFSET` | 车摆正时读出来多少，就填多少，把它减成 0 |
| `ERROR_GAIN` | 整体放大或缩小，一般不动 |

## 6.4 提前打方向（重点）

### 为什么要提前

摄像头装在 20cm 高、低头 30°，**离车 0.25 米以内的路面根本看不见**。
这是镜头视场角决定的，换什么装法都一样。

```
   看得见的区域
  ┌──────────────┐
  │              │
  │              │
  └──────────────┘
   ░░░░░░░░░░░░░░░░  ← 0.25m 以内的盲区
        [ 车 ]
```

所以每到弯口最后二三十厘米，画面里只剩一条线甚至什么都没有。
**等真看见偏了，车已经冲出去了。**

### 对策

```python
turning = corner and err < C.CORNER_TRIGGER
if turning:
    err = C.CORNER_BIAS          # 直接把误差顶到 40
```

只要判断出"内圈线拐走了"，哪怕此刻车还正对着（误差接近 0），
也**立刻把误差顶到 40**，抢先打过去。

### 为什么要 `CORNER_TRIGGER`

```python
turning = corner and err < C.CORNER_TRIGGER    # 只有"刚进弯"才算
```

如果误差已经很大了还往同一个方向顶，**方向会打死**。
`CORNER_TRIGGER = 8` 的意思是：只有误差还小于 8（说明车还基本正对着）才触发。

> ⚠️ 这套逻辑假设**赛道顺时针、三个弯全是右弯**。
> 换逆时针赛道，要把 `CORNER_BIAS` 改成 `-40` 或设 `0` 关掉。

## 6.5 指数平滑

```python
err = self.last_err + ((err - self.last_err) >> C.SMOOTH_SHIFT)
```

不是直接用新值，而是"从旧值往新值挪一部分"：

```
err = 旧值 + (新值 - 旧值) ÷ 2^SMOOTH_SHIFT
```

| `SMOOTH_SHIFT` | 每次挪多少 | 效果 |
|---|---|---|
| 0 | 不滤波 | 反应最快，可能抖 |
| 1 | 一半 | 折中 |
| 2 | 四分之一 | 更平滑，但更迟钝 |
| 3 | 八分之一 | 很平滑，反应慢 |

> `>>` 是右移，相当于除以 2 的幂，比浮点除法快很多。

## 6.6 必须夹到 -128~127（致命坑）

串口那一帧里误差只占 **1 个字节**，有符号就是 -128 ~ 127。

如果算出 200 直接发出去，到了 C 语言的 `int8_t` 里会**回绕**：

```
200 的真实二进制: 1100 1000
按 int8 解读:      -56
```

**方向直接反了，车往反方向打。**

所以：

```python
if err > 127:
    err = 127
elif err < -128:
    err = -128
```

## 6.7 状态机 0/1/2/3

状态由"远处偏得厉害不厉害"决定，越弯越慢：

```python
curv = far_raw if far_raw >= 0 else -far_raw     # 取绝对值
if curv < C.CURV_T1:      state = 0
elif curv < C.CURV_T2:    state = 1
else:                     state = 2
```

| 状态 | 含义 | STM32 的基础速度 |
|---|---|---|
| 0 | 直道 | 40 |
| 1 | 一般弯 / 远处看不见 / 长时间丢线 | 25 |
| 2 | 急弯，或确认要拐弯了 | 15 |
| 3 | 冲过终点线 | 停车 |

两条额外规则：

```python
if far_hits == 0 and state < 1:
    state = 1           # 远处的路看不见了 = 前面到头了
if turning:
    state = 2           # 确认要拐了，直接降到最慢
```

# 7. 发送：帧格式与补码

对应 `main.py`。

## 7.1 一帧 4 个字节

```
0xAA | 误差(int8) | 状态(uint8) | 0x55
帧头      1 字节        1 字节      帧尾
```

| 部分 | 作用 |
|---|---|
| `0xAA` 帧头 | 告诉 STM32"新的一帧开始了" |
| 误差 | -128 ~ 127，正 = 车道在右 = 车偏左 |
| 状态 | 0 ~ 3 |
| `0x55` 帧尾 | 校验"这一帧完整收到了" |

> 为什么选 0xAA / 0x55？它们是互为反相的方波（`10101010` / `01010101`），
> 用示波器看特别好认，而且和"全 0 全 1"这种常见电平差别大。

## 7.2 负数怎么塞进一个字节

```python
uart.write(bytes((0xAA, err & 0xFF, state & 0xFF, 0x55)))
```

`err` 可能是 -40，串口一次只能发 0~255。

`-40` 在计算机里存成 8 位二进制是 `1101 1000`，也就是 **216**：

```
-40 & 0xFF  =  216   →  发出去是 216
```

STM32 那边按 `int8_t` 读，216 又被解释回 **-40**。

> 这就是**补码**的用处：同一个字节，
> 按无符号看是 216，按有符号看是 -40。两边约定好用同一个规则，数据就对上了。

## 7.3 主循环时序

```python
while True:
    clock.tick()                # 记下开始时间
    img = sensor.snapshot()     # 拍照片（最耗时）
    err_raw, far_raw, hits, bars, far_hits, corner = vision.find_lane(img)
    err, state = j.step(...)
    send_frame(uart, err, state)
    ...
```

| 步骤 | 耗时占比 | 说明 |
|---|---|---|
| `sensor.snapshot()` | 最大 | 曝光 + 传输 |
| `find_lane()` | 中 | 5 行 × 152 像素 |
| `j.step()` | 很小 | 纯算术 |
| `send_frame()` | 很小 | 4 个字节 |

> 想提速，优先降分辨率或减少 `N_SCAN`，别去优化 `judge.py`。

## 7.4 摄像头初始化

| 语句 | 为什么 |
|---|---|
| `sensor.reset()` | 复位到已知状态，避免上次运行的残留配置 |
| `set_pixformat(GRAYSCALE)` | 灰度比彩色快一倍 |
| `set_framesize(QQVGA)` | 160×120，够用且够快 |
| `skip_frames(time=2000)` | **等自动曝光稳定**，扔掉前 2 秒的废帧 |

`skip_frames` 很重要：摄像头刚上电时自动曝光还没调好，
前几十帧会一会儿全黑一会儿全白，直接拿去算只会得到垃圾结果。

# 8. 与 STM32 的接口

## 8.1 串口参数必须完全一致

| 项 | K210 | STM32 |
|---|---|---|
| 串口 | `UART1` | `USART1` |
| 波特率 | `BAUD = 115200` | `USART_BaudRate = 115200` |
| 数据位 | 8 | `USART_WordLength_8b` |
| 校验 | 无 | `USART_Parity_No` |
| 停止位 | 1 | `USART_StopBits_1` |
| 引脚 | `IO24`(TX) → `PA10`(RX) | `PA10` |
| 地线 | `GND` | `GND`（**必须接**） |

> 不共地 = 收到的全是乱码。这是最常见的接线错误。

## 8.2 状态 → 基础速度对照

STM32 端 `Service.c` 的 `Task_CalculateTargetSpeed()`：

| `car_state` | STM32 变量 | 默认值（counts/5ms） |
|---|---|---|
| 0 | `Speed_Straight` | 40 |
| 1 | `Speed_SmallAngle` | 25 |
| 2 | `Speed_LargeAngle` | 15 |
| 3 | —— | `Motor_SetDuty(0,0)` + `CarRun_State = 0` |

## 8.3 误差方向必须核对

| K210 发的 | STM32 的理解 | 车怎么动 |
|---|---|---|
| 正数（车道在右） | `turn > 0` | `左轮 = base + turn` → 左轮快 → 往右转 ✔ |
| 负数（车道在左） | `turn < 0` | `右轮 = base - turn` → 右轮快 → 往左转 ✔ |

**怎么验证**：手拿着车往右平移，看 `err` 是不是变成负数。
反了就改 `HMIRROR`（会自动取反）。

## 8.4 定时约束

| 层 | 周期 | 说明 |
|---|---|---|
| K210 发帧 | 约 33~40 ms | 25~30 fps |
| STM32 方向环 | 30 ms | `ServiceTask_30ms` |
| STM32 速度环 | 5 ms | `ServiceTask_5ms` |
| STM32 视觉超时 | 120 ms | 4 次 30ms 都没收到数据 → 强制停车 |

> **重要**：K210 在丢线时**仍然继续发帧**（只是状态降级），
> 所以 STM32 的 120ms 超时不会被误触发。这是两边刻意对齐的设计——
> "看不见线"和"串口断了"是两回事，要分开处理。

## 8.5 STM32 侧的二次保护

即使 K210 发来数据，STM32 还会做三件事：

| 保护 | 代码 | 作用 |
|---|---|---|
| 死区 | `if (fabsf(error) <= 3) error = 0` | 忽略细微抖动，防止车原地摆 |
| 限幅 | `turn` 夹在 `±base_speed` | 保证目标速度不为负（轮子不反转） |
| 断线停车 | `lostdata_time > 3` | 串口真断了就停 |

# 9. 调参指南

## 9.1 上车前（改 `config.py`）

必须量的三个数：

```python
CAM_H_CM      = 20.0    # 卷尺：镜头中心到地面，厘米
CAM_PITCH_DEG = 30.0    # 镜头光轴和水平面的夹角，低头为正
HFOV_DEG      = 90.0    # 镜头水平视场角，看参数表
```

改完看启动打印的表，**距离对不上就是这三个数错了**。

## 9.2 静态验证（车不动，手拿着）

| 步骤 | 看什么 | 不对怎么办 |
|---|---|---|
| 1 | IDE 预览里 5 条横线上有没有黑点 | 没有 → 调小 `CONTRAST_MIN` |
| 2 | 车摆正放车道中间，看 `err` | 不是 0 → 把这个数填进 `CALIB_OFFSET` |
| 3 | 手拿车往右平移，`err` 应变负 | 反了 → 改 `HMIRROR` |
| 4 | 5 个"间距"值和实测黑线位置对不对得上 | 对不上 → 调 `HFOV_DEG` |

## 9.3 动态调参顺序

> **铁律：一次只改一个参数。** 改两个就不知道是哪个起作用了。

| 顺序 | 调什么 | 从多少开始 | 观察 |
|---|---|---|---|
| 1 | STM32 速度环 `Kp/Ki` | 0.6 / 0.15 | 单轮悬空，看转速跟不跟得上 |
| 2 | STM32 方向环 `Kp` | 0.05 | 直道会不会左右摆 |
| 3 | STM32 方向环 `Kd` | 0.3 | 进弯会不会冲出去 |
| 4 | `CURV_T1/T2` | 10 / 22 | 减速时机早不早 |
| 5 | `SMOOTH_SHIFT` | 0 | 抖得厉害改 1 或 2 |
| 6 | `CORNER_BIAS` | 40 | 急弯能不能过去 |

## 9.4 常见现象 → 原因 → 改哪个

| 现象 | 最可能的原因 | 先动哪个参数 |
|---|---|---|
| 完全不发数据 | 接线 / 波特率 | 查 GND、查 `BAUD` |
| 发了但 STM32 没反应 | 帧头帧尾不匹配 | 用示波器看波形 |
| `err` 一直是 0 | 完全没找到线 | 看预览图，调 `CONTRAST_MIN` |
| 车左右画龙 | 方向环 `Kd` 太大或 `SMOOTH_SHIFT` 不够 | 先加平滑，再降 `Kd` |
| 直道走得直，进弯冲出去 | 转向不够 / 减速不够 | 加 `Kp`，降 `Speed_SmallAngle` |
| 每个弯口都瞎 | 一根线的判断不对 | 看 `SIDE_DEAD`、看 `corner` 是否触发 |
| 车往反方向打 | 误差符号反了 | 改 `HMIRROR` |
| 跑一会儿就停 | 串口断了 / K210 死机 | 看板载灯是不是快闪 |
| 帧率很低（< 15） | 分辨率太高 / 行数太多 | 减 `N_SCAN` |

# 10. 已知限制与坑

| # | 限制 | 后果 | 缓解 |
|---|---|---|---|
| 1 | **77° 顶角最难** | 转弯半径只有 0.25m，会短暂看不见线 | 靠"记住最后误差 + 状态 2 慢速"硬顶 |
| 2 | **0.25m 内是盲区** | 入弯最后一段看不见 | 提前打方向（`CORNER_BIAS`） |
| 3 | 只用 5 行，不是整图 | 急变路面反应慢 | 够用，别加太多行 |
| 4 | `HFOV_DEG` 是估算值 | 扫描行整体偏移 | 用打印表反推校准 |
| 5 | 终点检测只认"整行变黑" | 别的终点样式认不出 | 默认关着，要用得先说清长什么样 |
| 6 | 假设全右弯 | 逆时针赛道会反 | 改 `CORNER_BIAS` 符号或设 0 |
| 7 | 光照过暗/过曝 | 对比度不够，整行放弃 | 加补光灯、调 `CONTRAST_MIN` |

## 特别提醒：这些数字别随便改

| 参数 | 为什么危险 |
|---|---|
| `X_MIN` / `X_MAX` | 改了会扫到画面暗角，干扰最亮/最暗的判断 |
| `RUN_MAX` | 改小会把稍微宽一点的黑线判成"不是线" |
| `SCAN_WEIGHT` | 改了影响远近权重，直接改变转向手感 |
| `IMG_W/IMG_H` | 只在换分辨率时改，且 `vision.py` 里写死了 160×120 |

# 附录 B：一句话记住整个模块

> **K210 拿 5 行像素，每行自己算一个黑白分界线，找出黑段，
> 两条都看见就取中点、只剩一条就按已知间距推算，
> 5 行加权平均得到一个"偏了多少像素"的数字，
> 再配上"前面是不是弯"的状态，4 个字节发给 STM32。
> 怎么打方向、打多少，全归 STM32 管。**
