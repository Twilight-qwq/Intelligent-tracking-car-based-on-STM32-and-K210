## 二、比参数过期更严重：§6 的仿真不是当前系统

`_corner_unified.py` 文件头自己写明了仿真输入：

```
TURN_ARM_CM 20、CM_PER_COUNT 0.01610 —— Service.c
V_TURN 0.483 m/s（15档）、V_FAST 0.966 m/s（30档）
th = lo + (hi-lo)*0.40
keep = [...] if 0.45*lw <= ... <= 2.6*lw
bd <= 0.25 * 2 * HALF_PX[k]
```

即：旧刻度 0.01610、旧阈值 0.40、旧线宽上限 2.6、旧容差 25%、旧档位速度。当前固件是 `0.01402 / 0.55 / 3.0 / 40% / 84.1 cm/s`。

**§6 那张"直角 90.2°／钝角 38.5°／锐角 103.0°"的表，是旧参数下的理想世界结果。**

更关键的是仿真是**无噪声渲染**（白 235、黑 20，干净利落），完全没模拟这些真实因素：

- 喷绘布褶皱 → 等效高度抖 1 cm → 所有行半宽偏 3~6%（`Doc/明天现场流程与交接.md:224`）
- 反光把黑段切成两截 → 需要 `MERGE_GAP_RATIO = 0.20` 填洞
- 高光把"最亮"顶到 124 → 分界线落到地面之上、扫出 39/58/82/156 像素巨块 → 为此加了 `TRIM_BRIGHT_PERCENT = 97` 和 `REJECT_ROW_WITH_WIDE_RUN`
- 掉帧：处理最坏 37.9 ms > 27.7 ms 预算，而状态 2 要连续 2 帧确认 → 触发时机晚一帧，车多走约 2~3 cm，对 `TURN_ARM_CM = 20` 是显著比例

所以"仿真复现了实车现象"要打折：**几何趋势可能对，精确角度数字不能当决策依据。**

## 三、§5.3 的 −52 归因可能错了

材料说：偏差从 −10 掉到 −52、符号反了，原因是"只剩左线时用左线+半宽推中心"。

但 `VisualTest/live_scan_test.py:94-98` 的注释写得更具体：

> 巨块本身会被线宽上限挡掉，但挡掉之后剩下的"合格段"全是巨块的边缘，或者白纸外面那块深色地板（列 8~26、290~311）。实测这一条能造出中 54 / 259 / 268 三个错 100 像素的中心，**远偏差 −52 就是它**。

也就是说，工程师当时把 −52 归因于**反光/地板误检**，不是单线推算的固有缺陷。而且 11-19/20 已针对性加了三道补丁（窄 ROI、去高光、wide-run 作废）。

材料拿一个可能已被修掉的旧现象，推出了"弯里偏差永远不可信、只能靠编码器"的强结论。**修复后偏差到底可不可信，需要拿新固件重测。**

## 四、五边形是 5 个弯，不是 3 个

材料自己算出的内角是 `90°、90°、77°、141.5°、141.5°`——两个直角、两个钝角、一个锐角。一圈要过 **5 个弯**，顺序 `直 → 钝 → 锐 → 钝 → 直`。

全文按"三个弯"论述；§9.1"数第几个弯：第一个直角、第二个钝角、第三个锐角……"的省略号藏着第 4、第 5 个弯。按 3 个弯计数，跑后半圈必错。

**顺带得到一个免费的分类器**：赛道几何固定，出弯后累计里程即可查表决定下一个弯的角度，不需要任何新硬件。

| 出弯后里程 | 上一个弯 | 下一个弯 | 航向折角 |
|---|---|---|---|
| 110 cm | 直角 | 钝角 | 38.5° |
| 110 cm | 钝角 | 直角 | 90° |
| 200 cm | 钝角 | 锐角 | 103° |
| 200 cm | 锐角 | 钝角 | 38.5° |
| 294 cm | 直角 | 直角 | 90° |

注：这些是赛道边线长度，车走车道中心的路径长度略有差异，但 110/200/294 cm 差距远大于误差，容差足够。

## 五、回答材料 §11 的六个问题

### 1. 一个固定角度管三个弯（实际五个），有没有解？用什么信号？

**固定角度无解**——车不知道前面是哪个弯，这是根本矛盾。但不必靠视觉分类：

- **首选：编码器里程查表**（上表）。硬信号，不受反光、褶皱、光照影响，不需要新硬件，只需在出弯时清零里程并记住上一个弯的类型。
- **备份：视觉状态 2 触发**。保留原触发做兜底，但"用哪个角度"由里程表决定，不由视觉决定。
- 视觉图案分类（数 x 个数）已被实车数据否定，不建议再投入。

### 2. 如果必须分类，最稳的信号是什么？

**编码器里程**。理由：视觉图案的 x 个数在同一标签下横跨 6 行（实车 64 次），偏差符号会反，只有里程是确定的。注意 §8.4 那 64 次全被标成"锐角弯"，本身可能混了三个弯，所以"x 个数不能分类"的结论虽然成立，但论据要更谨慎。

### 3. "永远少转 + PD 补"靠不靠谱？

**比材料说的更不靠谱，但理由不同。**

材料说 PD 权限只有 `0.231×30 = 6.9`，补不动 50°。这个估算漏了 D 项：

- P 项 `0.231×30 = 6.93`，D 项 `0.53×8 = 4.24`，合计 **11.17**；最终限幅是 `±base_speed`（直行 30、状态 1 为 25、状态 2 为 15），11.17 不受限
- 满输出角速度 = `11.17 counts/5ms × 0.01402 cm/count ÷ 0.005s ÷ 11 cm ≈ 2.85 rad/s ≈ 163°/s`，补 50° 只需 0.31 s，期间前进约 13 cm，横向偏移约 5.5 cm

**所以"权限不够"是错的。真正的杀手有两个：**

1. `CORNER_HANDOVER_MS = 500` 规定转完后强制直行 500 ms 才交回 PD。少转 50° 后，这 500 ms 里车以 50° 斜角前进约 21 cm，横向偏移约 16 cm——车道半宽只有 20 cm，几乎压线出界，PD 根本没机会救。
2. 弯里偏差信号可能被反光/单线推算污染，方向可能反（§5.3 的争议）。

要试这条方案，必须先缩短或取消那 500 ms 强制直行，并确认偏差信号在新参数下可靠。

### 4. 有没有更简单的整体架构？

推荐"分层状态机 + 里程查表 + 角度三档"：

```
巡线（状态0/1）→ 里程达阈值 → 预备转弯（减速）
      → 固定差速 + 编码器计数停（角度查表）→ 出弯恢复（PD 接管，里程清零）
```

相较之下：
- "固定差速 + 固定时长"：更依赖打滑系数和电压，更脆
- "完全靠视觉"：弯里偏差不可靠，不可行
- "陀螺仪/IMU 闭环"：最直接，但改代码结构、3 天内风险高（用户手上虽有 MPU6050 手册，但时间不够）

### 5. 三天内必须出一个能跑完一圈的版本，怎么取舍？

- **Day 1**：角度改成三档/五段查表 + 里程触发。视觉状态 2 只做备份触发。这是最小改动、最大收益。
- **Day 2**：现场标定三个角度。不要按比例外推 1730→740/1980（打滑非线性），各转一次量角度再调。
- **Day 3**：联调。优先级：**钝角**（唯一过不去）> 直角（压线过头）> 锐角（能救回来）。

风险：摄像头 11-23 才到货，3 天窗口很紧；布面要铺平压四角；车必须先摆上赛道再上电（开机 2 秒锁曝光）。

### 6. §7.2 "1730 里有 41% 在补打滑"站得住吗？

**方向对，表述不准。**

- 理论 1230 counts 对应 90°，实测只转 64° → 转角增益是理论的 **71%**（64/90），即损失 29%
- 1730/1230 = 1.41，是"计数放大 41%"，不是"41% 在补打滑"

材料的核心判断是对的：**这个系数依赖地面、胎压、电压、载重，1730 不是车的常数，是"这台车在这块地"的常数**。所以所有靠固定计数的转角方案都会随场地变。

不依赖它的办法：① 给前轮万向轮加编码器测真实车速反推转角（硬件改动小）；② 每次铺完布现场重标三个角度；③ 用视觉修残余（前提是确认偏差信号在新参数下可靠）；④ 陀螺仪（最稳但时间不允许）。

## 六、现实约束下必须考虑的因素

这些在材料的仿真和取舍里基本没体现：

- **反光**：工程里有四道防线——窄 ROI（15 px 余量）、去高光 97% 分位、wide-run 整行作废、并段填洞。强反光仍能把近处几行全打成 `x`；此时状态机按设计**只降速、不判弯**，车会以 25 档冲进弯——这是材料没提的失败模式。
- **误判代价不对称**：`Doc/明天现场流程与交接.md:370` 原话——"把光照当弯 = 直道上打死方向 = 必死，而且没信息能救"。所以宁可漏判不能误判。
- **褶皱**：高度抖 1 cm → 半宽偏 3~6% → 远行配对失败 → 这就是 x 个数横跨 6 行的重要来源之一。
- **掉帧**：处理最坏 37.9 ms > 27.7 ms 预算；状态 2 要连续 2 帧确认。掉帧会让转弯起点晚一帧，多走约 2~3 cm，对 `TURN_ARM_CM = 20` 是显著比例。
- **曝光**：开机自适应 2 秒后锁死。车必须先摆上赛道再上电；换个角落、换光照都要重来。
- **设备**：只有一台车，摄像头刚损坏（线束全断），11-23 到货；验收 2026-12-05，缓冲 9 天。
